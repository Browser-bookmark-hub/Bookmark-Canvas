# 画布浏览统计：按天分桶账本重构实施计划（v4 修订版）

> **基准 Commit**：`1491383` (`HEAD -> main`)，承接 `6aa030b` → `b18b0cd` → `f74b68e` → `1491383`。  
> **定位**：处于未发布开发期，**不做旧版（v1/v2/v3）IndexedDB 快照历史数据迁移兼容**，直接采用简洁精炼的 `schemaVersion: 4` 数据结构；遇到旧版或空库时直接按冷启动重新建库。  
> **目标**：在不挂载常驻后台 `chrome.history.onVisited` 监听、保证画布打开后仅在空闲时轻量预热（无变化不写盘）的前提下，彻底解决跨 90 天活跃书签「增量次数倒退」、「>500 条溢出误覆盖老账」、「剪切/恢复误删老账」、「右键单条吞老账」以及「多端覆盖与重定向翻倍」等全链路问题。

### 2. Chrome 底层行为与真机实测依据

1. **`chrome.history.search` 无法按时间窗拆分次数**：即使传入近期 `startTime`，返回的 `HistoryItem.visitCount` 依然是 Chrome 库内该原始 URL 的总计数，只适合用来低成本筛选「哪些书签网址发生过访问」。
2. **「先白名单过滤 → 再仅对命中书签调 `getVisits` 落天桶」是最优顺序**（Chrome Beta 实测 15,000 条历史 + 300 个命中书签）：
   * **先过滤、再分桶**：仅对 300 个命中书签调 `getVisits`，总耗时 **`291.7 ms`**（其中 `getVisits` + 分桶仅 **`19.4 ms`**）；
   * **先全量分桶、再过滤**：对 15,000 条全网记录全调 `getVisits` 再筛选，总耗时 **`803.1 ms`**（多发 14,700 次无效 IPC）。
3. **`getVisits` 明细层必须处理的三个浏览器特性**：
   * **刷新与自动内嵌框**：`transition === 'reload'`（含刷新与会话恢复）及 `transition === 'auto_subframe'`（第三方页面隐藏内嵌 `iframe` 自动加载）均不属于用户主动打开书签，需一并剔除；
   * **同规范化 URL 重定向链双计**：收藏 `http://a.com` 点击自动 301/302 跳往 `https://a.com` 时，Chromium 会生成两条 `VisitItem`，后跳的 `referringVisitId` 指向前跳的 `visitId`，合并同一 `canonicalUrl` 多变体明细时必须按引用链去重；
   * **跨设备延迟同步**：手机端早些时候点击的书签可能数小时后才通过账号同步写入桌面端本地库，增量查询窗口往前重叠 24 小时（配合按天幂等覆写）即可无损接住。

## 三、新版数据结构设计（`schemaVersion: 4`，精简无冗余）

### 1. 核心思路：两段式瘦身账本 + 软保留保护 + 内存投影

将“封存老账”、“近期按天明细”与“变体网址清单”解耦，**不在每天的天桶里重复存储冗长原始 URL 字典**：

* **`archiveMap`**（`archiveCutoffDay` 以前封存老账）：
  `Map<canonicalUrl, { visitCount: number, lastVisitTime: number, domain: string, title: string }>`
  * 记录已超过 95 天滚动封存线（Chrome 已物理淘汰）的历史累计次数与老账最新访问时间。
  * 平时只增（老天桶到期滚入）不减；仅在收到 `allHistory` 全清，或书签被删除满 30 天宽限期后才物理移除。
* **`recentDayBuckets`**（近 95 天按天分桶纯数值明细）：
  `Map<dayNum, Map<canonicalUrl, [visitCount, lastVisitTime]>>`
  * 天桶编号采用 UTC 整数天号：`dayNum = Math.floor(clampedVisitTime / 86400000)`，无时区/夏令时跳变。
  * 每条仅存轻量二元数值（序列化为纯三元组 `[canonicalUrl, visitCount, lastVisitTime]`），0 访问天与非书签 0 占用，相比每桶嵌套 URL 字典体积缩减 5~10 倍。
* **`variantsMap`**（顶层变体原始 URL 表）：
  `Map<canonicalUrl, Set<rawUrl>>`（单键上限最多保留 `15` 个原始变体 URL）
  * 仅在顶层存一份该书签曾命中过的原始 URL 集合（如带不同协议、`www` 或历史 `utm` 参数的原始地址），供增量同步与单条删除对账时精确查询 `getVisits`。
* **`missingSinceMap`**（移出书签后的 30 天宽限期记录）：
  `Map<canonicalUrl, timestampMs>`
  * 当某网址暂时不在当前书签白名单中（如用户正在执行「剪切 → 搜索目标卡片 → 粘贴」、误删待恢复），**内存投影 `urlMap` 立即隐藏该项**，但底层 `archiveMap` 与 `recentDayBuckets` 保留 30 天；若 30 天内重新回到书签白名单则立即清除标记无损恢复老账，满 30 天仍未回归才物理淘汰。
* **`urlMap`**（仅存在于内存的 O(1) 运行时汇总投影，不落盘）：
  `Map<canonicalUrl, { visitCount, lastVisitTime, domain, title }>`
  * 仅对**当前存在于实时白名单 `liveData.targetSet`** 中的书签，由 `archiveMap` + `recentDayBuckets` 累加生成；变更时按受影响 `canonicalUrl` 局部重算，对外查询保持 O(1) 零感知。

### 2. IndexedDB 快照格式（键：`bookmark_visit_analytics`）

```javascript
{
  archiveItems: [
    // [canonicalUrl, visitCount, lastVisitTime, domain, title]
  ],
  dayBuckets: [
    // [dayNum, [[canonicalUrl, visitCount, lastVisitTime], ...]]
  ],
  variants: [
    // [canonicalUrl, [rawUrl1, rawUrl2, ...]]  // 每个 canonicalUrl 最多 15 个变体
  ],
  missingTargets: [
    // [canonicalUrl, missingSinceMs]
  ],
  knownTargets: [
    // canonicalUrl 字符串列表，用于跨重启/卸载识别真正新增的书签
  ],
  meta: {
    schemaVersion: 4,
    lastSyncTime: 1795582425000,
    lastPurgedAt: 0,
    savedAt: 1795582425500,
    archiveCount: 0,
    bucketDaysCount: 0,
    knownTargetsCount: 0
  }
}
```

**版本策略**：
* `loadSnapshotFromStorage()` 严格校验 `meta?.schemaVersion === 4`（并校验核心数组字段合法）。
* 遇到旧开发版（`v1`/`v2`/`v3`）或无快照时直接返回 `null`，走干净的 `performColdBuild()` 重建。

## 四、阈值、时间护栏与过滤规范

| 常量 / 规则 | 设定值 | 作用与用户侧意义 |
| :--- | :--- | :--- |
| `DEFAULT_HISTORY_DAYS` | `90` 天 | 冷启动与溢出重建时 `history.search` 回溯跨度（对齐 Chromium 本地库物理留存上限）。 |
| `RECENT_REBUILD_DAYS` | `89` 个完整天<br>`rebuildStartDay = floor((anchorTime - 90d) / 864e5) + 1` | **防第 90 天半截过期误伤**：溢出或增量覆写永远只动 `dayNum >= rebuildStartDay` 的近端天桶，不动第 90 天当天已被浏览器滚掉上半截的边界桶。 |
| `ARCHIVE_ROLLUP_DAYS` | `95` 天<br>`archiveCutoffDay = floor((anchorTime - 95d) / 864e5)` | **必须在每次对账第一步先执行**：将 `dayNum < archiveCutoffDay` 的天桶累加锁入 `archiveMap` 并移除该天桶，防止隔数月未搜索时老天桶被空结果覆写蒸发。 |
| `DELTA_OVERLAP_MS` | `24 小时` (`864e5`)，且不早于 `lastPurgedAt` | 短间隔增量 `history.search` 起点回看 24 小时（`max(0, prevSyncTime - 864e5, lastPurgedAt)`），既无损接住手机/多设备延迟同步记录，又绝不穿透全清时间线把清库前残影带回。 |
| `DELTA_DIRECT_REBUILD_DAYS` / 双引擎参数 | `21` 天；小目标 `<= 3500`、探针 `3000`、直查上限 `10000` | 距上次同步 `< 21` 天走小窗 `history.search`；`>= 21` 天、`overflow_at`、冷启动及 `>50` 批量新增统一走自适应双引擎（`0` 书签或 `maxResults: 1` 空历史秒退；`<=3500` 直接分批 `getVisits`；更大库先探 `3000` 条，打满且 `<=10000` 切 `getVisits`，超万级兜底 `history.search`）。 |
| `UNBOOKMARKED_RETENTION_DAYS` | `30` 天 | 书签被剪切或移除后，界面立即隐藏，底层老账保留 30 天宽限期再物理清理，彻底杜绝「剪切→搜索→粘贴」或误删恢复弄丢一年老账。 |
| `OLD_LEDGER_PROTECT_DAYS` | `85` 天 | 单条 `deleted_urls` 护栏：若该书签在近端天桶无记录且总 `lastVisitTime < anchorTime - 85d`，判定为 Chrome 滚动到期淘汰，直接跳过不伤老账。 |
| **有效访问过滤与去重** | 剔除 `reload` 与 `auto_subframe` + 同链 `< 500ms` `referringVisitId` 去重 + 未来时间钳制 | 1）刷新/会话恢复与网页内嵌隐藏 `iframe` 不计次数；<br>2）同一 `canonicalUrl` 下仅当 `referringVisitId` 命中同组 `visitId` **且时间差 `< 500ms`**（HTTP 301/302 为 `0ms`，头部脚本跳转 `< 300ms`）才合并为 1 次，保留超过 `500ms` 的站内正常二次点击；<br>3）若系统时间异常导致 `visitTime > anchorTime`，统一钳制为 `anchorTime`，防止脏时间永久霸榜 `@最近`。 |
| `GET_VISITS_BATCH_SIZE` / 分片让出 | `100` 条/批 + `250 条 / 10ms` 解析让出 | `getVisits` 每批 100 个并发且批间让出事件循环；`scanHistoryMatches` 在返回 `>= 500` 条时拆包后立刻让出一帧，并以 `250 条 / 10ms` 分片让出，防止大包与 JS 解析叠加掉帧。 |
| **多端同步通道** | `BroadcastChannel('bcs_visit_stats_v4')` + `staleByPeer` 脏标记 | 主画布标签页与侧边栏双开时，任一端落盘后广播最新 `savedAt`；另一端收到后不打断正在执行的 `loadingPromise`，仅置 `internalCache.staleByPeer = true` 穿透 30 秒节流并在下次读取或写盘前先对齐最新快照。 |

## 五、六大核心流程细节

### 1. 权威白名单解析与临时栏目就绪守卫（`resolveLiveBookmarkData`）

1. 读取永久书签树（`chrome.bookmarks.getTree()`，失败回退 `cachedCurrentTree`）+ 画布临时栏目（`CanvasState.tempSections`）。
2. **双源完整性判定（`isCompleteWhitelist`）**：
   * 仅当永久书签树成功返回，**且**画布临时栏目运行时已完成加载（如 `isCanvasSearchStateReady()` 为真或 `CanvasState` 已完成 BCS 初始化）时，`isCompleteWhitelist` 才为 `true`。
   * 若页面刚打开瞬间临时栏目尚未异步加载完，`isCompleteWhitelist` 为 `false`：**此时绝不将临时栏目书签打上“已移除”标记，也绝不清理任何账本数据**，彻底杜绝启动早期竞态误伤临时栏目书签。

### 2. 统一访问明细汇总器（`collectBucketedVisitsForCanonical`）

针对某个 `canonicalUrl` 及其候选 `rawUrls` 集合：
1. 并发调用 `chrome.history.getVisits({ url })` 拿到所有候选原始 URL 的 `VisitItem[]`；
2. 过滤掉 `!v || v.transition === 'reload' || v.transition === 'auto_subframe'` 及 `!(Number(v.visitTime) > 0)` 的无效项；
3. **同规范化 URL 重定向链去重（带 `< 500ms` 时间窗保护）**：
   * 按 `visitId` 去重并建立 `visitById` 映射；
   * 若某条记录的 `parent = visitById.get(v.referringVisitId)` 存在，**且 `Math.abs(v.visitTime - parent.visitTime) < 500`**（HTTP 301/302 在 Chromium 内时间戳完全相等即 `0ms`，同步脚本跳转 `< 300ms`），则将上游 `parent.visitId` 标记为跳转中间源予以剔除，仅保留链尾落地访问；时间差 `>= 500ms` 的同页锚点或站内链接正常二次点击予以完整保留，绝不误杀；
4. **时间戳钳制与分桶**：将 `clampedTime = Math.min(Number(v.visitTime), anchorTime)` 按 `dayNum = Math.floor(clampedTime / 864e5)` 归入对应天计数与最大时间戳。

### 3. 冷启动全量构建（`performColdBuild`）

1. **触发时机**：打开画布页后仅在空闲时轻量预热快照并追齐增量（数据无变化不写盘），同时在聚焦搜索框、执行 `@热度`/`@最近` 或右键文件夹「信息」时按需就绪。
2. 若 `!liveData.hasAuthoritativeTree`：仅返回空内存映射，**不落盘覆盖 IndexedDB**。
3. **真 0 书签 / 真 0 浏览历史快速短路与自适应双引擎**：
   * 0 书签：0 次历史 API 调用，直接保存空 `v4` 快照（补齐 `syncedWithCompleteWhitelist: true` 且后续 `ensureMemoryLoaded` 直接命中快路径不重复对账）；
   * 调 `resolveAdaptiveHistoryScanPlan`：若待查 URL `<= 3500`，先用 `maxResults: 1` 判空后直接全批 `getVisits`；若 `> 3500`，先用 `maxResults: 3000` 探测（`0` 条直接秒退，`< 3000` 直接过滤命中项，打满且 `<= 10000` 切全目标分批 `getVisits`，超万级再全拉 `history.search` 兜底）。
4. **分批查询落桶与精确记账变体**：
   * 仅当某书签确实存在有效访问（`totalCount > 0`）时才将其原始 URL 写入 `variantsMap`，绝不让占大多数的 0 访问书签撑大快照；
   * `dayNum < archiveCutoffDay` 的极少数未过期同步老记录直接计入 `archiveMap`，其余计入 `recentDayBuckets`；
5. 构建内存投影 `urlMap`，原子提交并立即写盘、发送 `BroadcastChannel` 通知。

### 4. 日常增量与删除分级对账（`reconcileLoadedState`）

冷恢复或重对齐时一律在局部 `stagedState` 中执行完下述固定顺序，最后一步再通过 `commitReconciledState` 原子切换到 `internalCache`：

1. **第一步（铁律先执行）：老天桶滚动封存（`rollupExpiredDayBuckets`）**
   * 将 `recentDayBuckets` 中所有 `dayNum < archiveCutoffDay`（95 天前）的天桶累加进 `archiveMap`（`visitCount` 相加，`lastVisitTime` 取较大值），随后删除这些老天桶。
   * **意义**：即便用户隔了半年没点过搜索框，此前存下的老天桶也会在任何覆写发生前安全锁进 `archiveMap`，绝不丢失。
2. **第二步：分级处理后台删除信号（与 `>= 21` 天长间隔重建合一）**
   * **情况 A — 清空全部历史（`purgedAt > prevSyncTime`）**：
     * 清空 `archiveMap`、`recentDayBuckets`、`variantsMap`、`missingSinceMap`，并记录 `state.lastPurgedAt = purgedAt`（持久化进 `meta.lastPurgedAt`）；
     * 重置 `knownTargets = new Set(liveData.targetSet)`；若 `purgedAt < anchorTime`，仅拉取 `[purgedAt, anchorTime]` 间的新访问，且明细严格过滤 **`visitTime >= purgedAt`**（精确到毫秒，不用整天零点），随后直接进入第五步原子提交落盘。
   * **情况 B — 大批量删除溢出（`overflowAt > prevSyncTime`，>500 条）或滞留 `>= 21` 天长间隔**：
     * **`archiveMap` 与 `dayNum < rebuildStartDay` 的老天桶 100% 原样保留**；
     * 构建安全重建集：除 `liveData.targetSet` 外，始终并入 `missingSinceMap` 软保留项，且 `!isCompleteWhitelist` 时并入 `knownTargets`（对既无候选 URL 又无老账的未就绪临时书签暂时从 `knownTargets` 剔除，待白名单完整时由第三步自动补种）；
     * 按 `resolveAdaptiveHistoryScanPlan` 自适应策略重算并仅重写可查项在 `dayNum >= rebuildStartDay` 的近 89 天桶（空历史秒退或全批直查均回填 `queriedInCaseB`）；
     * **注意不提前返回**：继续向下执行**第三步**（确保离线期间发生的剪切回归、30 天到期回收与新增书签 `knownTargets` 对齐一并生效），仅跳过第四步常规增量，最后在第五步重算投影并立即写盘。
   * **情况 C — 零星单条/小批量删除（`deleted_urls`，<=500 条，前台只读不直接清空，落盘后写 `synced_at` 由后台裁剪）**：
     * 筛选 `deletedAt > prevSyncTime` 且命中书签的 `canonicalUrl`；
     * 若某书签在 `dayNum >= rebuildStartDay` 无任何天桶记录且总 `lastVisitTime < anchorTime - 85d`，判定为浏览器到期滚动淘汰，直接跳过；
     * 否则**先清除该书签在 `[rebuildStartDay .. todayDay]` 所有天桶中的旧条目**，再对其关联全部原始 URL（`variantsMap` + 当前书签原始 URL）调 `getVisits`（过滤 `visitTime >= state.lastPurgedAt`），仅回填 `dayNum >= rebuildStartDay` 的剩余记录（若近端被删光而 `archiveMap` 有底数，自动精准回落为老账底数）。
3. **第三步：白名单对齐、30 天软保留回收与新书签补种**
   * 当 `liveData.isCompleteWhitelist === true` 时：
     * 已回归白名单的网址：从 `missingSinceMap` 移除标记，老账自动复活参与投影；
     * 当前不在白名单中的已建档网址：首次缺席记入 `missingSinceMap[url] = anchorTime`（投影立即隐藏）；若 `anchorTime - missingSince >= 30d`，才从 `archiveMap`、`recentDayBuckets`、`variantsMap`、`missingSinceMap` 中彻底清除。
   * 对比 `liveData.targetSet` 与 `knownTargets` 识别真正新增的书签（若第二步刚走完情况 B，跳过已在 `queriedInCaseB` 完成检查的书签；常规下 `<= 50` 条直接分批 `getVisits`，`> 50` 条走 `resolveAdaptiveHistoryScanPlan` 自适应扫描，均遵守 `visitTime >= state.lastPurgedAt`）。
4. **第四步：短间隔时间窗增量同步（`gapDays < 21`，情况 A/B 已全扫时跳过）**
   * 查询窗口起点取 **`queryStartTime = Math.max(0, prevSyncTime - 864e5, state.lastPurgedAt || 0)`**（回看 24 小时防跨设备同步延迟，同时严守 `lastPurgedAt` 全清边界不回穿），调 1 次 `history.search` 找出近期活跃的命中书签集合 `touchedCanonicals`；
   * 计算安全覆写下界：**`effectiveMinSyncDay = Math.max(Math.floor(queryStartTime / 864e5), rebuildStartDay)`**（绝不触碰 `< rebuildStartDay` 的天桶）；
   * 对每个 `touchedCanonical`：
     1. **先删除它在 `[effectiveMinSyncDay .. todayDay]` 所有天桶里的旧条目**（确保昨天被部分清除归零的记录不会残留）；
     2. 查询其全部候选原始 URL 的 `getVisits`（经去重、过滤及 `visitTime >= (state.lastPurgedAt || 0)` 校验），将 `dayNum >= effectiveMinSyncDay` 的结果写入对应天桶；
     3. 仅局部重算这些 `touchedCanonicals` 在 `urlMap` 中的汇总值。
5. **第五步：水位线推进与防覆盖落盘**
   * 更新 `lastSyncTime` 并清除 `staleByPeer` 标记；若落盘前检测到其他端已写入更新的 `savedAt`，先重读对齐最新快照再落盘，避免主页面与侧边栏互相覆盖；若本次无数据及白名单变动，仅推进内存水位线，距上次落盘满 1 小时才做一次防抖落盘（避免无效整包写盘与双开互打）。

### 5. 右键单个书签「信息」面板：不扫全库，也不吞老账（`getSingleUrlHistoryStats`）

彻底解决「搜索列表显示 `101 次`（100 老账 + 1 今天），右键信息却只显示 `1 次`」的前后打架问题：
1. **绝不调用 `ensureMemoryLoaded()`、绝不触发 `history.search` 全量扫描**；
2. 获取该网址关联的候选原始 URL（当前传入 `targetUrl` + 若内存已热时的已知变体），直接调 `getVisits`（同样走刷新/`auto_subframe` 剔除与 `< 500ms` 同链跳转去重），耗时 `< 1.5 ms`；
3. **老账底数合算（含全清信号校验）**：
   * 若内存账本已就绪（且无未处理的 `purged_at` / `staleByPeer`）：直接取内存中该书签 `archiveMap` + `< rebuildStartDay` 天桶的沉淀底数，加上本次实时查到的 `>= rebuildStartDay` 访问次数，时间取两者最大；
   * 若内存账本未加载（纯冷态右键单书签）：并行读取 IndexedDB 单键快照对象与 `chrome.storage.local.get(['canvas_history_purged_at'])`（总耗时 `~2 ms`，不建全库索引、不跑历史扫描）：
     * 若 **`purgedAt > (snapshot.meta?.lastSyncTime || 0)`**，说明用户刚清空了全部浏览器历史而尚未打开搜索，旧快照已作废，直接忽略老账，仅返回 `visitTime >= purgedAt` 的实时 `getVisits` 结果；
     * 否则将该书签在快照中 `< rebuildStartDay`（含 `archiveItems`）的沉淀底数与实时 `>= rebuildStartDay` 的 `getVisits` 结果合并返回。

### 6. 文件夹与域名统计（保持统一去重口径）

* 搜索分组、文件夹行与右键文件夹「信息」继续统一走按 `canonicalUrl` 去重的 `computeFolderAggregatedStats`，读取内存投影 `urlMap`，不重复统计同网址多份书签副本。

### CDP 端到端验收清单（覆盖全部用户真实触发场景）

1. **跨 90 天增量不倒退**：某书签封存老账 `20` 次（110 天前），今天新点开 `1` 次并触发增量 → 搜索 `@热度` 与右键「信息」均精准显示 **`21` 次**（既不倒退成 `1`，右键也不吞掉老账的 `20`）。
2. **隔 100+ 天未搜索再回归不丢账**：构造 `lastSyncTime` 为 105 天前、天桶中存有第 96~102 天记录的快照，今天新访问后聚焦搜索 → 验证先完成滚动封存、第 96~102 天次数完整并入 `archiveMap` 零丢失。
3. **清掉昨天历史后再点击不残留**：昨天访问 `5` 次入桶，执行 `deleteRange` 清掉昨天记录后今天新访问 `1` 次 → 验证昨天天桶被擦除归零，最终精准显示 **`1` 次**而非 `6` 次。
4. **`http → 301 → https` 点击不翻倍且不误杀站内二次点击**：收藏短跳地址（自动 301/302 到同规范化 URL）真实打开后，再在落地页正常点击同规范化 URL 链接（间隔 `> 500ms`）→ 验证自动跳转合并为 `1` 次、人工二次点击正常累加为 **`2` 次**。
5. **清空全部历史后冷态右键单书签立即归零**：书签原有 `20` 次老账，执行 `deleteAll` 后不点搜索框直接右键该书签「信息」→ 验证识别到 `purged_at > lastSyncTime` 直接显示 **`0` 次**，且此后 24 小时回看窗绝不穿越 `lastPurgedAt` 带回旧残影。
6. **`>500` 条批量删除溢出保老清近**：同一书签「老账 `20` 次 + 近 3 天 `2` 次」，触发 >500 条历史删除溢出 → 重建后精准回落为 **`20` 次**且 `lastVisitTime` 回到老账时间，同时正常完成离线期白名单软保留对齐。
7. **剪切书签 → 搜索目标卡片 → 粘贴不丢老账**：含 `20` 次封存老账的书签被暂时移出书签树（模拟剪切），期间执行搜索（验证搜索结果立即隐藏该书签），随后重新加回书签树 → 验证 `20` 次老账无损恢复。
8. **主画布标签页 + 侧边栏双开不互相覆盖**：两端同时打开，侧边栏增量产生新计数落盘后广播通知，主标签页置脏重读最新快照，不会拿旧内存覆盖回退侧边栏刚写入的次数。
9. **隐藏内嵌 `iframe` 与异常未来时间防护**：`auto_subframe` 记录不计入访问次数；未来异常时间戳被钳制为当前时间，不永久霸榜 `@最近`。
