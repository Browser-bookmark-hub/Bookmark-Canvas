## 1. 这份计划书要解决什么问题

第三刀只处理永久栏目主栏 / 副本这条线。

目标不是复制主 DOM，也不是给每个副本再造一份正文真相源。

目标固定为：

- 永久栏目主栏与副本共享同一份书签树内容源
- 主栏和每个副本都保留各自独立的视图壳

换句话说：

- 共享的是内容源
- 独立的是视图壳
- 不是共享同一个 DOM 实例

## 2. 当前仓库现状

### 2.1 当前已经是“一个内容源，多个 DOM”

当前仓库里，永久栏目内容本来就主要来自浏览器书签树，不是每个副本各自持久化一份正文。

`history_html/history.js` 里当前有：

- `getBookmarkTreeSnapshot`
- `cachedTreeData`
- `__buildPermanentTreeSourceFragment`
- `__renderPermanentTreeIntoTree`

说明现在已经存在：

- 主永久栏目树的统一缓存
- 副本树的二次渲染入口

### 2.2 当前副本创建仍然强依赖主 DOM / 旧存储键

`history_html/bookmark_canvas_module.js` 里当前有：

- `__createPermanentSectionCopyFromStorage`
- 创建副本时优先调用 `window.__renderPermanentTreeIntoTree(tree)`
- 兜底时直接取主栏 `originTree.innerHTML`

同时副本壳状态仍然散在多个 key：

- `permanent-section-position`
- `permanent-section-copies`
- `canvas-permanent-tip-text`
- `canvas-permanent-tip-text-copy-*`
- 各种 scroll / expand 分区 key

这说明当前实现方向已经对了，但还没有形成稳定的“视图壳对象”。

### 2.3 第三刀真正要收口的是“壳”

第三刀不改永久栏目主内容真相源：

- 继续是 Chrome bookmarks API / 规范化 permanent snapshot

第三刀真正要收口的是：

- 主栏视图壳
- 副本视图壳
- 导出 / 同步里对主栏与副本的表达方式

## 3. 第三刀的前置边界

### 3.1 依赖第一刀

第三刀默认第一刀已经完成：

- permanent snapshot 有统一协议入口
- 同步 / 导入 / 导出不再各自解析永久树
- 永久内容源和视图壳读口已经能分开

### 3.2 依赖第二刀

第三刀默认第二刀已经完成：

- 空白栏目正文已切到 `markdownSource` 单一真相源
- `.md` 正文和 `.canvas` 布局已经分边

这样第三刀在处理永久栏目时，就不会再和空白栏目正文、`.canvas` 布局边界互相牵扯。

### 3.3 第三刀不做什么

- 不把永久栏目主内容改成 Markdown-first
- 不把副本改成独立书签树正文源
- 不重做现有 DOM 合同
- 不提前删除 `copyId`、目录定位、搜索跳转、导出节点 id、同步识别这些旧外部接口

## 4. 第三刀锁死的外部语义

### 4.1 内容源

- 主永久栏目和所有副本共用同一份 `permanentTreeSnapshotProtocol`
- 主永久栏目导出真实正文
- 副本只导出引用 / 包装，不导出第二份树正文

### 4.2 视图壳

每个永久视图只保留自己的壳状态。

最少包括：

- `viewId`
- `copyId`
- `displayIndex`
- `descriptionMd`
- `scrollState`
- `foldState`
- `cardState`

这里的 `descriptionMd` 用来承接“说明也遵守 Markdown 单一真相源”的方向。

当前仓库现有的 `canvas-permanent-tip-text*` 仍然可以先作为迁移读侧和兼容写侧，但 HTML 不应再被长期视为壳正文真相源。

### 4.3 DOM 与节点标识

第三刀先保留这些外部合同：

- `.permanent-bookmark-section`
- `.bookmark-tree`
- `data-permanent-section-copy-id`
- `.canvas` 中的 `permanent-section`
- `.canvas` 中的 `permanent-section-copy-*`

也就是：

- 外部标识不变
- 内部实现从“主树 clone / 借主树 DOM”切成“同源独立渲染”

## 5. 面向当前仓库的实施顺序

### 5.1 第一步：先把永久视图壳整理成对象

先不要大改渲染，先把当前散落的 key 收成统一读写对象。

读口至少要能从现有仓库收集出：

- 主栏位置尺寸
- 副本列表与显示顺序
- 主栏 / 副本说明
- 主栏 / 副本滚动状态
- 主栏 / 副本折叠状态

这样第三刀后面所有模块都能先拿“壳对象”，不再直接各自拼 localStorage。

### 5.2 第二步：把主栏 / 副本渲染统一到同一内容源入口

`history_html/history.js` 已经有 `__renderPermanentTreeIntoTree(tree)`，第三刀要把它固定成唯一内容渲染入口。

要求是：

- 主栏渲染走它
- 副本渲染也走它
- 不再依赖 `originTree.innerHTML` 作为长期兜底主路径

这样每个视图仍有自己的 DOM，但内容都从同一份 snapshot 渲染出来。

### 5.3 第三步：让副本创建 / 恢复都只依赖内容源 + 视图壳

当前 `__createPermanentSectionCopyFromStorage` 已经很接近目标。

第三刀要把它进一步收口成：

- 读 `permanentViewShellProtocol`
- 创建视图壳 DOM
- 往该 DOM 的 `.bookmark-tree` 里渲染共享内容源
- 绑定该副本自己的说明、滚动、折叠、拖拽行为

而不是：

- 从主栏复制一份行为和内容

### 5.4 第四步：导出 / 导入 / 同步跟着切壳对象

涉及文件：

- `history_html/bookmark_canvas_module.js`
- `history_html/sync/obsidian-git-sync.js`

第三刀后这些链路应当改成：

- 主永久栏目输出一份内容正文
- 副本输出引用包装和自己的壳信息
- `.canvas` 继续承载主栏 / 副本 file node 布局
- 同步比较时，正文只比较一份 permanent snapshot；副本差异只比较壳

### 5.5 第五步：把依赖 `copyId` 的周边模块切到壳对象

当前这些地方都在消费 `copyId`：

- `history_html/canvas_sidebar_directory.js`
- `history_html/bookmark_tree_context_menu.js`
- 导出 `.canvas` 节点 id
- 同步识别与定位

第三刀不能把这些识别方式打断。

正确做法是：

- 保留 `copyId`
- 但让这些模块从统一视图壳对象拿数据
- 不再直接假设副本状态只散在 DOM 或 localStorage 某个旧 key

## 6. 第三刀完成后的预期结果

- 主栏和副本继续显示成多个独立卡片
- 任意一个副本都不持有第二份永久书签树正文
- 主栏与副本的树内容始终来自同一份 snapshot
- 主栏 / 副本说明、滚动、折叠、卡片状态继续允许独立
- 导出 / 同步 / 比较终于能把“内容差异”和“壳差异”分开

## 7. 验证要点

### 7.1 内容一致性

- 新增 / 删除 / 移动书签后，主栏和所有副本都能反映同一份变化
- 副本不出现“旧 DOM 内容没刷新、主栏已刷新”的分叉
- 导出时副本文件不重复落第二份树正文

### 7.2 视图壳独立性

- 副本 A 的滚动不影响副本 B
- 副本 A 的折叠不影响副本 B
- 主栏说明与副本说明可以不同
- 副本拖拽、位置、尺寸互不污染

### 7.3 外部接口兼容性

- `copyId` 不变
- 搜索定位 / 跳转正常
- 目录栏定位正常
- 导出 `.canvas` 节点 id 仍可识别
- 同步对主栏 / 副本的识别不退化
- 右键菜单和多副本选中态同步不退化

### 7.4 性能与稳定性

- 创建副本时不再依赖主 DOM 已经完整可用
- 主栏重渲染后，副本仍能按统一内容源刷新
- 懒加载、路径徽章、变化标识在副本上不应丢失

## 8. 回滚与并行协作要点

### 8.1 回滚原则

- 回滚优先切回旧渲染入口，不删除新协议数据
- 保留旧 DOM 合同和旧存储键的兼容读口
- 出问题时先回退“壳对象读写 / 独立渲染路径”，不要回退别人同时动过的外围模块

### 8.2 安全迁移原则

- 先读旧 key，组装成新壳对象
- 再逐步让新调用方依赖壳对象
- 验证稳定后，再考虑清理直连旧 key 的分支

### 8.3 并行协作原则

- `history.js`、`bookmark_canvas_module.js`、`canvas_sidebar_directory.js`、`bookmark_tree_context_menu.js` 都是高碰撞文件
- 第三刀实现必须优先走“包旧入口、保旧合同、逐步切换”
- 不能为了收口永久副本而用覆盖式回退处理冲突，更不能回退别人正在改的调用方

一句话总结：

- 第三刀不是把副本做成第二份永久正文
- 而是把当前仓库已经存在的“共享书签树 + 多个副本 DOM”路线，正式收口成“共享内容源 + 独立视图壳”
