# 路线图与架构演进思考

> 定位：后续演进方向与核心要点备忘（非已排期开发承诺）。

---

## 一、画布架构与性能演进

- **从 DOM 虚拟化走向「壳肉分离」（JS 内存与 BCS 按视口进出）**：
  - **现状卡点**：DOM 层已支持视口虚拟化与低细节裁剪（`lowDetailDomPruned`），但 JS 内存层仍由 `storageBCS_core.js` 的 `__loadCanvasTempStateBundleFromBcs()` 启动时全量读入所有 `bcs:section:<id>`；`bcs:canvas` 缺少卡片壳摘要字段，且 `bookmark_canvas_module.js`、`canvas_sidebar_directory.js`、`search.js`、`history.js` 等存在上百处对 `CanvasState.tempSections` 的同步遍历（全量保存兜底、搜索切片、目录树、溯源、导出等），默认全部 `items` 常驻内存。
  - **演进要点**：
    - `bcs:canvas`（或独立轻量壳清单）补充极小壳摘要（`title`、`label`、计数等），首屏秒开即可绘制远景轮廓、连线与左侧目录，视野外分片不读盘；
    - 复用底层已有的 `__loadTempSectionsFromBcs(sectionIds)`，实现 `items` 按视口进出内存，长期离屏休眠时同时清空 DOM 与 JS 引用交还 GC，并守住“未加载分片绝不覆写磁盘”；
    - 全局跨卡片查询（搜索、标签汇总、溯源、统计）统一收口至 IndexedDB 索引。
- **低细节模式缩放临界区闪烁治理**：
  - 缩放进入低细节模式并触发 DOM 裁剪后，在临界缩放比例区间（如 40%～50%～100%）频繁停顿往返缩放易引起裁剪/恢复振荡闪烁。
  - 后续需补齐进入/退出滞回（Hysteresis）区间，并协同定时器与关键帧缩放状态。
- **远期渲染与模块化边界**：
  - 渲染管线长期可关注 [gpucanvas](https://github.com/berkantay/gpucanvas) 等 GPU 画布思路；
  - 维持“不对老代码做高风险全量 ESM 打包重写”的边界，仅在新增独立复杂子系统时延续 `tools/build-tiptap-bundle/` 模式，用 TypeScript + 清晰模块边界隔离构建。

## 二、外置研究路线（优先级最高，Bookmark-Research 与生态协同）

- **为什么优先外置分析（务实妥协）**：
  - 本扩展在**导出（`.canvas` / JSON / 快照包）与 GitHub 推送/拉取**上的存量工程已经非常成熟；相比在 MV3 扩展内部重造一整套 Agent Harness，优先让外置宿主直接读取导出/推送包是最稳妥、工程性价比最高的选择。
- **核心载体与多宿主协同**：
  - 主载体为独立伴侣插件 [Bookmark-Research](https://github.com/Browser-bookmark-hub/Bookmark-Research)（Skill + 本地 MCP + CLI），重点覆盖并验证四大宿主：**Codex、Claude Code、DeepSeek Harness（dsh）、Pi**；
  - 演进路径：**单 Skill → Skill + 本地 MCP 聚合 → 多 Skill / 多 MCP 封装的 Agent Plugin**；导出包中的 `AGENTS.md` 也可配合 GitHub 连接器服务网页端研究入口。
  - 生态分工：`Bookmark-Canvas`（主工作台与落点）+ `Bookmark-Research`（外置只读研究层）+ `Bookmark-Record-Recommend`（时间、行为与 Push & Analyze 数据辅助，优先级高于备份）+ `Bookmark-Backup`（快照、变更审计与网页存档辅助）。
- **画布天然的双层上下文**：
  - **空间上下文**：`.canvas` 拓扑、卡片组嵌套、连接线方向、常规链式栏目分裂关系（`A-1` → `A-1-1`）、同书签跨卡片位置、`visibleRange` 锚点视野。
  - **时间与交互上下文**：Git 提交记录、书签节点时间戳、`@热度` 访问统计、置顶/折叠状态，以及 `descriptionMd`、`note`、`tags` 携带的人类语义。
- **三层外部调研与 LLM Wiki 沉淀**：
  1. **直接读取 / Non-reasoning Fetch**：有明确 URL 时直接提取正文（或并发轻量抓取）；
  2. **Agentic Search**：由宿主 Agent 驱动多轮检索、跨栏目对比、去重与清洗整理；
  3. **Deep Research**：调用外部 Deep Research API 或连接器生成带来源引用的专题报告；
  - 调研结果沉淀为 Markdown / **LLM Wiki** 知识库，经用户确认后再以 R5 特殊临时栏目格式导回画布。
- **速度优化与检索 / SQLite / RAG 取舍**：
  - **工具调用提速**：参考 [codegraph](https://github.com/colbymchenry/codegraph) 与 `smartsearch` / `aether-search` 的低延迟思路，压缩过深的 Python 工具链路、减少频繁串行阻塞（如优化 `research_record` 类工具的并发与调用频次）。
  - **原生结构优先，不先建重型 RAG**：书签核心是高时效 URL 数据库，网页正文持续变动且常带登录墙，过早维护全量向量库 / Reranker / GraphRAG 成本过高；首阶段优先直接检索原生 JSON 与 `.canvas` 显式结构。
  - **轻量增强候选项**：可评估 JEV / 小模型辅助检索打分，以及独立于用户手工 `note` 之外的专项检索摘要字段 `info`（必须支持海量存量老书签渐进处理，不能只依赖收藏瞬间抓取）；仅当离线大规模重复研究需求充分成立时，再考虑 SQLite 本地索引。

## 三、浏览器内操控与 AI 工程成本梯度（CDP / MCP / Harness）

### 工程复杂度梯度：外置分析 ＜ CDP 特化握手 ＜ 扩展自暴露 MCP ＜ 端内 AI Harness

- **1. 依赖外部浏览器 Agent 操控页面（CDP 是关键通道）**：
  - **为什么绕不开 CDP**：基于普通网页脚本注入（Content Script）的浏览器插件/自动化工具受限于 Chrome 扩展源隔离，无法注入和操作 `chrome-extension://` 页面；真正能直接操控扩展画布页面的外部通道，本质上都依赖 **CDP**（包括原生 CDP、`chrome-devtools-mcp` 开启 `--categoryExtensions`，以及底层走 CDP 的 Playwright / Puppeteer / Browser-use）。
  - **现状瓶颈与特化方向**：通过 CDP / F12 已能实际操作画布（如新建空白卡片、移动临时/永久栏目），但当前大模型必须先阅读源码再临时编写脚本，耗时长且脆弱。后续若要提速，需要**页面侧特化能力**：提供稳定的局部只读接口与操作原语 + 面向浏览器 Agent 的 `AGENTS.md`（按当前视野或选中卡片分片读取永久/临时/空白栏目、时空上下文与搜索结果，避免一次性灌入全库）。
  - **现实门槛**：仍受浏览器远程调试开关（`chrome://inspect/#remote-debugging` / `edge://inspect/#remote-debugging`）、`--categoryExtensions` 等平台限制，对普通用户有配置门槛。
- **2. 扩展自暴露特化 MCP（次级备选）**：
  - 若不完全依赖通用 CDP 摸索 DOM，可扩展自身暴露一套**特化 MCP 工具**；但它依然依赖浏览器的外界调试/通信端口或本地桥接进程，并且必须处理好 MV3 前后台通信与生命周期协同。
- **3. 扩展内接云端 Agent API / 自建本地 Harness（工程最重，暂缓）**：
  - 即便接入现成的云端 Agent 运行时或 API（如 OpenAI Agents API / Responses API、Cloudflare Agents、AWS Bedrock AgentCore 等，或自配 DeepSeek / Gemini API），由于云端沙盒无法直接读写本地 `chrome.bookmarks` 与前端画布 DOM，扩展本地仍然必须承接一整套 **Agent Harness**（工具映射、状态同步、MV3 后台保活、密钥隔离与人工确认 UI）。
  - 该路线工程量远高于外置分析与 MCP，因此目前仅作按钮级交互预留，不作为近期主线。

## 四、明确不做与暂不推进

- **客户端不做**：暂不开发独立桌面客户端，不将现有画布强行迁移为 React + XYFlow、SQLite WASM 或 Obsidian 插件。
- **不做重型后台爬虫与全网监听**：不把扩展做成常驻抓正文爬虫，不复制 `Bookmark-Record-Recommend` 的常驻全网浏览流水监听。
- **不做附件与文件管理**：坚持轻量化边界，不做图片/PDF/音视频附件库或第二个 Obsidian（见 [限制与妥协.md](限制与妥协.md)）。
- **不无确认自动写回**：任何 AI 产出默认只读，写回永久书签树或远端同步目录必须经用户选定范围并显式确认。
