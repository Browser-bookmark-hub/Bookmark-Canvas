# 画布浏览统计：双引擎自适应扫描与空库防御改造计划书

> 本文档基于 2026-11-26 在真实日常 Edge Beta 环境（`1,066` 永久 + `3,418` 临时 = `3,347` 去重书签 / `3,370` 原始 URL；近 90 天 `17,704~17,711` 条历史；IndexedDB `v4` 快照 `370 KB`）的只读 CDP 压测结果，以及对 `Bookmark-Canvas-main/history_html/search/history_stats_service.js`、`Bookmark-Canvas-main/background.js` 和 `Bookmark-Canvas-main/history_html/search/search.js` 的 CodeGraph 调用链审计整理而成。
> **当前状态**：已实施并通过验证（已完成 `history_stats_service.js` 改造与文档同步；Node 回归/自适应全套单测及 Chrome Beta 实机 CDP 验证全部通过）。

## 一、核心背景与为什么要改

### 1. 「肉眼体感顺滑」与「绝对耗时更短」的双重原因
两种扫描方式最终**都会**调用 `chrome.history.getVisits({ url })` 走 `dedupeAndBucketVisits` 完成去重和按天分桶，差别只在**如何拿到待查 URL 集合**：
- **方法 A（`history.search` 拉时间窗 → 白名单过滤 → 命中项 `getVisits`）**：
  - 传入 `maxResults: 0` 拉近 90 天全部 `17,711` 条历史时，Chromium 必须跨进程一次性打包、并在画布渲染主线程反序列化 `17,711` 个 `HistoryItem` JSON 对象（光 IPC+拆包即耗时 `361~410 ms`）。叠加后续 `parseCanonicalUrl` 过滤，导致总耗时 **`450~502 ms`**，且产生 **`58.3~83.7 ms` 的单帧掉帧卡顿**（超过人眼可感知的 `16.7 ms` 帧预算及 `50 ms` 长任务阈值）。
- **方法 B（书签目标集直接分批 `getVisits`，每批 100 并发 + 让出主线程）**：
  - 查询在浏览器进程的 History DB 后台线程按 SQLite `urls.url` 索引执行，绝大多数未访问 URL 秒返空数组 `[]`。每 `100` 个并发完成后调用 `yieldToMainThread()` 交还主线程，因此全库 `3,370` 个 URL 总耗时仅 **`116.9~125.5 ms`**（带上 `variantsMap` 的 `3,404` 个 URL 为 **`134.0 ms`**），且每帧间隙稳定在 **`8.4~8.7 ms`**（`0` 次掉帧，哪怕扩展到 `15,000` 个 URL 帧间隙仍仅为 **`9.4 ms`**）。

### 2. 为什么必须保留「双方法」，而不能全部换成方法 B？
1. **短间隔增量场景**：日常打开间隔在数天内（`1` 天仅 `99` 条、`14.6 ms`；`7` 天 `1,179` 条、`32.2 ms`）时，历史增量远小于书签全集，方法 A 比盲扫全部书签快 **4~9 倍**。
2. **URL 变体发现能力**：`chrome.history.getVisits({ url })` 仅做精确字符串匹配。现行 `scanHistoryMatches` 通过 `parseCanonicalUrl`（去协议/`www.`/尾斜杠/`utm_*` 等跟踪参数）把日常访问到的变体原 URL 收入 `variantsMap`（Edge Beta 上已累计 `596` 组、`631` 条变体）。完全放弃 `history.search` 会导致 **18 个书签计数漏算/偏低**（其中 `1` 个掉成 `0`、`17` 个偏少）。
3. **长间隔退化与大规模书签反向边界**：
   - `runReconciliationPipeline` 第 4 步的拉取起点为 `prevSyncTime - 24h`（并非固定只查近 24 小时）：若用户停用 **`30` 天**（Edge Beta 上攒到 `5,920` 条历史，`128.9 ms`）乃至 `90` 天，增量入口会退化成重度全量扫；
   - 反过来，若用户导入 **`15,000+` 个书签** 但近 90 天只有一两千条历史，盲扫 `15,000` 次 `getVisits` 需要 **`511.7 ms`**，远慢于拉两千条历史（**`~35.9 ms`**）。

### 3. 空库边界审计发现（避免重复冷启动 / 无效全量）
- **实锤发现（0 书签重复对账缺陷）**：[`ensureMemoryLoaded`](../Bookmark-Canvas-main/history_html/search/history_stats_service.js#L2103-L2128) 第 2103~2105 行判断快照有效性的条件为：
  ```js
  const hasContent = snapshot.knownTargets.size > 0 ||
      snapshot.archiveMap.size > 0 ||
      snapshot.recentDayBuckets.size > 0;
  ```
  当用户没有任何书签（`knownTargets.size === 0`）时，即便首次已经完整构建并写入了带 `lastSyncTime > 0` 的空 `v4` 快照，之后每次打开页面/侧边栏 `hasContent` 均判定为 `false`，都会绕过快路径强行同步执行 `resolveLiveBookmarkData()` + `reconcileLoadedState()`。
- **空历史保护**：若在冷启动或溢出重建中切换至「全书签直查」，若未先判空历史，遇到「1 万书签 + 0 历史」的全新隐私浏览器时会白发 1 万次空 `getVisits`。用 `history.search({ text: '', startTime: scanStart, maxResults: 1 })` 仅耗时 **`0.8 ms`** 即可提前秒退。

| :--- | :--- | :--- | :--- |
| **`DELTA_DIRECT_REBUILD_DAYS`** | **`21`**（天） | 日常第 4 步增量入口 | `14` 天（`71.8 ms`）内走增量极快且能持续采集新 URL 变体；`30` 天（`128.9 ms`）已追平 3 千书签全扫且出现 `16.7 ms` 帧波动。以 `21` 天为界：`< 21` 天走时间戳增量，`>= 21` 天改走双引擎近 89 天重置刷新（**保留 `archiveMap` 与 `variantsMap`**）。 |

## 四、分场景改造细节与状态流转

### 场景 1：空库与升级防重复（修复现存 2 处快照闭环缺陷 + `0.8 ms` 判空门神）
1. **0 书签快照读取判定修复（`ensureMemoryLoaded` 第 2103~2128 行）**：
   - 将 `hasContent` 升级为：
     ```js
     const hasSyncedState = snapshot.knownTargets.size > 0 ||
         snapshot.archiveMap.size > 0 ||
         snapshot.recentDayBuckets.size > 0 ||
         (snapSyncTime > 0 && snapshot.syncedWithCompleteWhitelist);
     ```
   - 当用户 0 书签且上次已完整对齐落盘后，再次开页/切侧边栏直接 `1.8 ms` 命中快路径秒返空 Map，不再重复同步执行 `resolveLiveBookmarkData()` 与 `reconcileLoadedState()`。
2. **白名单完整状态落盘修复（`runReconciliationPipeline` 第 1912 行前）**：
   - 现行代码在 `1912` 行只更新了 `state.syncedWithCompleteWhitelist = Boolean(liveData.isCompleteWhitelist)` 却未置位 `metaChanged`。若冷启动时临时栏目尚未就绪（落盘为 `false`），后续临时栏目就绪且无新增书签（如 0 书签或纯永久书签用户），`setsDiffer` 与 `dataChanged` 均为 `false`，会导致长达 1 小时内始终不重写 IndexedDB、快路径条件持续失效。
   - **修正**：在 `state.syncedWithCompleteWhitelist = ...` 赋值前补充：
     ```js
     if (!state.syncedWithCompleteWhitelist && liveData.isCompleteWhitelist) {
         metaChanged = true;
     }
     ```
3. **空历史 `0.8 ms` 秒退**：
   - 任何进入自适应双引擎重扫的路径，若目标集合为空直接跳过并写齐 `lastSyncTime`；若非空，前置 `historySearch({ text: '', startTime: scanStart, maxResults: 1 })` 返回 `0` 条时直接跳过扫描并写齐 `lastSyncTime` + `knownTargets`。
4. **升级兼容性**：
   - 保持 `SCHEMA_VERSION = 4` 不变（本次改造只改扫描策略、阈值与快照门控，不改动 IndexedDB 存储格式），用户版本升级后直接继承现有 `v4` 快照与 `variantsMap`，**零重复冷启动**。

---

### 场景 2：日常时间戳增量同步（`gapDays < 21` 天且未溢出）+ 削峰让出
- **保留现行小窗增量**：继续从 `queryStartTime = Math.max(0, prevSyncTime - DAY_MS, minVisitTime)` 拉取小窗 `history.search`，过滤命中后对当窗访问过的极少数书签调用 `getVisits` 更新 `recentDayBuckets` 并发 `canvas-history-stats-updated` 事件，兼顾 `14~72 ms` 极速同步与新变体发现。
- **`scanHistoryMatches` 帧峰值削峰（第 1071~1103 行）**：
  - 当 `rawItems.length >= 500` 时，在 `await historySearch(...)` 返回后**立刻先执行一次 `await yieldToMainThread()`**，把 Mojo IPC 反序列化与随后的 JS URL 解析拆进不同渲染帧；并将让出间隔从 `40 ms / 2000 条` 调整为 `10 ms / 250 条`，防止 `14~20` 天窗口或万级兜底回退时出现单帧掉帧。
- **边界口径（如实披露）**：
  - 长停用（`gapDays >= 21`）在 `runReconciliationPipeline` 第 2 步即与 `overflowAt > prevSyncTime` 合并并标记 `ranFull90dScan = true`，直接转入场景 3，避免先白跑一遍 `deleted_urls` 情况 C 与第 3 步补种再到第 4 步推倒重算；
  - 短间隔（`< 21` 天）走 `history.search` 时，新点击的重定向跳转书签因 Chromium `TransitionIsVisible()` 只返 `CHAIN_END` 仍不实时入账（搜索列表不变、单条右键「信息」实时准确），需等到长间隔/`>500` 溢出重建时校准。

---

### 场景 3：`overflow_at` 溢出重建、长间隔（`gapDays >= 21`）、冷启动与批量新增（`>50`）统一自适应引擎
抽出通用自适应历史匹配/重算基础能力（覆盖全文件所有高耗时 `scanHistoryMatches` 入口：`performColdBuild`、`overflowAt` + `gapDays >= 21`、对账第 3 步 `unhitNewCanonicals.length > 50`，以及 `seedNewBookmarks` `entries.length > 50`）：

```
构建待查集合（含必要安全并集，共 B 个待查 URL）：
  ├─ B === 0 → 仅清理目标范围旧桶（若有），直接结束
  ├─ B <= SMALL_TARGET_DIRECT_URLS_MAX (3500)：
  │    └─ 调 historySearch({ startTime: scanStart, maxResults: 1 })（~0.8 ms）
  │         ├─ 0 条 → 历史全空，清空对应范围旧桶，直接收工
  │         └─ >=1 条 → 对全部目标走 queryAndApplyBucketedBatch / seedCanonicalEntries（每批 100 `getVisits` + 让出）
  └─ B > 3500：
       └─ 调有限探针 historySearch({ startTime: scanStart, maxResults: 3000 })（~36~60 ms）
            ├─ 返回 0 条 → 历史全空，清空对应范围旧桶，直接收工
            ├─ 返回 < 3000 条（数学上保证未截断！）→ 直接用本次返回做白名单过滤 + 对命中项走分批 getVisits
            └─ 返回 === 3000 条（打满，说明历史海量！）：
                 ├─ B <= DIRECT_GETVISITS_URL_CAP (10000) → 放弃拉剩余历史，改走全目标分批 getVisits（<= 334 ms, 0 掉帧）
                 └─ B > 10000（万级以上超大规模书签）→ 兜底走 historySearch({ startTime: scanStart, maxResults: 0 }) 拉全历史过滤
```

**必须同步落地的 2 项源码级防坑修正**：
1. **防止 `variantsMap` 快照体积翻倍与 0 访问垃圾占位（全文件 4 处写口统一收口）**：
   - 现行代码在拿到 `bucketed.totalCount` 之前就无条件写 `variantsMap`：`queryAndApplyBucketedBatch`（966~969 行）、`seedCanonicalEntries`（1020~1024 行）、`scanHistoryMatches`（1092 行）、`Step 4`（1859~1860 行）以及 `seedNewBookmarks`（2199~2201 行，在调 `seedCanonicalEntries` 前的预处理循环里即无条件写入）。全书签走直查后，会把占全库 `~85%` 的 0 访问书签及纯 `reload` 访问全塞进快照，并导致 `collectAllLedgerCanonicals` 删书签时白挂 `missingSinceMap` 30 天。
   - **修正**：
     - 彻底移除 `scanHistoryMatches`（1092 行）和 `seedNewBookmarks` 预处理循环（2199~2201 行，仅在 `internalCache.urlMap.has(canonicalUrl)` 时补充已有活跃书签的新原始 URL）对 `variantsMap` 的无条件写入；
     - 在 `queryAndApplyBucketedBatch`、`seedCanonicalEntries` 与 `Step 4` 中，推迟到 `writeBucketsForCanonical` 落桶**之后**调用 `syncVisitedVariantsAfterBucket`：以 `hasLedgerEntry(state, canonicalUrl)` 为唯一准绳保留/写入当前书签 URL，且仅当 `visitTotalCount > 0` 时才写入 `extraRaw`（防止 `< minDayNum` 越界访问或纯 `reload` 新变体污染 `variantsMap`）；若 `!hasLedgerEntry(state, canonicalUrl)`，顺带从 `state.variantsMap` 清理该键。
2. **防止「临时栏目未就绪 / 剪切宽限期」重扫丢近 89 天数据（第 1657~1683 行、`search.js` 第 3192 行竞态）**：
   - 聚焦搜索框时 `warmupBookmarkHistoryStatsIfNeeded` 先于 `await ensureIndexForModeLoaded` 拉起对账，`isTempSectionsReady()` 可能仍为 `false`（此时 `liveData.targetSet` 仅含永久书签，缺少临时书签），且 `state.missingSinceMap` 里的剪切保留书签也不在 `targetSet` 中。若此时发生 `overflowAt` 或 `gapDays >= 21` 并一口气删光近 89 天 `recentDayBuckets`、只用 `liveData.targetSet` 重算并推高 `lastSyncTime`，之后临时栏目就绪时因 `knownTargets` 已有这些键且增量只回溯 24 小时，会**永久抹掉临时/剪切书签 2~89 天的统计**；而之前 0 访问的临时书签因不在 `variantsMap` 中、`knownTargets` 又只存剥掉协议的 `canonicalUrl`，当轮同样无法查 `getVisits`。
   - **修正**：
     - 全量/近 89 天重建构建待查集合时，在 `liveData.targetSet` 之外，**始终并入 `state.missingSinceMap.keys()`**，并在 **`!liveData.isCompleteWhitelist` 时并入 `state.knownTargets`**（由 `variantsMap` 提供已有历史条目的原 URL）；
