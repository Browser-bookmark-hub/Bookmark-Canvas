# 存储现状与重构分析

## 1. 结论先行

当前这套存储可以运行，但不算一套收敛过的架构。

它更像是历史演进后叠加出来的结果：

- Chrome 书签 API、`localStorage`、`chrome.storage.local`、`IndexedDB` 都在参与
- 导出结构、同步结构、运行时真实存储结构并不完全一致
- `localStorage` 同时承担了主数据、视图态、启动镜像、跨页面同步信号、兼容兜底等多种职责

所以问题不在于 Chrome 提供了三种存储，而在于我们当前没有把这些存储的边界彻底收口。

一句话判断：

- 当前方案能跑
- 但确实偏乱
- 也没有发挥出极致性能
- 不建议现在做一次“全量大搬家”
- 但非常有必要先把数据域、真相源、正式持久化层分清楚

---

## 2. Chrome 为什么会给三种存储

Chrome 扩展里常见的三种存储，不是重复设计，而是为了不同职责：

- `localStorage`
  - 最简单
  - 同步读写
  - 适合启动瞬间就要拿到的小型 UI 状态
  - 不适合大对象主状态

- `chrome.storage.local`
  - 扩展正式持久化 API
  - 异步
  - 适合扩展长期设置和正式状态
  - 可跨扩展页面、侧边栏、后台使用
  - 有 `storage.onChanged`

- `IndexedDB`
  - 浏览器数据库
  - 更适合超大对象、恢复包、缓存、staging
  - 不适合作为大量零碎小设置的主路径

另外，本项目已经声明了 `unlimitedStorage` 权限，见 `manifest.json`。

这意味着容量限制被放宽，但不意味着 `localStorage` 自动变成最优方案。

---

## 3. 当前四类主数据实际存在哪里

需要先区分：

- 运行时真实持久化
- 导出时拼出来的结构

这两者目前不是一回事。

### 3.1 永久栏目主内容

永久栏目主内容当前**不是**存到插件自己的 JSON 主状态里。

它的正文真相源是 Chrome 书签树：

- 运行时通过 `chrome.bookmarks.getTree()` / `browserAPI.bookmarks.getTree()` 获取
- 导出永久栏目时，也是重新从书签 API 拉树

所以：

- 永久栏目主内容的真相源 = Chrome 书签 API
- 不是插件本地再额外持久化一整份永久正文

### 3.2 永久栏目副本

永久栏目副本当前没有各自持久化完整书签树正文。

当前副本主要持久化的是“视图壳”：

- 副本列表
- 副本位置
- 副本尺寸
- 副本显示顺序
- 副本说明
- 副本滚动位置
- 副本折叠状态

目前这些主要落在 `localStorage`：

- `permanent-section-position`
- `permanent-section-copies`
- `canvas-permanent-tip-text`
- `canvas-permanent-tip-text-copy-*`
- 以及若干分区 scroll / expand key

所以：

- 永久栏目正文真相源 = Chrome 书签 API
- 永久栏目壳数据 = `localStorage`

### 3.3 临时栏目、空白栏目、Canvas 连线

这三类当前共用一个主状态桶：

- key：`bookmark-canvas-temp-sections`

这个对象里实际包含：

- `sections`：临时栏目
- `mdNodes`：空白栏目 / Markdown / 文本类卡片
- `edges`：Canvas 连线

也就是说，当前“临时栏目 + 空白栏目 + 连线”被当成同一个画布文档在存。

这部分当前的后端顺序是：

1. 默认先走 `localStorage`
2. 如果 `localStorage` 超限，则切到 `chrome.storage.local`
3. 如果再不行，则切到 `IndexedDB`

所以它现在不是一个稳定单一后端，而是一个“分级 fallback 主状态”。

### 3.4 导出文件

导出结构并不是插件平时真实存储的原始形态，而是导出时再拼装。

全量备份时会输出：

- `bookmark-canvas.backup.json`
- `.canvas`
- `.md`
- 其他辅助文件

其中全量 JSON 里会同时放：

- `storage`
- `permanentTreeSnapshot`
- `canvasState`

也就是说：

- 导出结构比运行时存储结构更“完整”和“可移植”
- 但它不是当前运行时的真正单一存储模型

## 4. 当前存储有哪些合理点

虽然整体偏乱，但不是全错。

### 4.1 永久栏目正文直接以 Chrome 书签库为真相源

这个方向是对的。

优点：

- 不需要插件自己维护永久正文的主副本一致性
- 永久栏目天然跟随浏览器书签变化
- 导出和同步时可以直接重新拿完整树

### 4.2 临时栏目、空白栏目、连线作为同一个画布文档

这个概念也对。

因为从用户视角看，它们本来就是一个完整画布状态，而不是三个互不相关的子系统。

### 4.3 IndexedDB 只做大对象兜底

这个方向本身没问题。

问题不在于“用了 IndexedDB”，而在于当前谁是主路径、谁是兜底、谁是镜像，没有被彻底规范。

---

## 5. 当前为什么说它不够合理

### 5.1 `localStorage` 承担了过多职责

当前 `localStorage` 不只是小设置：

- 画布主状态
- 永久副本壳数据
- 永久栏目说明
- 视图分区状态
- 启动视图状态
- 主题 bootstrap
- 搜索偏好
- 同步恢复记录 / 恢复锁的本地镜像
- 某些跨页面同步信号

这就导致：

- 主数据和轻量 UI 偏好混在一起
- 正式持久化和兼容 / signal 混在一起
- 难判断哪些 key 是“真相源”，哪些 key 只是“镜像”

### 5.2 画布主状态是整包重写

临时栏目、空白栏目、连线被放在同一个对象里，这个概念对。

但当前保存方式通常是整包序列化后重写：

- 一点点改动
- 也要把 `sections + mdNodes + edges` 一起重新写入

这会带来：

- `JSON.stringify` 成本
- 写放大
- 高频操作时主线程压力更大

所以真正的性能瓶颈，不只是存在哪个桶里，而是“写入粒度过粗”。

### 5.3 永久栏目副本壳状态过于分散

永久栏目副本相关状态现在分散在多个 key：

- 副本列表
- 位置尺寸
- 说明
- 字号
- 滚动状态
- 折叠状态

逻辑上它们都属于“永久副本视图壳”，但当前没有形成统一的数据对象。

这会导致：

- 导出、同步、导入都要自己重新拼
- 读取和维护成本高
- 容易漏字段

### 5.4 同步层仍然被旧主路径绑定

当前同步恢复、快照应用时，仍然直接回写若干 `localStorage` key。

这说明同步层目前默认认为：

- `localStorage` 还是主落点之一

也意味着如果以后要重构主存储，不能只改 UI 层，必须同步改同步链路。

### 5.5 导出结构和运行时结构不统一

当前内部运行时、导出、同步三者不是完全同构：

- 运行时有自己的对象结构
- 导出时会重新组装
- 同步时又会做协议层处理

这不是不能接受，但会导致：

- 解析器压力更大
- 后期维护更复杂
- 用户感觉“导出长这样，为什么内部不是这样”

---

## 6. 当前性能没有做到极致，问题到底在哪

不是简单一句“用了 localStorage 所以慢”。

真正的性能问题更可能来自下面几个叠加：

- 主线程同步写 `localStorage`
- 大对象整包 `JSON.stringify`
- 写入后触发一整套 UI / DOM / 状态联动
- 永久栏目 DOM 和副本 DOM 之间存在额外同步成本
- 大量栏目 / 大量书签时仍然有整树重建或大范围刷新

所以：

- 仅仅把当前结构搬到 `chrome.storage.local`，不会自动变成极致性能
- 只改存储桶，不改数据边界和写入粒度，收益有限

---

## 7. 我对当前方案的总体评价

### 7.1 能不能继续用

能。

### 7.2 合不合理

部分合理，但整体不够收敛。

### 7.3 是否很乱

是，确实偏乱。

### 7.4 是否应该立刻全量重构

不建议。

因为现在牵连面太大：

- 导入
- 导出
- 同步
- 搜索
- 目录面板
- 永久副本
- 视图态
- 恢复态

如果直接全搬，很容易把已有平衡打乱。

### 7.5 是否应该开始做结构收口

应该。

但要分阶段。

---

## 8. 更合理的目标架构

我认为更合理的目标是：

### 8.1 永久栏目正文

- 真相源继续保持为 Chrome 书签 API
- 插件内部只保留“规范化后的永久树快照缓存”
- 主永久栏和所有副本都读取同一个内容源

### 8.2 永久栏目副本

- 不再散落成很多独立 key 的临时组合
- 统一成“副本视图壳对象”
- 每个副本只保存：
  - `viewId`
  - `sourceId`
  - `descriptionMd`
  - `scrollState`
  - `foldState`
  - `cardState`

### 8.3 临时栏目 + 空白栏目 + 连线

- 继续作为同一个画布文档
- 但正式主存储应逐步收口到 `chrome.storage.local`
- `localStorage` 最多保留 marker / bootstrap / signal
- `IndexedDB` 只做超大对象或恢复兜底

### 8.4 localStorage 的职责

只保留：

- 启动瞬间就要同步读取的小型 UI 状态
- 必要的镜像
- 必要的同步 signal
- 极轻量的 fallback

不要再继续让 `localStorage` 扛正式大对象主状态。

### 8.5 IndexedDB 的职责

只保留：

- 恢复包
- staging bundle
- 超大缓存
- 极端情况下的主状态兜底

而不是把大量零碎正式配置继续往里丢。

---

## 9. 现阶段最合适的推进方式

不建议一口气做“所有存储统一大重构”。

更适合的顺序是：

### 阶段 1：先把边界写清楚

先统一认知：

- 哪些是真相源
- 哪些是正式主存储
- 哪些只是镜像
- 哪些只是 signal
- 哪些只是导出时拼装层

### 阶段 2：先打磨解析器 / 同步链路

因为当前你们最频繁在动的是：

- 导入
- 导出
- 同步

这时候最不适合一边大改主存储，一边再改协议层。

### 阶段 3：再收口主状态

优先级建议：

1. 临时栏目 + 空白栏目 + 连线的正式主存储
2. 永久副本视图壳对象
3. 恢复态 / 快照态 / staging
4. 最后再慢慢减少 `localStorage` 的遗留 key

---

## 10. 当前最重要的判断

### 10.1 现在的存储合理吗

不算完全合理。

### 10.2 现在的存储能不能继续支撑开发

能，但维护成本会越来越高。

### 10.3 现在最需要做什么

不是立刻大迁移，而是先把下面三件事定死：

- 数据域边界
- 真相源边界
- 导入 / 导出 / 同步的协议层边界

### 10.4 现在最不该做什么

最不该做的是：

- 还没把边界说清楚，就直接全面搬存储

因为那样很容易把已有功能打散。

---

## 11. 当前可作为后续计划的核心原则

后续如果要继续重构，我建议始终遵守下面几条：

- 规则 1：先定义真相源，再定义持久化层
- 规则 2：正式主状态尽量只有一个主路径
- 规则 3：`localStorage` 只做轻量、启动快读、signal、fallback
- 规则 4：`IndexedDB` 只做大对象、恢复包、staging、缓存
- 规则 5：导出结构可以比运行时结构更完整，但不要反过来主导运行时存储
- 规则 6：不要在同步、导入、导出、搜索、目录各自偷偷维护一套不同理解的数据模型

---

## 12. 一句话收尾

当前的问题，不是“Chrome 为什么给三种存储”，而是“我们还没有把这三种存储的职责收口清楚”。

后续最值得做的，不是盲目搬家，而是先把：

- 永久栏目
- 永久副本
- 临时栏目
- 空白栏目
- 连线
- 导入 / 导出 / 同步

这些东西到底谁是真相源、谁是正式主存储、谁只是镜像，彻底讲清楚。

讲清楚以后，再动刀，风险才可控。
