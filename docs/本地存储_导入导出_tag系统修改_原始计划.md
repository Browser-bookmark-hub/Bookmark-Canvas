## 0、补充执行口径：BCS 文档层与插件 UI 状态边界

当前不做 `settings.json` 导入/导出，也不做“完整插件工作区备份”。因此本轮不需要做三层物理迁移，只需要守住导入、导出、备份、推送、拉取的 BCS 文档边界。

核心原则：
- BCS 存储的首要目标是服务 Obsidian JsonCanvas 对齐，以及导入、导出、备份、拉取、推送。
- `bcs:canvas`、`bcs:section:*`、`bcs:perm:*`、`bcs:meta`、`bcs:signal` 是当前文档/同步主链路。
- `bcs:canvas` 不是直接导出运行时对象，而是由 builder 转换成 Obsidian JsonCanvas 形态；`pinned`、`colorLocked`、Markdown 字号、放大比例、窗口状态、性能设置等不应进入 `bcs:canvas`。
- 导出、备份、推送、拉取准备流程应先 flush 运行时状态到 BCS，再从 BCS 构建 export sandbox。懒加载/休眠只影响 DOM 或渲染树，不卸载 `CanvasState` 的核心数据。
- 插件 UI/偏好状态继续保存在独立本地 key 中，例如 `canvas-node-ui-state-v1`、`canvas-appearance-settings-v1`、`canvas-other-settings-v1`、`canvas-node-layout-zoom-v1`、性能设置、快捷键、滚动/展开状态等；这些默认不进入导出包或备份内容本体。
- `bcs:backup:slot`、`bcs:auto-backup:settings:v1`、`canvas-import-threshold-v1`、`bcs:legacy-temp-migrated-v1` 属于流程状态，不是 Obsidian JsonCanvas 文档内容。当前可保留命名，不做迁移。
- `bcs:section:*` 是本插件的临时栏目 JSON 协议，可以保存恢复临时栏目内容所需的最小 `sectionMeta`，但新增字段必须判断是否服务导入、导出、备份、推送、拉取；纯 UI 偏好应放独立本地 key。

临时栏目分片后的写入边界：
- 临时栏目内容编辑：只写受影响的 `bcs:section:<sectionId>`。
- 临时栏目创建/删除：整体写 `bcs:canvas` 清单，同时只 upsert/remove 受影响的 `bcs:section:*`，不重写无关 section。
- 画布布局、Markdown 节点、连接线：写 `bcs:canvas` 清单，不重写所有 `bcs:section:*`。
- 清空、覆盖恢复、迁移兜底等全局语义操作允许全量重建 BCS 文档。

未来只有在明确实现 `settings.json`、完整工作区备份、跨设备同步插件偏好或正式稳定 storage 协议时，才需要把“文档数据、流程状态、插件 UI/偏好状态”做物理分层迁移。

1.2.2、sectionId 强绑定关联点（必须一并改）

1、DOM 与定位
- 临时栏目 DOM 壳体 `id=section.id`，并写入 `data-section-id`；目录定位、批量面板锚点、右键菜单等均按 sectionId 定位。

2、树节点与拖拽
- 临时树节点 `data-section-id`、`data-node-id`、`data-tree-type=temporary` 参与拖拽/放置/懒加载。
- 拖拽跨栏目移动使用 `moveWithin/moveAcross(sectionId, ...)`；sectionId 变更会直接影响目标路由。

3、临时栏目 item 主键体系
- item.id 当前是 `temp-${sectionId}-${counter}`，item.sectionId 也与 sectionId 强绑定。
- 跨栏目移动会重建 item.id 并重写 item.sectionId，因此新 ID 规则必须覆盖这些路径。

4、展开/折叠状态
- 折叠键有 `temp-section-collapsed:${sectionId}`。
- 树内 folder 展开态使用 `${sectionId}-${itemId}` 复合键（展开/折叠集合 + 持久化状态）。

5、滚动状态
- 临时栏目滚动位置键是 `temp-section-scroll:${sectionId}`，sectionId 变化会导致历史滚动键失效。

6、连接线（edge）
- 连接线 `fromNode/toNode` 直接引用栏目 id；sectionId 改造时要同步处理 edge 引用。

7、导入包组框归属
- 导入容器 `containedTempIds` 保存的是临时栏目 id；sectionId 规则变化必须同步。

8、目录栏 locate 规则
- 目录有 `id.startsWith('temp-section-')` 的判断；若未来去掉该前缀，需要同步改目录识别逻辑。

9、计数器/解析正则
- 现有计数恢复存在对旧 ID 形态的正则匹配（如 `temp-section-(\d+)`、`temp-[^-]+-(\d+)`），ID 改造后需统一更新。

			- 本地值一致：说明是同一个书签/文件夹，检查标题、URL、父级、顺序，进行本地的 Chrome API 移动、修改操作（mapping 不新增、不删除；syncId 不变；id 保持为当前本地 chromeId；若导入包映射表有 color/tags/text，则按 syncId 覆盖这些扩展字段）
			- 本地没有这个值：说明导入包新增，本地要创建（Chrome API 创建成功后，拿返回的新 chromeId，新增 mapping 项：{ id: newChromeId, syncId: 导入包节点 id }；若导入包映射表有 color/tags/text，一并写入）、（bcs/dom 也进入bulk增量，参考2.2.1.4、2.2.1.5）
			- 本地多出来的值：说明导入包没有，本地要删除，也有 removeTree 等对于文件夹的操作（Chrome API 删除成功后，删除该 syncId 对应的 mapping 项（即最小单元「参考「一、的1.1、」」）；如果是文件夹删除，连同其子节点对应的 mapping 项一起删除）、（bcs/dom 也进入bulk增量，参考2.2.1.4、2.2.1.5）


2.2.1.4、特别注意1：导入阶段 syncId 来源规则
导入过程中，永久栏目的 syncId 只以「导入包快照树」里的 id 为准。
无论是「覆盖更新」还是「增量更新」，导入阶段都禁止为永久栏目节点重新生成新的 syncId：
- 覆盖更新：清空并重建 Chrome 书签树后，用「导入包快照树 id(syncId) -> Chrome API 返回 id(chromeId)」重建本地映射表。
- 增量更新：本地已有节点沿用其 mapping 中的 syncId；导入包新增节点使用「云端快照树」里的 id 作为 syncId，Chrome API 创建成功后只补 chromeId；本地多余节点删除 mapping。
- 云端映射表中的 tags 等扩展字段，按 syncId 覆盖/补入本地映射表。
导入流程结束并完成映射表校验后，才恢复普通本地操作规则。普通本地新增节点时，再由本地生成新的 syncId。


2.2.1.5、特别注意2：bulk mute 与刷新/校准规则

为了防止导入应用过程中 Chrome bookmark events 触发 DOM/BCS 快照或映射表的逐条增量更新，必须保留当前代码的 bulk mute 机制。
- 覆盖更新：必须整体包在 bulk mute 中。期间清空、重建 Chrome 书签树，并在 create 返回时记录 syncId -> chromeId；不要让 onCreated/onRemoved 逐条改 BCS/DOM/mapping。覆盖完成后，再统一拉取 Chrome 树做校验、刷新，并写回本地 BCS 快照与映射表。
- 增量更新：建议也在一次导入事务/bulk mute 中执行本轮 move/update/create/remove。期间由同步流程自己维护 mapping 增量变化，不依赖 onCreated/onRemoved/onMoved 事件去反写 mapping。增量操作完成后，再统一拉取 Chrome 树做校验、刷新，并确认 BCS 快照与 mapping 一致。
bulk mute 只静默事件监听器的逐条副作用，不影响 Chrome API 调用本身的返回值；因此 create 返回的新 chromeId 仍可用于更新或重建映射表。

## 4、单文件 JSON/HTML 导入自兼容补齐；

本节放在「3、加 颜色 / 标识 /tag系统」之后执行。

目标：
- 单文件 JSON/HTML 永远作为增量素材导入为临时栏目，不参与永久覆盖，不直接改浏览器真实永久书签树，不改永久栏目 identityMap。
- JSON 导入必须兼容 Chrome Bookmark API 树状结构，例如 `chrome.bookmarks.getTree()` 的数组根、单 root 对象、普通 `{ title, url, children }` 书签树。
- JSON 导入必须兼容本插件导出包中的永久栏目 `.json` 与临时栏目 `.json` 单文件；即使脱离 `.canvas` 包导入，也应能被识别为一个临时栏目。
- 第三步 tag 系统完成后，单文件 JSON 导入需透传节点级 `tags` / `color` / `text` 等扩展字段；若导入为新临时栏目，不与本地已有节点做冲突合并，以导入文件自身字段为准。

永久栏目 JSON 单文件导入：
- 识别 `sectionType: "permanent"` 且存在 `tree` 的结构。
- 读取 `tree.children` 作为书签树内容，导入为一个「快照临时栏目」。
- 保留 `title`、`descriptionMd`、`slot`、`fileRole` 等可展示元信息；`identityMap` 只作为 tags 等扩展字段来源参考，不把其中的 Chrome ID 写入本地永久映射表。
- 如果是永久副本 anchor 文件（例如只有 `inheritFrom`，没有 `tree`），单文件导入时不得静默失败；可提示需要主永久 JSON 文件，或只导入说明为空栏目（执行时再定）。

临时栏目 JSON 单文件导入：
- 识别 `sectionType: "temporary"` / `sectionMeta` / `items` 的结构。
- 读取 `items` 作为临时书签树，导入为一个新临时栏目。
- 保留 `sectionMeta`、`title`、`descriptionMd`、`label`、`sequenceNumber`、颜色与 tag 扩展字段。
- 导入时重新分配本地临时栏目 ID 与 item ID，避免和现有临时栏目冲突。

最低兼容：
- 单文件 JSON 若只有最基础书签树结构，也必须能导入。
- 标题为空时使用 URL 或默认标题兜底；文件夹标题为空时使用默认文件夹名。
- 空 children 合法，不能因为空数组直接判定整个 JSON 无效。
- 无法识别为书签树时才报错，并给出明确提示。
