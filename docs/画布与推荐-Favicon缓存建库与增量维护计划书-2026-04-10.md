# 画布与推荐 Favicon 缓存建库与增量维护计划书（2026-04-10）

## 1. 目标
本计划只覆盖两个项目：
1. `Bookmark-Canvas`（书签画布）
2. `Bookmark-Record-Recommend`（书签推荐）

核心目标：
1. 初装后尽快建立可复用的 favicon 缓存库。
2. 后续只做增量维护，避免反复全量请求。
3. 保留现有渲染懒加载策略，优先优化数据层，不做大范围 UI/DOM 机制改造。

## 2. 当前现状（结论）
1. 两个项目都已存在 `FaviconCache`（内存 + IndexedDB），不是“每次都重新拉取”。
2. 当前整体偏“谁渲染谁触发拉取”，首次安装时缓存库不完整，体感会有“慢慢补图”。
3. 画布中永久栏目、临时栏目、搜索等入口大体共用同一缓存逻辑，属于“共享缓存，不是每个卡片一份”。
4. 推荐项目还有“推荐卡片快照层”，会出现“先占位再补图”的视觉过程。

## 3. 基本原则
1. 一库多用：图标数据按 `URL/域名` 去重存储，只存一份，多个卡片复用。
2. 视觉优先：首屏先显示可用缓存，缺失图标后台补，不阻塞页面可操作性。
3. 增量优先：新增/删除/改 URL 才触发对应图标任务，移动/改标题不触发图标重拉。
4. 防降级：低清图不覆盖高清图；16x16 仅允许“填空”，不允许覆盖已有高质量图标。
5. 渲染懒加载保留：本轮不重做 DOM 懒渲染，只优化“图标从哪里来、如何维护”。

## 4. 方案总览
建立“初装建库 + 空闲补齐 + 增量维护”三段式流程：
1. 初装建库：先建 URL/域名任务索引，不做全量阻塞拉图。
2. 空闲补齐：首屏可见节点高优先，非可见节点走空闲队列慢慢补。
3. 增量维护：书签事件只处理变更项，持续维护缓存库完整度。

## 4.1 落地方式修订（按当前代码现状）
本计划不做“一次性重构”，改为分片落地：
1. 先做低风险“旁路增强”，不替换现有主读取链路。
2. 再做增量闭环（创建/修改/删除）中缺失的细节。
3. 最后再评估是否上移到 background 常驻。

原因：
1. `Canvas` 当前缓存主键以 `domain` 为主，直接做强清理有误伤风险。
2. `Recommend` 当前依赖 `historyCurrentCards + snapshot` 秒显，结构改动风险高。
3. 两边都已有可用链路，先“补齐短板”比“整体替换”更稳。

## 5. 画布（Bookmark-Canvas）执行计划
## 5.1 初装阶段
1. 在读取书签树后，构建一次“favicon 任务索引”（URL 去重）。
2. 先渲染永久栏目首屏，图标优先读已有缓存。
3. 对首屏可见节点立即拉取缺失图标。
4. 其余节点加入空闲补齐队列。

## 5.2 常规使用阶段
1. 永久栏目继续保持现有懒加载渲染。
2. 临时栏目按“用户打开该栏目时”再触发对应 URL 子集补图。
3. 同一 URL 在多个卡片复用同一缓存结果，不重复请求。

## 5.3 增量维护
1. `onCreated`：新 URL 入队，必要时触发网络分支重评估。
2. `onChanged(url)`：旧 URL 缓存清理，新 URL 入队。
3. `onRemoved`：移除引用并清理对应缓存项。
4. `onMoved`/仅标题改动：不触发图标重拉。
5. 批量导入：走批处理队列，避免事件风暴导致卡顿。

## 5.4 Canvas 分片顺序（最终执行口径）
1. 第一片：保持现有渲染触发链，只补 `onCreated` 轻量入队与限流。
2. 第二片：补 `onChanged` 闭环（先软失效，不做物理删库）。
3. 第三片：引入引用计数后，再落 `onRemoved` 的安全清理。
4. 第四片：把“固定 preload 50”升级为预算化空闲补齐队列。
5. 第五片：评估是否把索引/增量维护上移到 background 常驻。

## 6. 推荐（Bookmark-Record-Recommend）执行计划
## 6.1 初装阶段
1. 继续保留当前“卡片快照秒显”。
2. 在 `allBookmarks` 可用后，后台构建全量 URL 任务索引。
3. 推荐卡片（当前 3 张）作为最高优先级补图任务。
4. 非首屏图标空闲补齐，不阻塞推荐卡片交互。

## 6.2 常规使用阶段
1. 继续使用 `historyCurrentCards + snapshot` 做快速恢复。
2. 将补到的 favicon 及时写回 `cardData/snapshot`，减少下次打开抖动。
3. 保持“打开网页回写图标”能力，用于后续提高清晰度。

## 6.3 增量维护
1. 新增/改 URL：只处理该 URL 的图标队列。
2. 删除：清理对应图标缓存与引用。
3. 与推荐轮转逻辑解耦：图标补齐不阻塞选卡、翻牌、刷新轮次。

## 6.4 Recommend 分片顺序（最终执行口径）
1. 第一片：旁路双写（在 `saveCardFaviconsToStorage`、tab 回写成功点双写，不改主读取）。
2. 第二片：miss 场景只读回填新库到内存，不替换现有 `getFaviconUrl/Fetch` 主流程。
3. 第三片：补删除/URL 变更闭环，复用现有消息链，避免事件风暴。
4. 第四片：增强 tab 回写为“可持久化 + 可即时刷新”双通道。
5. 第五片：确认稳定后，再评估是否替换旧主链路。

## 7. 本轮不做
1. 不重写现有 DOM 懒加载框架。
2. 不新增复杂 UI 配置项。
3. 不把所有图标在首次安装时“全量强制拉完后再展示”。
4. 不直接把 `domain` 级缓存主键改成 `url` 级（该项后置）。
5. 不改 `historyCurrentCards/snapshot` 核心结构（该项后置）。

## 8. 验收标准
1. 首次安装时：页面可先展示结构与占位，图标逐步补齐，但不阻塞主要操作。
2. 再次打开时：同批书签图标命中率明显提升，不应出现“每次都从零补图”体感。
3. 新增少量书签时：只补新增项，不触发大面积重拉。
4. 同一 URL 多处复用时：网络请求去重有效，图标一致。
5. 已有高清图标不会被低清来源覆盖。

## 9. 实施顺序
1. 先做 `Recommend` 第一片、第二片（低风险、收益快、验证路径短）。
2. 再做 `Canvas` 第一片、第二片（先补闭环，不碰高风险清理）。
3. 然后并行推进 `Recommend/Canvas` 第三片、第四片。
4. 最后统一评估第五片（是否替换主链路、是否上移 background）。
5. 全流程联调：首次安装、重复打开、批量新增、批量导入、侧边栏秒显。

## 10. 风险与兜底
1. 风险：初装阶段任务过多导致后台持续占用。
2. 兜底：限制并发、分批次、空闲调度、可中断恢复。
3. 风险：旧缓存质量参差不齐。
4. 兜底：保留质量守门，不让低质量回写覆盖高质量结果。
