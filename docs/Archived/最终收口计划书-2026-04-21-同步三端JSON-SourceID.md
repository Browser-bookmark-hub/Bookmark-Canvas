# 最终收口计划书（2026-04-21）

## 1. 目标与统一口径

1. 永久栏目分两种状态。
同步应用态：云端拉取后先替换永久栏目协议数据与副本说明，再执行增量/覆盖落地浏览器书签树。
日常编辑态：同步完成并重建基线后，恢复到日常 API + Chrome ID 的增删改移动交互。

2. Chrome ID 的位置固定。
云端协议不依赖 Chrome ID。
Chrome ID 只在本地运行时通过 Chrome API 复用/生成。

3. 三端 JSON 收敛到同协议语义。
本地、云端、手动导出使用同一协议对象语义。
拉取/手动导入采用整块替换。
推送采用当前本地协议对象直接上云。
替换后只做两件事：重建运行态、重建基线。

4. Source ID 与 Chrome ID 分离。
Source ID 只表示来源谱系，不替代运行时节点 ID。

## 4. 差距清单（必须补齐）

1. 流程顺序差距。
目标要求“先替换协议 JSON，再永久树落地”，当前代码是“永久树先落地，再文件替换”。

2. 三端顶层包差距。
协议语义虽逐步统一，但本地分片、云端 snapshot 包、手动 full-backup 包仍并存，未形成单一顶层契约。

3. 对照日志差距。
当前对照日志仍在主流程中持续记录，增加复杂度且容易引发误解。

4. Source ID 策略差距。
Source ID 已进入主路径，但“启用方式、阻断策略、迁移策略、脚本口径”未统一。
