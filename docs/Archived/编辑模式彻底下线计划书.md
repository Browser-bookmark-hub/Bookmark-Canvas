# Bookmark-Canvas 编辑模式彻底下线计划书

> 返回文档索引：[docs/README.md](./README.md)

> 本文只讨论一件事：如何把 Obsidian 导出格式里的 `editable / 编辑模式` 安全下线。  
> 本文不讨论 JSON 结构模式怎么设计；那是下一份计划书的范围。

## 1. 这份计划书要解决什么问题

当前项目里“编辑模式”这个词有两层含义，必须先拆开：

1. **需要下线的编辑模式**
- 指 Obsidian 导出格式里的 `editable`
- 也就是“标题树 + H6 后列表”的那套 Markdown 协议

2. **不能误删的编辑态**
- 画布内部的富文本编辑
- 空白栏目 `contenteditable`
- 标题重命名
- 临时栏目/空白栏目正常编辑行为
- 各种“进入编辑态 / 退出编辑态”的交互代码

这份计划书的目标，就是只删第 1 类，不碰第 2 类。

---

## 2. 删除边界

### 2.1 本次必须删除的范围

- 导出格式枚举里的 `editable`
- 手动导出弹窗里的“编辑模式”选项
- 同步设置里的“编辑模式”选项
- 与 `editable` 导出分支绑定的默认值、保存值、文案说明
- `BC_EDITABLE_RULE` 注释块及其写出逻辑
- `__buildPermanentBookmarksMarkdownEditable(...)`
- `__buildTempSectionMarkdownEditable(...)`
- 所有“如果 exportFormat === editable 就走旧 Markdown 树导出”的分支

### 2.2 本次不能误删的范围

- `visual`
- `visual-no-icon`
- 全量备份 JSON
- `.canvas` 导出与导入
- 空白栏目 Markdown 导出
- Obsidian 原生 text 镜像
- 画布内部真实编辑能力
- 所有 `contenteditable`、WYSIWYG、富文本工具栏、标题编辑、双击编辑等逻辑

### 2.3 为什么要单独写这个边界

因为代码里很多地方出现“编辑模式”字样，但并不等于“Obsidian 导出格式 editable”。

如果不先立边界，后面很容易把这些也误删掉：

- 空白栏目编辑
- 富文本编辑器
- 编辑态下禁拖拽
- 标题输入与焦点逻辑

这些都必须保留。

---

## 3. 删除对象清单

### 3.1 用户可见层

必须下线：

- 同步二级 UI 的导出格式选项
- 手动导出弹窗里的导出格式单选项
- 所有“编辑模式更适合 AI / diff / 编辑”的说明文字
- 所有“默认导出格式是编辑模式”的文案

必须保留：

- 视觉模式
- 视觉模式（无图标）

### 3.2 设置与默认值层

必须删除或迁移：

- `obsidianExportFormat: 'editable'`
- `OBSIDIAN_EXPORT_FORMATS` 里的 `editable`
- `normalizeObsidianExportFormat(...)` 对 `editable` 的新写入支持

必须增加或改成：

- 默认值不再是 `editable`
- 老设置若仍保存 `editable`，加载时要先迁移，而不是继续原样写回

### 3.3 导出实现层

必须删除：

- 永久栏目 editable 导出构建器
- 临时栏目 editable 导出构建器
- `BC_EDITABLE_RULE` 注释块生成
- `exportFormat === 'editable'` 的正文分支

必须保留：

- `visual`
- `visual-no-icon`
- 全量备份导出

### 3.4 导入与同步兼容层

这里不能一刀切，必须分阶段。

先保留：

- 旧 `editable` 文件的兼容读取能力
- 旧 `BC_EDITABLE_RULE` 的容错提取
- 旧 Markdown 树解析器

暂不保留到最后：

- 旧 editable 作为“新导出目标值”
- 旧 editable 作为“UI 可选项”

也就是说：

- **先删写出**
- **再保留一段时间读取兼容**
- 最后再决定要不要把旧解析器物理删除

---

## 4. 推荐删除顺序

### 第 1 阶段：先删用户入口

- UI 里删掉 `editable`
- 默认值不再指向 `editable`
- 文案不再提 `editable`
- 新保存设置不再写入 `editable`

这一阶段的目标是：

- 用户再也选不到它
- 系统再也不会新生成它

### 第 2 阶段：删导出实现

- 删除永久栏目 editable 构建器
- 删除临时栏目 editable 构建器
- 删除 `BC_EDITABLE_RULE` 写出逻辑
- 删除所有 editable 导出分支

这一阶段的目标是：

- 代码里彻底不再生成旧协议

### 第 3 阶段：保留兼容读取

- 旧文件导入先继续支持
- 同步拉取若碰到旧 editable 文件，先仍能读

这一阶段的目标是：

- 不把历史数据立刻判死

### 第 4 阶段：最后决定是否物理删解析器

只有在确认下面条件后，才删：

- 用户不再需要导入历史 editable 文件
- 云端仓库里已没有 editable 遗留文件
- 替代协议已经完全稳定

在此之前，不建议删：

- `__parseEditableMarkdownToTree(...)`
- `BC_EDITABLE_RULE` 读取容错
- 旧 Markdown 树识别逻辑

---

## 5. 验收标准

### 5.1 删除后必须成立

- UI 中再也看不到 `editable / 编辑模式`
- 新建导出不会再产生 editable 文件
- 新保存设置不会再写入 `editable`
- 视觉模式和视觉模式（无图标）不受影响
- 画布内部编辑能力不受影响

### 5.2 删除后不能发生

- 删除了空白栏目编辑能力
- 删除了富文本编辑器
- 删除了标题编辑
- 删除了视觉模式
- 删除了 `visual-no-icon`
- 删除了全量备份 JSON

---

## 6. 与下一份 JSON 计划书的关系

文档顺序上，必须先有这份“删除计划书”，再有“JSON 结构模式计划书”。

原因：

- 先明确“删谁，不删谁”
- 再讨论“新模式怎么接上来”

但代码落地时，允许采用下面这个更稳的顺序：

1. 先把 JSON 结构模式分支补齐
2. 再切默认值和 UI
3. 再删除旧 editable 导出实现
4. 最后再处理旧解析器兼容

也就是说：

- **文档顺序：先删旧，再谈新**
- **实现顺序：可以先铺新，再删旧**

---

## 7. 最终定性

这份计划书的结论不是“以后少用 editable”，而是：

- 对用户：直接下线
- 对新导出：彻底停止
- 对老数据：短期兼容读取
- 对无关编辑能力：完全不碰

后续 JSON 结构模式计划书，必须建立在这份删除边界之上。
