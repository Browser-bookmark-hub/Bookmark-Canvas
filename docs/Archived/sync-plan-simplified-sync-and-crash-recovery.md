# Bookmark-Canvas 简化同步与崩溃恢复规划书

> 返回文档索引：[docs/README.md](./README.md)

## 1. 这份规划书解决什么问题

这份文档用于锁定当前同步方向，避免项目继续在以下两条路线之间摇摆：

- 路线 A：把 Bookmark-Canvas 做成一个“类 Obsidian Git / 类 Git 客户端”的同步器
- 路线 B：把 Bookmark-Canvas 做成一个“远端存储驱动的状态同步器”

当前结论：

- **不把 Chrome 插件继续往 Git 客户端方向推进**。
- **同步模型优先参考 Remotely Save，而不是 Obsidian Git**。
- **GitHub 在本项目中主要扮演远端存储角色，而不是完整 Git 运行时**。
- **崩溃恢复先做最小可行方案，不做重型 checkpoint / WAL / Git 级事务系统**。

---

## 2. 当前方向（已锁定）

### 2.1 架构定位

Bookmark-Canvas 当前更适合被定义为：

- 浏览器扩展中的书签 / 画布状态同步器
- 远端后端当前仅支持 GitHub
- 不依赖本地 Git 仓库、Git CLI、index、HEAD、rebase、stash 等 Git 语义

### 2.2 参考项目取向

#### 更接近的参考：Remotely Save

参考点：

- 本地维护同步元数据
- 以“上次同步基线 + 当前本地 + 当前远端”产出 sync plan
- 冲突策略有限，不追求通用 merge
- 适合“没有本地 Git 运行时”的环境

#### 不作为主方向的参考：Obsidian Git

原因：

- 它的核心是 Git 语义（merge / rebase / reset / pull / push）
- 桌面端依赖 `simple-git`，移动端退化为 `isomorphic-git`
- 它适合 Vault + Git 仓库，不适合 Chrome 扩展的浏览器状态同步

## 3. V1 同步模型（先做减法）

V1 不追求“智能通用双向合并”，只保留三类明确动作：

### 3.1 Push

语义：**本地导出包覆盖远端**

流程：

1. 从当前 Bookmark-Canvas 状态生成本地导出包
2. 比较本地摘要与远端摘要
3. 将导出包上传到 GitHub
4. 上传成功后更新本地同步元数据

中断策略：

- 若中断在“导出包生成前 / 生成中”：下次重新导出
- 若中断在“上传中”：下次重新上传
- 若中断在“上传完成但本地状态未更新”：下次重新比对远端，再决定是否补记成功或重传

V1 目标：

- **不做上传断点续传**
- **允许下次整轮重传**
- **要求重传过程幂等 / 可收敛**

### 3.2 Pull

语义：**远端下载包覆盖本地**

流程：

1. 从 GitHub 下载当前远端导出包
2. 校验包是否完整可解析
3. 用远端包整包覆盖本地
4. 覆盖成功后更新本地同步元数据

中断策略：

- 若中断在“下载前 / 下载中”：下次重新拉取
- 若中断在“下载完成但尚未开始本地覆盖”：下次重新拉取或重新应用暂存包
- 若中断在“本地覆盖中”：下次**重新执行整包覆盖**，不做中间接续

V1 目标：

- **不做本地覆盖断点续写**
- **要求覆盖操作重复执行后仍收敛到同一个远端目标态**
- **优先保证“重做一遍能拉齐”，而不是“从 43% 继续”**

### 3.3 双方都变

语义：**默认不自动 merge**

处理原则：

- 不做 Git merge
- 不做通用 diff3 合并
- 不把复杂冲突放到云端服务端去做

V1 默认动作：

- `Use Local`
- `Use Cloud`

也就是说：

- 用户选择 `Use Local`：本地覆盖远端
- 用户选择 `Use Cloud`：远端覆盖本地

后续若要扩展“有限自动合并”，也仅限非常明确、低风险的对象类型；V1 不纳入范围。

## 4. 浏览器突然崩溃时的最小恢复方案

## 4.1 不做的事情

V1 明确不做：

- 不做 Git 级 checkpoint
- 不做 WAL / rollback journal 全系统实现
- 不做上传断点续传
- 不做本地覆盖断点续写
- 不做服务端 merge

## 4.2 要做的事情

V1 仅做一套**轻量恢复标记 + 强制恢复锁**。

核心原则：

- 不做通用断点续传
- 不从“半写状态”继续推演下一步
- 一旦进入恢复锁，用户必须先完成上次动作
- 在恢复完成前，普通同步按钮和三个面板按钮全部锁住

### 4.2.1 强制恢复面板

只要检测到上次同步已经进入执行阶段但未完成，就优先显示**强制恢复面板**，其优先级高于：

- 首次同步面板
- 云端不一致面板
- 冲突面板
- 主同步按钮（立即同步 / 仅上传 / 仅拉取）

面板规则：

- 不提供关闭按钮
- 不提供删除 / 取消恢复按钮
- 不提供切换方向按钮
- 只提供一个主按钮：`继续上次操作`

含义：

- 上次如果是 `Use Cloud / Pull`，这次只能继续 `Use Cloud / Pull`
- 上次如果是 `Use Local / Push`，这次只能继续 `Use Local / Push`
- 恢复完成前，不允许用户误点相反方向

### 4.2.2 Push 侧

记录：

- 当前同步模式（push / full / use-local）
- 当前触发原因
- `baseRemoteSha`（开始上传前的远端基线）
- `targetPackageHash`（这次目标包的最终摘要）
- `stagedLocalManifest`
- `stagedLocalBundle`（冻结的本地包，建议落 IndexedDB）
- 当前运行阶段（prepared / uploading / verifying）

恢复规则：

- 崩溃后先校验远端当前状态
- 若远端当前摘要已经等于 `targetPackageHash`：说明上次其实已经完整成功，只需清锁
- 若远端当前摘要不等于 `targetPackageHash`，且远端仍然基于 `baseRemoteSha`：继续用 `stagedLocalBundle` 重放上传
- 若远端当前摘要不等于 `targetPackageHash`，且远端已经脱离 `baseRemoteSha`：说明别的端/别的操作改过远端，转入冲突或待处理状态

注意：

- Push 恢复时不重新从“当前本地页面状态”导出
- 必须继续使用**当次点击按钮时冻结下来的本地包**

### 4.2.3 Pull 侧

记录：

- 当前同步模式（pull / full / use-cloud）
- 当前触发原因
- `targetRemoteSha`（当次采用的远端版本）
- `targetPackageHash`（这次远端包的最终摘要）
- `stagedRemoteManifest`
- `stagedRemoteBundle`（冻结的远端包，建议落 IndexedDB）
- 当前运行阶段（downloaded / applying-local / applying-permanent / finishing）

恢复规则：

- 若还没进入本地覆盖：下次直接重新拉取或重新应用 `stagedRemoteBundle`
- 若已经进入本地覆盖：下次直接重新执行**整包覆盖**
- Pull 恢复时不允许切换成 `Use Local`
- 恢复过程不做增量 merge，不依赖半写本地状态

注意：

- Pull 恢复时不重新读取“当前本地状态”来决定动作
- 必须继续使用**当次点击按钮时冻结下来的远端包**

### 4.2.4 冲突侧

记录：

- 当前是否存在待处理冲突
- 冲突来源（主同步 / 首次同步 / mismatch）
- 用户上次点下去的方向（use-local / use-cloud）
- 若已进入执行阶段，对应的 `stagedLocalBundle` 或 `stagedRemoteBundle`

恢复规则：

- 单纯“待处理冲突未决”时：下次打开继续显示冲突状态
- 一旦用户已经点下去并进入执行阶段：转入**强制恢复面板**
- 不允许在恢复完成前切换到相反方向

### 4.2.5 什么叫“冻结的包”

这里的“冻结”不是指“最新的数据”，而是指：

- **用户点击那个按钮当下，系统准备用来执行这次操作的那份完整数据副本**

举例：

- 用户点 `Use Cloud` 时，系统从云端下载到的那份完整远端内容，就是 `stagedRemoteBundle`
- 用户点 `Use Local` 时，系统当时从本地导出的那份完整内容，就是 `stagedLocalBundle`

为什么要冻结：

- 如果崩溃后改用“当前最新本地 / 当前最新远端”重新计算，就不再是“继续上次操作”，而是开启了一轮新操作
- V1 恢复锁要求恢复时**重放上次那份确定输入**，而不是拿新的输入重新决策

### 4.2.6 什么叫“目标包”

目标包指的是：

- 这次操作最终想让本地或远端达到的**完整受管文件集合**

建议做法：

1. 对当次包生成一份规范化 `manifest`
2. `manifest` 至少包含：
   - 所有受管文件路径（排序后）
   - 每个文件的内容 hash
   - 删除清单（排序后）
3. 对这份 `manifest` 再计算一次 hash，得到 `targetPackageHash`

含义：

- `targetPackageHash` 不是某个模糊概念
- 它就是“这次操作最终应达到的目标文件状态摘要”

### 4.2.7 为什么 Push 中断后通常不会产生“半个 commit”

当前主上传路径使用的是 GitHub Git Data API 的批量提交流程：

1. 创建 blob
2. 创建 tree
3. 创建 commit
4. 最后更新 branch ref

这意味着对主分支可见状态来说，通常只有两种结果：

- 还是旧状态
- 已切换到完整新状态

通常不会出现主线上“本来想传 6 个文件，结果只挂了 2 个文件的新 commit”这种半截状态。

需要注意的例外：

- 当前实现里有少数 fallback 删除路径会单独调用删除接口
- 这种场景更可能出现的是“主体 commit 已成功，但少数旧文件还未清理完”
- 这属于“新状态 + 少量旧残留”，不是主上传树本身的半 commit

恢复口径：

- 不删除 commit
- 先校验远端当前状态是否已等于 `targetPackageHash`
- 若不相等，再继续重放或补清理

## 5. 永久栏目（浏览器真实书签树）当前策略

## 5.1 V1 默认策略

永久栏目当前优先目标是：**稳定、可恢复、可重复执行**。

因此本规划的当前口径为：

- **永久栏目先禁用增量同步**
- **永久栏目只使用覆盖恢复**

也就是：

- 云端 -> 本地：覆盖恢复本地书签树
- 冲突选择 `Use Cloud`：覆盖恢复本地书签树
- 崩溃恢复重试：再次覆盖恢复本地书签树

## 5.2 为什么这样定

原因不是“增量一定做不出来”，而是：

- 书签树是结构型对象
- 增量同步的失败面比文本型文件更复杂
- 崩溃恢复场景下，增量更难证明收敛性
- 覆盖恢复更容易满足“重复执行后结果一致”

## 5.3 后续是否还能保留增量

可以，但仅在后续满足以下条件时考虑重新打开：

1. 明确证明增量路径可重复执行且不叠加
2. 明确证明崩溃后重跑不会依赖半写中间态
3. 有单独的复杂变化回退机制

在这些条件没满足前，永久栏目以覆盖恢复为准。

---

## 6. 为什么现在不把 merge 放到云端去做

当前不建议把“双方都变”的处理迁移到云端服务端，原因如下：

1. 这会把项目从“扩展同步”升级为“扩展 + 云端同步服务”
2. 要额外处理服务部署、鉴权、数据安全、稳定性和回滚
3. 即使放到云端，也不代表就天然拥有 Git merge 能力
4. 目前本项目同步对象并不是纯文本仓库，而是书签树 + 画布状态 + 浏览器本地状态
5. 对当前 V1 目标而言，收益远小于复杂度

结论：

- V1 不做云端 merge
- V1 不做真正 Git merge
- V1 先用“选本地 / 选云端”解决双方都变的情况

## 7. 本地同步元数据（建议保留）

虽然不做重型 checkpoint，但仍建议保留一套轻量同步元数据：

- `lastRemoteSha`
- `lastLocalHash`
- `lastSuccessAt`
- `lastAppliedDirection`
- `pendingConflict`
- `pendingMismatch`
- `activeSyncMarker`
- `recoveryLock`（强制恢复锁）
- `targetPackageHash`
- `baseRemoteSha` / `targetRemoteSha`
- `stagedLocalManifest` / `stagedRemoteManifest`
- `stagedLocalBundle` / `stagedRemoteBundle`
- `prevSyncRecords`（按路径或按对象的上次成功同步信息）

用途：

- 判断是否需要 push / pull
- 判断双方都变
- 崩溃后恢复到“重新比对并重做”
- 给 UI 显示明确状态

## 8. V1 设计原则（务必遵守）

1. **宁可重做，不做复杂断点续写**
2. **宁可显式冲突，不做错误自动 merge**
3. **宁可覆盖恢复，不在永久栏目上冒进做增量**
4. **GitHub 先当远端存储，不当完整 Git 引擎**
5. **优先做可收敛的同步，而不是看起来高级的同步**

## 9. 当前阶段的最终口径

当前阶段 Bookmark-Canvas 的同步方案，可以统一表述为：

- 参考 Remotely Save 的同步思路
- 使用 GitHub 作为当前唯一远端后端
- Push / Pull 走整轮重试，不做精确断点续传
- 双方都变默认不自动 merge，只给用户 `Use Local / Use Cloud`
- 永久栏目暂时只走覆盖恢复，不走增量同步
- 浏览器崩溃恢复先做轻量标记与重做，不做重型事务系统

## 11. 二级 UI 按钮与崩溃兜底落地规则

这一节用于把“Push / Pull / Sync + 三个面板 + 自动触发”的恢复口径，直接落到当前二级 UI 的具体按钮与开关上。

目标不是让每个按钮都拥有一套不同的恢复系统，而是统一成两类：

- **Push 类动作**：本地覆盖云端
- **Pull 类动作**：云端覆盖本地

`完整同步` 只是一个组合流程：

- 先决定本轮是否需要 `Push`
- 再决定本轮是否需要 `Pull`
- 如果两者都开启，则它本质上是“按阶段执行的 Push + Pull”

因此，崩溃恢复时要恢复的是：

- **对用户：继续上次同步 / 上传 / 拉取**
- **对系统：继续上次流程里已经进入执行阶段的那个具体阶段**

### 11.1 状态页主按钮

#### 11.1.1 `立即同步`

语义：

- 用户主动发起一次“完整同步”
- 具体是否包含上传 / 拉取，取决于：
  - `完整同步时包含上传`
  - `完整同步时包含拉取`

按钮口径：

- 若两项都开启：这是 `Sync = Push + Pull`
- 若仅开启上传：它退化为 `Push`
- 若仅开启拉取：它退化为 `Pull`

崩溃恢复规则：

- 若中断发生在“同步计划计算阶段”，尚未进入具体执行：下次打开可从头重新跑本轮同步计划
- 若中断发生在 **Push 阶段**：
  - 恢复面板应显示为“检测到未完成的同步（当前阶段：本地覆盖云端）”
  - 主按钮建议文案：`继续上次同步`
  - 系统先恢复上次 `Push`
  - 若原始模式仍包含后续 `Pull`，则 **Push 完成后自动继续后续 Pull**
- 若中断发生在 **Pull 阶段**：
  - 恢复面板应显示为“检测到未完成的同步（当前阶段：云端覆盖本地）”
  - 主按钮建议文案：`继续上次同步`
  - 系统直接恢复上次 `Pull`

重点：

- 不应让用户理解成“上次同步失败后，现在只能恢复 Push、后续 Pull 没了”
- 正确含义是：**继续上次同步；当前先从中断阶段恢复起，后续阶段按原始配置自动接上**

#### 11.1.2 `仅上传`

语义：

- 本地导出包覆盖远端

崩溃恢复规则：

- 若已进入执行阶段，则进入恢复锁
- 恢复面板建议：
  - 标题：`检测到未完成的本地覆盖云端`
  - 主按钮：`继续上次上传`
- 点击后流程：
  1. 先校验远端当前状态
  2. 若远端已等于 `targetPackageHash`：当成功处理，清锁
  3. 若远端仍等于 `baseRemoteSha`：继续上传冻结的 `stagedLocalBundle`
  4. 若远端已脱离 `baseRemoteSha`：转入不一致 / 冲突处理，不再盲传
  5. 若远端当前状态无法校验：保持恢复锁，不执行上传

这里的“不执行上传”不是永久禁止，而是：

- 网络恢复后可继续
- Token 修复后可继续
- 仓库/分支/路径修复后可继续

即：**禁止的是“在远端状态未知时盲传”，不是禁止继续上传本身。**

#### 11.1.3 `仅拉取`

语义：

- 远端下载包覆盖本地

崩溃恢复规则：

- 若已进入执行阶段，则进入恢复锁
- 恢复面板建议：
  - 标题：`检测到未完成的云端覆盖本地`
  - 主按钮：`继续上次拉取`
- 点击后流程：
  1. 先看上次记录的 `targetRemoteSha`
  2. 若该版本仍可读取：**优先重新拉取该版本，再整包覆盖本地**
  3. 若暂存的 `stagedRemoteBundle` 仍在，也可直接重放该包
  4. 若 `targetRemoteSha` 已不存在或远端已变化：转入不一致 / 冲突，不自动改成别的版本

重点：

- Pull 恢复不是“从 43% 继续写”
- Pull 恢复是：**重新拿到同一目标包，然后整包再覆盖一次**

#### 11.1.4 `立即后台检查`

语义：

- 只做检查，不做覆盖写入

规则：

- 它不是恢复对象
- 关闭页面 / 崩溃后无需恢复锁
- 检查结果若形成 `pendingMismatch`，则下次打开由“不一致面板”或自动策略接管

### 11.2 三个面板按钮

#### 11.2.1 首次同步面板 -> `使用云端覆盖本地`

语义：

- 属于 Pull 类动作
- 但来源是“首次同步面板”，不是普通拉取

崩溃恢复规则：

- 进入恢复锁后，不允许切换为 `Use Local`
- 恢复面板建议：
  - 标题：`检测到未完成的首次同步`
  - 摘要：`上次首次同步已进入“云端覆盖本地”阶段，请先继续完成该阶段。`
  - 按钮：`继续上次首次同步`
- 底层执行仍按 Pull 类恢复：重新拉取 / 重放冻结远端包，再整包覆盖本地

#### 11.2.2 云端不一致面板 -> `使用云端覆盖本地`

语义：

- 这是 Pull 类动作

崩溃恢复规则：

- 一旦点下并进入执行阶段，就进入恢复锁
- 恢复面板只允许继续同一方向
- 不允许在恢复完成前切到 `保留本地并覆盖云端`

#### 11.2.3 云端不一致面板 -> `保留本地并覆盖云端`

语义：

- 这是 Push 类动作

崩溃恢复规则：

- 一旦点下并进入执行阶段，就进入恢复锁
- 恢复面板只允许继续同一方向
- 不允许在恢复完成前切到 `使用云端覆盖本地`

#### 11.2.4 冲突面板 -> `Use Cloud`

语义：

- 这是 Pull 类动作
- V1 默认不做自动 merge，只执行“云端覆盖本地”

崩溃恢复规则：

- 一旦用户点下去并进入执行阶段，恢复面板只允许继续 `Use Cloud`
- 不允许中断后重新打开又改点 `Use Local`
- 对永久栏目仍按覆盖恢复，不使用增量

#### 11.2.5 冲突面板 -> `Use Local`

语义：

- 这是 Push 类动作
- V1 默认不做自动 merge，只执行“本地覆盖云端”

崩溃恢复规则：

- 一旦用户点下去并进入执行阶段，恢复面板只允许继续 `Use Local`
- 不允许中断后重新打开又改点 `Use Cloud`

#### 11.2.6 `稍后处理`

语义：

- 只是保留 `pendingMismatch` 或 `pendingConflict`
- 不进入执行阶段

规则：

- 它不应产生恢复锁
- 下次打开时，仍然显示原面板待处理状态即可

### 11.3 自动触发类开关与定时器

这些开关本身不是“恢复对象”，但它们会触发 Push / Pull / Sync，因此崩溃口径要统一映射到对应动作。

#### 11.3.1 `自动同步`

语义：

- 定时发起 `完整同步`

恢复规则：

- 若自动同步已进入具体执行阶段并中断：
  - 若中断时已有恢复锁：下次打开优先显示恢复面板
  - 若仅记录到“本轮同步被中断”，但尚未进入具体 Push / Pull 恢复锁：可在前台重新发起同模式同步
- 页面关闭不会在后台继续执行

#### 11.3.2 `定时推送`

语义：

- 定时发起 `Push`

恢复规则：

- 一旦进入执行阶段后中断，下次打开按 `仅上传` 的恢复口径处理

#### 11.3.3 `定时拉取`

语义：

- 定时发起 `Pull`

恢复规则：

- 一旦进入执行阶段后中断，下次打开按 `仅拉取` 的恢复口径处理

#### 11.3.4 `打开页面时先拉取云端`

语义：

- 页面打开后自动发起一次 Pull

恢复规则：

- 若该次 Pull 已进入执行阶段后中断，下次打开按 Pull 类动作恢复

#### 11.3.5 `云端不一致处理策略`

建议口径：

- `自动使用云端覆盖本地` -> 视为自动触发 Pull
- `自动保留本地并覆盖云端` -> 视为自动触发 Push
- `弹窗提示` -> 不自动执行，只显示面板等待用户点按钮

因此：

- 前两者一旦已进入执行阶段并中断，下次打开也必须遵守恢复锁
- 不能因为它们是“自动触发”就绕开恢复约束

### 11.4 恢复面板的最终交互建议

为了避免用户理解错，恢复面板建议区分“对外文案”和“底层阶段”。

#### 11.4.1 对外文案

建议标题：

- `检测到未完成的同步`
- `检测到未完成的上传`
- `检测到未完成的拉取`
- `检测到未完成的首次同步`

建议按钮：

- `继续上次同步`
- `继续上次上传`
- `继续上次拉取`
- `继续上次首次同步`

不建议统一写成过于模糊的：

- `继续上次操作`

因为用户更关心的是：

- 我上次是在同步？
- 还是上传？
- 还是拉取？
- 还是首次同步？

#### 11.4.2 明细区

恢复面板明细区建议长期保留以下信息：

- 来源：同步主流程 / 首次同步面板 / 云端不一致面板 / 冲突面板
- 当前恢复阶段：Push / Pull
- 当前阶段内部状态：prepared / uploading / verifying / downloaded / applying-local
- `targetPackageHash`
- `targetRemoteSha`
- `baseRemoteSha`

这样用户就能看到：

- 这是哪来的恢复
- 现在卡在哪一阶段
- 系统恢复时依据的目标态是什么

#### 11.4.3 恢复锁的绝对优先级

这是当前阶段必须严格遵守的规则：

- **只要恢复锁已经存在，整个同步系统就进入“恢复优先”状态**
- **恢复面板是当前唯一允许继续推进的入口**
- **其他同步、检测、提示、自动化入口全部停火**

具体要求：

1. 恢复锁存在时，不允许再自动发起：
   - 自动同步
   - 定时推送
   - 定时拉取
   - 启动自动拉取
   - retry / fallback 之类的自动重试
2. 恢复锁存在时，不允许再自动弹出：
   - 云端不一致面板
   - 冲突面板
3. 恢复锁存在时，不允许再根据“当前本地状态”重新计算并偷偷重跑上传或同步
4. 恢复锁存在时，只允许：
   - 显示恢复面板
   - 用户点击 `继续上次同步 / 上传 / 拉取 / 首次同步`
   - 系统按冻结包继续上次那一轮动作

换句话说：

- **恢复锁存在 = 全局停火，只走恢复面板这一个入口**

### 11.5 当前 UI 中建议收敛或降权的旧概念

基于本规划，以下 UI 文案或选项已经偏离 V1 目标，应在后续实现中考虑降权、隐藏或重命名：

1. `合并策略（Merge / Rebase / Reset）`
   - 当前 V1 主方向不是 Git 客户端
   - 不应继续让用户把主要心智放在 Git 语义上
2. `冲突合并策略（Git 默认 / ours / theirs）`
   - V1 更适合改成：
     - 手动选择
     - 自动用本地覆盖云端
     - 自动用云端覆盖本地
3. `仅记云端版本（Reset）`
   - 它不属于当前兜底恢复的主路径
   - 若保留，建议放入高级排障，不作为主同步心智

换句话说：

- 当前二级 UI 的主心智应收敛为：
  - `同步`
  - `仅上传`
  - `仅拉取`
  - `使用云端覆盖本地`
  - `保留本地并覆盖云端`
  - `继续上次同步 / 上传 / 拉取`

而不是继续扩散成一整套 Git 客户端术语。
