## 1. 这份补充计划要解决什么问题

这份文档只补“永久栏目主栏 / 副本在运行时显示一致性”这一段。

要解决的不是书签正文真相源丢失，而是下面这类严重现象：

- 主栏与副本之间互相拖动后，一边正常，另一边临时显示为空
- 在副本里新增书签后，主栏层级短暂错乱，重开后恢复
- 主栏 / 副本 / 副本之间的移动、修改、删除，在当前页内表现不一致

这些现象共同说明：

- Chrome bookmarks API 仍是权威真源
- 当前问题主要出在“页面运行时内容同步链路”
- 重开恢复正常，说明大多数情况下不是底层书签数据真丢了，而是当前页多个视图壳没有在同一时刻吃到同一份内容结果

## 1.1 当前已落地状态

截至本轮实现，下面这些已经进代码：

- `history.js` 已补出统一共享渲染入口，主栏和副本可以从同一份共享内容结果重画
- 实时 `新增 / 删除 / 修改 / 移动` 已不再只依赖“主栏局部 DOM 补丁 + 副本稍后跟随”
- Canvas 永久栏目实时事件里，旧的“只改主树 `#bookmarkTree`”增量 DOM 补丁已被共享渲染链路旁路，避免主体和副本被两套链路分别写成不同状态
- 旧的永久栏目 DOM 增量补丁主链已从实时监听中物理拆除，避免后续维护时被误接回共享树路径
- 实时 `新增 / 删除 / 修改 / 移动` 已改成“帧内合并一次共享刷新”，避免一次操作把主体和副本连续重刷多轮
- 主树 `MutationObserver -> 副本补刷` 这条旧同步旁路已从共享树主链摘掉，避免一次共享渲染后又触发第二轮副本刷新
- `renderTreeView()` 的完整渲染、缓存快路径、无变化快路径、空树、报错分支，都会主动把副本拉回共享内容结果
- `bookmark_canvas_module.js` 的布局恢复、壳快照恢复，已补“恢复壳后立即触发共享树同步”
- 主栏 / 副本各自的说明、折叠、滚动、懒加载展开进度、卡片位置尺寸、`copyId` / `displayIndex` 仍保留在各自壳状态里

当前还需要人工重点回归的，不是“能不能编译”，而是下面这些实操链路：

- 主栏 -> 副本拖动
- 副本 -> 主栏拖动
- 副本 A -> 副本 B 拖动
- 在副本里新增书签
- 导入 / 同步恢复后，不重开页面直接看当前显示是否一致

## 2. 当前结构到底是什么

先把当前结构用业务语言画清楚。

### 2.1 当前真实数据与显示关系

```text
[ Chrome 书签真源 ]
        |
        v
[ 页面拿到一份书签树快照 ]
        |
        +---------------------------+
        |                           |
        v                           v
[ 当前树缓存 ]                 [ 主栏目局部 DOM 更新 ]
        |
        v
[ 显示专用树 / 渲染树 ]
        |
        v
[ 主栏目树 DOM ] + [ 副本 A 树 DOM ] + [ 副本 B 树 DOM ] + ...
```

当前不是“每个副本各自再去拉一遍 API”。

当前更像是：

- API 统一拿一次
- 页面里再拆成几层缓存和几份 DOM
- 主栏有时先做局部 DOM 补丁
- 副本再根据共享渲染结果同步

### 2.2 当前每个视图壳里各自独立的东西

不管是主栏还是副本，当前每个卡片都不只是“树内容”。

每个永久视图壳至少各自有：

- 自己的说明文字
- 自己的折叠 / 展开状态
- 自己的懒加载展开进度
- 自己的垂直 / 水平滚动位置
- 自己的卡片位置与尺寸
- 自己的 `copyId` / `displayIndex`

所以当前真正的结构不是“一棵树被复制了几份数据”，而是：

- 书签内容真源只有一份
- 视图壳有多个
- 每个视图壳各自保存“怎么看这棵树”

### 2.3 当前 bug 的核心成因

当前的严重 bug，不是因为副本又拉了一份不同的书签 API。

真正的问题是：

```text
同一份书签真源
-> 页面内缓存
-> 显示专用树
-> 主栏目 DOM
-> 副本 DOM
```

这条链在“新增 / 删除 / 修改 / 移动”的实时更新里，不总是统一、原子地完成。

结果就是：

- 主栏先改了一部分
- 副本晚一点同步
- 某个父文件夹因为懒加载还没展开，局部 DOM 补丁找不到位置
- 于是同一时刻不同视图壳看到的内容不一致

## 3. 这次补充计划锁死的外部边界

这次补充计划是“运行时显示一致性收口”，不是另起一套产品语义。

下面这些外部边界直接锁死，不允许实现时偷偷改变。

### 3.1 永久栏目真源不变

- 永久栏目内容真源继续是 Chrome bookmarks API
- 不把永久栏目改成副本各自持有一份独立书签正文
- 不把副本改成“独立永久书签树”

### 3.2 主栏与副本继续共享同一份内容

- 主栏和所有副本继续共用同一份书签树内容
- 副本继续只是“同内容，不同壳”
- 不允许把副本做成第二份正文真相源

### 3.3 每个视图壳继续独立

必须继续允许主栏 / 副本各自保留：

- `descriptionMd`
- `foldState`
- `scrollState`
- `cardState`
- `copyId`
- `displayIndex`
- 懒加载展开进度

也就是说：

- 共享的是内容
- 独立的是壳状态

### 3.4 导入 / 导出 / 同步外部语义不变

这次补充计划不允许破坏下面这些能力：

- 导出永久主栏正文
- 导出副本引用 / 包装
- 导入 `.canvas` 布局后恢复主栏 / 副本卡片
- 同步时识别主栏与副本节点
- 继续保留 `.canvas` 里的 `permanent-section` / `permanent-section-copy-*`
- 继续保留 `copyId` 作为外部识别锚点

## 4. 目标结构是什么

这次补充计划要把当前“半共享模型”收口成“唯一共享内容模型 + 多个独立视图壳”。

### 4.1 目标结构图

```text
[ Chrome 书签真源 ]
        |
        v
[ 永久栏目共享内容模型 ]
        |
  -----------------------------------------
  |                    |                  |
  v                    v                  v
[ 主栏视图壳 ]      [ 副本 A 视图壳 ]   [ 副本 B 视图壳 ]
  |                    |                  |
  v                    v                  v
[ 主栏 DOM ]        [ 副本 A DOM ]      [ 副本 B DOM ]
```

### 4.2 这里的“共享内容模型”到底是什么

这里不是再发明一份新的永久存储。

它在运行时的职责只有两个：

- 接住当前页最新的永久书签树结果
- 让主栏和所有副本都从它渲染

它不是新的真相源。

真正的真相源仍然是：

- Chrome bookmarks API

共享内容模型只是：

- 当前页面里唯一权威的内容中控对象

### 4.3 这里的“视图壳”到底是什么

视图壳只负责“这个卡片怎么看共享内容”。

它不负责定义书签树内容本身。

视图壳里保留：

- 描述
- 折叠
- 懒加载展开进度
- 滚动位置
- 卡片位置 / 尺寸
- 副本编号

## 5. 懒加载在新结构里放哪

懒加载必须继续保留，但它的职责要被严格限制。

正确位置是：

```text
共享内容模型 -> 视图壳 -> 懒加载渲染器 -> DOM
```

意思是：

- 共享内容模型里保存完整树结构
- 懒加载只决定当前这个视图壳先画多少 DOM
- 懒加载不能再决定“哪一份内容才算当前真实内容”

所以这次改造不删懒加载。

这次改造只是把懒加载从“半数据层 + 半渲染层”收回到“纯渲染层”。

## 6. 与导入 / 导出 / 同步的关系

这次补充计划不要求重做文件格式。

要改的是“运行时刷新接线方式”，不是“外部文件协议语义”。

### 6.1 保持不变的部分

- 主永久栏目仍导出真实永久正文
- 副本仍导出引用 / 包装
- `.canvas` 仍承载主栏和副本卡片布局
- `bcs:canvas` 仍是永久卡片布局 canonical source
- `bcs:perm:copies` 仍只存副本元数据
- `copyId` 仍是副本识别锚点

### 6.2 需要改变的部分

导入 / 同步 / 拉取之后，不能再让主栏和副本各自零散恢复内容。

正确做法改成：

```text
导入 / 同步恢复
    -> 更新壳状态
    -> 触发共享内容模型刷新
    -> 主栏与所有副本统一从共享内容模型重画
```

也就是：

- 文件格式尽量不动
- 页面内恢复链路统一走共享内容模型

## 7. 本次重构必须保住的功能清单

下面这些不是“尽量保留”，而是本次实施的硬约束。

| 能力 | 必须保留的结果 |
|---|---|
| 主栏 / 副本说明 | 每个视图壳继续独立说明，不互相覆盖 |
| 折叠状态 | 主栏 / 每个副本继续独立保存与恢复 |
| 垂直滚动条位置 | 主栏 / 每个副本继续独立保存与恢复 |
| 懒加载 | 继续保留，且允许不同视图壳展开深度不同 |
| 主栏与副本共享内容 | 继续共享同一份书签内容，不分裂成多份正文 |
| 导入 | 继续恢复主栏 / 副本卡片与壳状态 |
| 导出 | 继续导出主正文 + 副本包装 |
| 同步 | 继续识别主栏 / 副本与 `copyId` |
| `.canvas` 节点 id | 继续保留 `permanent-section` / `permanent-section-copy-*` |
| 上下文菜单 / 目录 / 搜索 | 继续能按 `copyId` 与视图上下文工作 |

## 8. 实施顺序

### 8.1 第一步：先正式定义“共享内容模型”和“视图壳对象”

先补对象边界，不先大改所有渲染。

要先明确两件事：

- 哪些字段属于共享内容模型
- 哪些字段属于视图壳

这一刀做完后，任何永久栏目相关代码都必须能回答：

- 我现在读的是内容，还是壳

### 8.2 第二步：统一主栏与副本的内容渲染入口

要求：

- 主栏内容渲染和副本内容渲染都走同一个入口
- 不再让主栏长期拥有“特殊 DOM 增量捷径”
- 不再依赖主栏 `innerHTML` 作为副本内容来源

### 8.3 第三步：统一实时变更链路

新增 / 删除 / 修改 / 移动时，永久栏目链路收口成：

```text
用户操作
-> Chrome bookmarks API 真修改
-> 共享内容模型更新
-> 主栏 / 所有副本一起重画
-> 各自恢复壳状态
```

实现时要特别注意：

- 有副本存在时，不允许再把“局部 DOM 补丁成功一半”视为正常路径
- 对永久栏目这条线，正确性优先于局部增量小优化

### 8.4 第四步：把导入 / 导出 / 同步接到统一对象边界

这一刀不重写外部协议，但要统一内部读写口。

要求：

- 导出读取共享内容模型 + 视图壳
- 导入恢复视图壳后，统一触发共享内容刷新
- 同步比较时，正文只比较一份 permanent 内容；副本差异只比较壳

### 8.5 第五步：补兼容层与清理顺序

现有仓库还有一些旧 key、旧 DOM 兜底和旧恢复路径。

这一步要求：

- 旧 key 继续可读
- 新结构优先写统一对象
- 清理旧路径必须分阶段进行，不能一次性删除

## 9. 验收标准

下面这些场景必须全部通过，才算这次重构完成。

### 9.1 主栏 / 副本实时一致性

- 主栏 -> 副本移动文件夹，双方当前页立即一致
- 副本 -> 主栏移动书签，双方当前页立即一致
- 副本 A -> 副本 B 移动节点，所有永久视图立即一致
- 在副本里新增书签，主栏层级不允许临时消失

### 9.2 壳状态独立性

- 主栏折叠状态不覆盖副本折叠状态
- 副本 A 滚动位置不覆盖副本 B
- 副本说明互相独立
- 不同视图壳允许懒加载展开深度不同

### 9.3 导入 / 导出 / 同步兼容

- 导出后主栏文件与副本文件结构保持兼容
- 导入旧包后仍能恢复主栏 / 副本
- 同步拉取后不会把副本误当成临时栏目
- `copyId`、`.canvas` 节点 id、目录定位、上下文菜单作用域继续正常

## 10. 结论

这次补充计划不是要把永久栏目再造一份新真相源。

真正要做的是：

- 继续让 Chrome bookmarks API 作为唯一真源
- 在当前页内补出一个真正权威的共享内容模型
- 让主栏与副本都从这份内容模型渲染
- 把说明、折叠、滚动、懒加载、卡片位置这些东西继续留在各自视图壳

最终目标只有一句话：

- 内容统一
- 壳继续独立
- 功能不能丢
