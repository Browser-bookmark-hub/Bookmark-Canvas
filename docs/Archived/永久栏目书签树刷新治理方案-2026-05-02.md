# 永久栏目书签树刷新治理方案（2026-05-02）

## 1. 背景

当前问题不是“永久栏目不能刷新”。

永久栏目在以下场景刷新是合理的：

- 打开侧边栏或 Canvas 页面时首次加载。
- 插件内部新增、删除、移动、修改永久书签。
- Chrome 自带书签管理器或其他外部入口修改书签。
- 浏览器书签导入、恢复、批量变更结束后。
- 永久栏目副本首次创建或需要补齐共享树内容时。

当前真正需要治理的是：

- 用户没有直接操作永久书签，只是切换 tab / 页面 / 窗口后，偶发看到永久栏目整棵树重挂。
- 快速来回切换不一定复现，但间隔一段时间后偶尔会立刻刷新。
- 临时栏目体感较轻，永久栏目更明显，因为永久栏目同时涉及 Chrome bookmarks、永久 JSON、共享树、副本、展开状态、滚动状态、懒加载索引和侧边栏壳。

## 2. 当前侧边栏壳结构

当前侧边栏不是直接打开 `history.html`，而是存在外层壳。

主壳文件：

- `panel-shell.html`
- `panel-shell-theme-bootstrap.js`
- `panel-shell.css`

`panel-shell.html` 中通过 iframe 加载真实 Canvas：

```html
<iframe
  id="canvasSidePanelFrame"
  src="history_html/history.html?view=canvas&sidepanel=1"
  title="Bookmark Canvas Side Panel"
  loading="eager"
></iframe>
```

这意味着侧边栏实际是两层：

- 外层 shell：负责首屏背景、主题、防白闪、iframe 容器。
- 内层 Canvas：`history_html/history.html?view=canvas&sidepanel=1`，负责真实画布和永久栏目。

因此治理永久栏目刷新时，要注意：

- 外层 shell 重新加载，会导致 iframe 内层重新初始化。
- iframe 内层重新初始化，会重新走 Canvas 初始化和 `renderTreeView()`。
- 不能把外层 shell 的生命周期误判为永久书签真实变化。
- 侧边栏壳存在时，应尽量让内层 Canvas 的永久树渲染具备 DOM 指纹幂等能力，避免 iframe 恢复、tab 切换、side panel 生命周期变化造成无意义重挂。

## 3. 当前项目的无变化判断机制

当前项目已经有“书签树无变化”判断。

主要标准是树指纹：

```js
getTreeFingerprint(tree)
```

该指纹提取以下字段：

- `id`
- `title`
- `url`
- `parentId`
- `index`
- `children`

因此它能识别：

- 新增
- 删除
- 移动
- 排序变化
- 标题变化
- URL 变化
- 文件夹层级变化

当前逻辑大致是：

```js
const currentFingerprint = getTreeFingerprint(currentTree);

if (!forceRefresh && cachedTreeData && currentFingerprint === lastTreeFingerprint) {
  // 认为书签树没有变化
}
```

另有 `lastTreeSnapshotVersion`，但当前永久 JSON 真相源路径通常返回 `version: null`，所以主判断仍是 fingerprint。

## 4. 当前问题的关键点

当前的主要问题不是“没有判断书签树是否变化”，而是：

**数据无变化后，UI 仍可能重挂永久树 DOM。**

### 4.1 快速缓存路径会重挂主永久树

在 `renderTreeView()` 的快速缓存路径中，如果存在永久栏目副本，会调用：

```js
__renderPermanentTreeSharedViews({
  includePrimary: true,
  includeCopies: true,
  reason: 'render-cached-fast-shared'
});
```

这意味着：

- 已有缓存。
- 不一定发生真实书签变化。
- 但主永久栏目和副本都可能被重新渲染。

### 4.2 无变化路径会重挂主永久树

在 `renderTreeView()` 的指纹一致路径中，如果存在永久栏目副本，会调用：

```js
__renderPermanentTreeSharedViews({
  includePrimary: true,
  includeCopies: true,
  reason: 'render-cached-nochange-shared'
});
```

这意味着：

- 书签树指纹已经判断为无变化。
- 但主永久栏目仍可能被 `replaceChildren()`。
- 用户体感就是“我没动书签，永久栏目又刷新了”。

### 4.3 操作后延迟同步会清缓存

插件内部书签操作后，会调度：

```js
schedulePermanentMainStorageSyncFromChrome(reason, 180)
```

该逻辑会同步 Chrome bookmarks 到永久 JSON，然后清理渲染缓存：

```js
bridge.clearPermanentTreeRenderCaches()
```

这会清理：

- `cachedTreeData`
- `lastTreeFingerprint`
- `lastTreeSnapshotVersion`
- `cachedCurrentTreeIndex`
- `cachedRenderTreeIndex`

因此可能出现：

1. 用户完成操作。
2. 界面已经刷新一次。
3. 延迟同步清掉缓存。
4. 用户切换 tab / 侧边栏恢复 / 其他入口触发 `renderTreeView()`。
5. 因缓存不存在，重新构建永久树。

### 4.4 多窗口 / 多侧边栏会触发 storage 实时同步

当前 Canvas 状态保存会写 `bcs:signal`。

其他扩展页面或侧边栏通过 `chrome.storage.onChanged` 消费信号，然后执行：

```js
__resetCanvasDomAndStateForImport()
__applyCanvasTempStateObject()
__finalizeTempNodesLoad()
loadPermanentSectionPosition()
```

`loadPermanentSectionPosition()` 又会触发永久布局和副本树同步。

因此多窗口、多侧边栏同时打开时，一个上下文的保存可能导致另一个上下文偶发重套 Canvas 状态，并间接触发永久树重挂。

### 4.5 Chrome 后台节流会制造偶发性

用户快速切换 tab 时通常不会复现。

但如果页面进入后台一段时间，Chrome 可能节流：

- `setTimeout`
- `chrome.storage.onChanged`
- `chrome.bookmarks` 事件
- Promise 队列
- DOM 更新

用户切回来时，之前排队的任务可能集中恢复执行。

这会造成“刚切回来就刷新”的体感。

## 5. Bookmark-Backup 项目的可借鉴点

参考项目：

`/Users/kk/Downloads/chrome download/Bookmark-Backup/Bookmark-Backup-3.0`

该项目对书签增加、删除、移动、修改的监听更准确，核心特点如下。

### 5.1 事件监听覆盖完整

监听：

- `browserAPI.bookmarks.onCreated`
- `browserAPI.bookmarks.onRemoved`
- `browserAPI.bookmarks.onChanged`
- `browserAPI.bookmarks.onMoved`

### 5.2 不是一收到事件就全量刷新 UI

其策略是：

- 先尝试把事件增量应用到 `cachedCurrentTree`。
- 如果增量应用失败，才调度快照刷新兜底。
- 对 add/remove 做短 quiet window 合并。
- 对大量 add/remove 做 bulk 路径，不逐条刷新 UI。

典型函数：

- `applyIncrementalCreateToCachedCurrentTree()`
- `applyIncrementalRemoveFromCachedCurrentTree()`
- `applyIncrementalChangeToCachedCurrentTree()`
- `applyIncrementalMoveToCachedCurrentTree()`
- `scheduleCachedCurrentTreeSnapshotRefresh()`
- `flushPendingAddRemoveEvents()`

### 5.3 有全局 mute / grace 机制

参考项目有更完整的 UI mute 状态：

- restore
- import
- bulk
- marker bulk
- local canvas bulk
- resume grace

相关逻辑：

- `isHistoryBookmarkUiMuted()`
- `isHistoryBookmarkEventGraceActive()`
- `shouldMuteHistoryBookmarkRealtimeEventHandling()`
- `flushDeferredHistoryBookmarkUiWork()`

这套机制的价值是：

- 批量恢复、导入、批量操作期间不让实时事件逐条扰动 UI。
- 操作结束后保留一个短 grace，吸收晚到事件。
- grace 结束后集中处理必要的 deferred work。

### 5.4 关键经验

`Bookmark-Backup` 的重点不是“不刷新”，而是：

1. 真实书签事件要准确接收。
2. 能增量更新缓存就不全量刷新。
3. 事件密集时先合并。
4. 批量/恢复/导入期间先 mute。
5. 最终需要时再重读快照兜底。
6. UI 刷新和数据同步解耦。

这些经验可以迁移到当前永久栏目，但必须结合当前项目的特殊点：

- 当前永久栏目有主栏目 + 多副本。
- 当前侧边栏有外层 shell + iframe。
- 当前永久内容有 Chrome bookmarks 与永久 JSON 双真相源同步问题。
- 当前 Canvas 还有 `bcs:signal` 跨窗口同步。

## 6. 最新治理目标

本方案目标不是减少所有刷新，而是区分三类刷新。

### 6.1 必须刷新

以下场景允许主永久栏目整树重挂：

- 首次打开且 DOM 为空。
- `forceRefresh === true` 且来源是明确书签结构变化。
- 指纹 / 版本确认书签树变化。
- 增量事件无法安全应用，需要快照兜底。
- 导入 / 恢复 / 大批量变更结束后统一刷新。

### 6.2 只允许副本补齐

以下场景不应重挂主永久栏目，只允许副本补齐或同步：

- 永久栏目副本首次创建。
- 副本 DOM 缺少 `.bookmark-tree` 内容。
- 主永久栏目 DOM 已经是同一份书签树指纹。
- `render-cached-fast-*` 路径。
- `render-cached-nochange-*` 路径。

### 6.3 不应刷新

以下场景不应重挂主永久栏目：

- 单纯切换 tab 回来。
- 侧边栏 shell 恢复但 iframe 内主树 DOM 已存在且指纹相同。
- 多窗口收到 `bcs:signal`，但永久书签内容和布局没有实际变化。
- 目录导航、滚动状态、展开状态、描述高度等非书签结构变化。

## 7. 推荐改造方案

### 阶段一：让“无变化”真正不重挂主树

这是优先级最高、风险最低的修复。

调整原则：

- `render-cached-fast-shared` 不允许 `includePrimary: true`。
- `render-cached-nochange-shared` 不允许 `includePrimary: true`。
- 缓存路径只同步副本，不重挂主永久栏目。

目标行为：

```js
__renderPermanentTreeSharedViews({
  includePrimary: false,
  includeCopies: true,
  reason: 'render-cached-nochange-shared'
});
```

适用路径：

- 快速缓存路径。
- 指纹一致路径。
- tab 切回触发的普通 `renderTreeView()`。
- side panel 恢复后已有主 DOM 的普通检查。

预期收益：

- 直接减少“没动书签但主永久栏目重挂”。
- 不影响真实新增、删除、移动、修改。
- 不影响副本缺树时补齐。

### 阶段二：给永久树 DOM 增加渲染指纹幂等保护

当前 JS 缓存可能被清掉，因此只依赖 `cachedTreeData` 和 `lastTreeFingerprint` 不够稳。

建议在主树和副本树 DOM 上记录：

```js
tree.dataset.permanentTreeFingerprint = fingerprint;
tree.dataset.permanentTreeSource = 'bcs' | 'chrome';
tree.dataset.permanentTreeRenderRole = 'primary' | 'copy';
```

在 `__renderPermanentTreeIntoTree(tree)` 前判断：

- 如果目标树已有同 fingerprint。
- 且不是强制刷新。
- 且不是首次空树。
- 且不是明确结构变更事件。

则跳过 `replaceChildren()`。

目标：

即使 JS 缓存被清理，只要 DOM 上已经是同一版本书签树，也不重挂。

这对侧边栏壳尤其重要，因为 iframe 恢复、页面生命周期变化时 JS 状态和 DOM 状态可能不同步。

### 阶段三：引入 Bookmark-Backup 式事件队列和增量缓存更新

当前项目已经有部分批量和增量处理，但永久栏目由于 BCS 永久 JSON 和副本共享树存在，仍偏向强制刷新。

建议统一成事件管线：

```text
Chrome bookmarks event
  -> 事件归一化
  -> mute/grace 判断
  -> 增量应用 cachedCurrentTree
  -> 同步永久 JSON
  -> 标记永久树内容版本 dirty
  -> 按需刷新 DOM
```

对不同事件：

- `onCreated`：增量插入缓存树，失败则快照兜底。
- `onRemoved`：增量删除缓存树，失败则快照兜底。
- `onChanged`：只更新节点 title/url，优先局部 DOM 更新。
- `onMoved`：增量移动缓存树，失败则快照兜底。

借鉴 `Bookmark-Backup`：

- add/remove 使用 quiet window 合并。
- 大批量 add/remove 直接走 snapshot fallback。
- onChanged/onMoved 前先 flush add/remove 队列，保证事件顺序。
- mute 期间只标记 dirty，不刷新 UI。

### 阶段四：扩展本项目的 mute/grace 模型

当前项目有：

```js
BULK_BOOKMARK_POST_EVENT_GRACE_MS = 1800
```

建议升级为类似 `Bookmark-Backup` 的统一状态：

```text
permanentBookmarkUiMuteState:
  localBulk
  chromeImport
  restore
  bcsSync
  sidePanelBootstrap
  externalStorageReplay
  resumeGraceUntil
```

用途：

- 插件内部批量操作期间，不让 Chrome 事件逐条刷新。
- BCS 同步回写期间，不让自己制造的 storage/bookmarks 回声导致二次重挂。
- 侧边栏 iframe 初始化期间，只允许首屏必要渲染。
- 页面恢复后短 grace 内，只合并事件，不立刻重挂主树。

### 阶段五：拆分“数据同步”和“视觉重挂”

当前一些函数同时做了：

- 读取书签树
- 更新缓存
- 同步永久 JSON
- 替换 DOM
- 恢复滚动
- 绑定事件
- 同步副本

建议拆为：

```text
syncPermanentDataFromChrome()
updatePermanentTreeCache()
markPermanentTreeContentDirty()
renderPermanentPrimaryIfNeeded()
renderPermanentCopiesIfNeeded()
restorePermanentShellState()
```

这样可以明确：

- 数据变了，不一定立刻重挂主 DOM。
- 副本缺树，不代表主树需要重挂。
- layout/storage 信号，不等于书签内容变化。
- shell 恢复，不等于永久树数据变化。

## 8. 推荐优先级

### P0：立即处理

- 修改 `render-cached-fast-shared`：不要重挂主永久栏目。
- 修改 `render-cached-nochange-shared`：不要重挂主永久栏目。
- 对已有主树 DOM 且书签指纹一致的情况，直接保留 DOM。

### P1：短期处理

- 给 `.bookmark-tree` 写入 fingerprint dataset。
- `__renderPermanentTreeIntoTree()` 增加 same-fingerprint skip。
- 副本只在缺树或 fingerprint 不一致时补齐。

### P2：中期处理

- 迁移 `Bookmark-Backup` 的事件队列思想。
- 增强 add/remove quiet window。
- onChanged/onMoved 优先增量缓存更新。
- 失败再走 snapshot fallback。

### P3：长期处理

- 完整建立永久树内容版本模型。
- 为 BCS 永久 JSON 增加稳定 revision / contentHash。
- 将 Chrome bookmarks 事件、永久 JSON 写入、DOM 渲染完全解耦。

## 9. 验收标准

### 9.1 不应再发生

- 只切换浏览器 tab，书签树无变化时，主永久栏目整树重挂。
- 多窗口收到画布状态同步，但永久书签内容未变化时，主永久栏目整树重挂。
- 永久栏目副本存在时，缓存路径无条件重挂主永久栏目。

### 9.2 应继续发生

- 插件内部新增永久书签后，永久栏目更新。
- 插件内部删除永久书签后，永久栏目更新。
- 插件内部移动永久书签后，永久栏目更新。
- 插件内部修改标题/URL 后，永久栏目更新。
- Chrome 书签管理器外部修改后，永久栏目更新。
- 大批量导入/恢复结束后，永久栏目最终一致。

### 9.3 体验要求

- 主永久栏目无变化时不闪、不重挂、不抢滚动。
- 副本可以补齐，但不应反向导致主树重挂。
- 侧边栏 shell 恢复时，如果 iframe 内 DOM 仍有效，不应产生可见整树刷新。
- 页面后台恢复后，积压事件应合并处理，不应逐条造成多次刷新。

## 10. 推荐实施顺序

建议按以下顺序实施：

1. 先改无变化路径 `includePrimary: false`。
2. 再加 DOM fingerprint 幂等保护。
3. 再统一永久树事件队列。
4. 最后抽象 revision/contentHash。

原因：

- 第 1 步最小、最直接，能立刻降低“无理由刷新”。
- 第 2 步能解决缓存被清后仍可判断 DOM 是否已经是最新。
- 第 3 步吸收 `Bookmark-Backup` 的准确事件处理经验。
- 第 4 步是架构完善，不适合一开始就大改。

## 11. 当前结论

当前偶发刷新不是固定定时校准。

更准确的判断是：

- 当前有树指纹判断，但无变化路径仍可能重挂主树。
- 侧边栏壳 + iframe 生命周期会放大初始化和恢复路径的可见刷新。
- 多窗口/多侧边栏 `bcs:signal` 会制造偶发同步。
- 操作后延迟同步清缓存，会让下一次普通渲染更容易重建。
- `Bookmark-Backup` 的监听准确性来自“事件增量应用 + quiet window + mute/grace + snapshot fallback”，值得迁移。

最终治理方向：

**以 Chrome bookmarks 事件保证数据准确，以 fingerprint/revision 保证变化判断，以 DOM fingerprint 保证视觉幂等，以 mute/grace 保证多窗口和批量操作不扰动 UI。**
