# 永久栏目 Chrome 校准与嵌入字段跟随计划书（执行版，2026-04-28）

> 返回文档索引：[docs/README.md](./README.md)

## 1. 这份计划解决什么

这份计划是对下面两份文档的补充和收口：

- [永久栏目 JSON 真相源与 sourceID 嵌入式存储改造计划书（2026-04-26）](./永久栏目JSON真相源与sourceID嵌入式存储改造计划书-2026-04-26.md)
- [永久栏目 JSON 真相源改造当前代码 Review 报告（2026-04-27）](./永久栏目JSON真相源改造当前代码Review报告-2026-04-27.md)

它专门解决这次讨论里的一个核心问题：

> 用户在 Chrome 书签管理器、其他插件、或者我们自己的插件里改了永久书签后，永久栏目内部 JSON 怎么和 Chrome 当前树对齐，并且让 `sourceID`、后续颜色/置顶/文件夹标识等嵌入字段跟着同一个节点移动。

这里不是推翻当前架构。当前架构仍然成立：

1. Chrome Bookmarks API 是浏览器原生书签的执行接口。
2. 本地永久 JSON 保存 Chrome 当前树的结构，并额外保存 `sourceID` 和后续嵌入字段。
3. Chrome ID 是本机可用的绑定句柄；推送云端和手动导出时剥离。
4. `sourceID` 和后续嵌入字段跟着节点 JSON 块走，不因为改名、改 URL、移动而变化。

本计划要补的是一层明确的“Chrome 当前树校准永久 JSON”机制。

## 2. 已确认的规则

### 2.1 sourceID 规则

| 动作 | 规则 |
|---|---|
| 改名 | 保留原节点 `sourceID` |
| 改 URL | 保留原节点 `sourceID` |
| 移动 | 整个节点块移动，`sourceID` 跟着走 |
| 同级重排 | 节点块顺序变化，`sourceID` 跟着对应节点走 |
| 删除 | 节点消失，节点上的 `sourceID` 一起消失 |
| 新增 | 新 Chrome ID，新 `sourceID` |
| 复制为新节点 | 新 Chrome ID，新 `sourceID` |
| 剪切移动 | Chrome ID 不变，保留 `sourceID` |

以后加入的颜色、置顶、文件夹标识、说明等嵌入字段也遵守同一条规则：跟着 Chrome ID 对应的节点块走。

### 2.2 本地普通操作不再解释成“一律先写 JSON”

旧计划里“先改 `bcs:perm:main.tree`，再和 Chrome API 交互”的表达容易误解。结合当前代码和这次讨论，执行口径改成：

1. 本地日常操作可以继续由 Chrome Bookmarks API 执行。
2. Chrome API 成功后，必须确认永久 JSON 已经同步到同一状态。
3. 如果 Chrome 已经成功，但永久 JSON 同步失败，不能只 `console.warn`，必须提示并标记需要修复。
4. 新增节点时，必须明确新 Chrome ID 对应哪个 `sourceID`。

也就是说，重点不是形式上的“先写还是后写”，而是最后不能留下“Chrome 已变、永久 JSON 状态不明”的结果。

### 2.3 云端覆盖本地是另一条流程

云端覆盖本地不是普通本地操作，它是破坏性同步流程：

```text
云端永久 JSON -> 写入/替换本地永久 JSON -> 应用到 Chrome 书签树 -> 回写 Chrome ID -> 后置校验
```

这里要继续采用中断恢复事务：

1. 开始前保存两份备份：
   - 当前永久栏目 JSON。
   - 当前 Chrome Bookmark API 树。
2. 保存目标云端永久 JSON。
3. 中断后进入恢复面板。
4. “按云端继续”就是继续把目标云端 JSON 覆盖到 Chrome。
5. “回到覆盖前本地状态”就是用开始前永久 JSON 覆盖回 Chrome。
6. 两条路径都按全量覆盖类流程做，不在恢复面板里做临时增量修补。

## 3. 当前代码真实现状

### 3.1 关闭期间

当前没有后台常驻监听 Chrome 书签变化。

用户关闭侧边栏/标签页后，如果在 Chrome 书签管理器或别的插件里大改书签，当前插件主要依赖下次打开时刷新。

但当前代码的取树路径有一个问题：`getBookmarkTreeSnapshot()` 会优先读 `bcs:perm:main`，再回退到后台 `getBookmarkSnapshot` 和 `chrome.bookmarks.getTree()`。

这意味着：

1. 如果永久 JSON 已经旧了，下次打开不一定第一步就拿 Chrome 当前树校准。
2. 旧永久 JSON 可能先参与渲染。
3. 后续嵌入字段越多，这个问题越明显。

### 3.2 打开期间

当前前台已经有监听：

- `bookmarks.onCreated`
- `bookmarks.onRemoved`
- `bookmarks.onChanged`
- `bookmarks.onMoved`
- `bookmarks.onImportBegan`
- `bookmarks.onImportEnded`

打开期间的小改动会触发事件，代码会更新缓存、刷新视图，并调度从 Chrome 同步到永久 JSON。

当前也有批量优化：

- 新增/删除事件会先合并一小段时间。
- 数量超过阈值时走批量路径。
- Chrome 导入开始/结束时会静音，结束后再刷新。

这条方向是对的，后续不要改成每个事件都做全量重算。

### 3.3 仍缺的关键点

当前仍缺这些收口：

1. 打开时没有明确“先读 Chrome 当前树，再校准永久 JSON”的步骤。
2. 回到前台时没有明确做一次校准。
3. Chrome -> 永久 JSON 同步主要保 `sourceID`，不是保整个嵌入字段包。
4. 运行期仍允许在普通整树同步里静默补旧节点的 `sourceID`。
5. 缺 `bookmarks.onChildrenReordered`。
6. 本地操作 Chrome 成功后，永久 JSON 同步失败还可能只是日志。
7. 永久 payload 仍有退回 Chrome subtree 或旧缓存的路径。
8. 根目录 `folderType/syncing` 还没有完整进入比较和 hash。

## 4. 目标方案：Chrome 当前树校准永久 JSON

### 4.1 校准什么时候发生

必须在这些时机做校准：

1. 侧边栏/标签页打开并准备渲染永久栏目之前。
2. 页面从后台回到前台时。
3. Chrome 导入结束后。
4. 前台监听到大批量新增/删除事件并进入批量路径后。
5. 收到同级重排事件后。
6. 本地插件操作 Chrome 成功，但需要确认永久 JSON 已同步时。

不做后台常驻全量同步。原因是以前已经遇到过大批量导入导致卡顿的问题。这里采用“前台打开/回前台/批量结束时校准一次”的方案。

### 4.2 校准输入

每次校准读取两份数据：

1. Chrome 当前树：从 `chrome.bookmarks.getTree()` 获取。
2. 旧永久 JSON：从 `bcs:perm:main.tree` 获取。

Chrome 当前树负责提供最新的浏览器真实结构：

- Chrome ID
- title
- url
- children
- parentId
- index

旧永久 JSON 负责提供插件自己的嵌入字段：

- `sourceID`
- 顶层 `folderType`
- 顶层 `syncing`
- 未来的颜色、置顶、文件夹标识、说明等字段

### 4.3 校准算法

核心算法很简单：

1. 从旧永久 JSON 建一个表：Chrome ID -> 嵌入字段包。
2. 遍历 Chrome 当前树。
3. 每个 Chrome 节点按 Chrome ID 找旧字段包。
4. 找到了，就把旧字段包贴回当前 Chrome 节点。
5. 没找到，说明这是新节点，生成新的 `sourceID`。
6. 如果 Chrome ID 找到了旧节点，但旧节点缺 `sourceID`，这是旧数据损坏或迁移遗漏，不能静默补；应提示修复。
7. 最后得到一棵新的本地永久树，写回 `bcs:perm:main.tree`。

重要限制：

1. title/url/children 顺序以 Chrome 当前树为准。
2. `sourceID` 和插件嵌入字段以旧永久 JSON 为准。
3. 不能把旧永久 JSON 的 title/url 反贴到 Chrome 当前树上。
4. 只因为 Chrome ID 回写变化，不应该标 dirty。
5. 如果 Chrome 真实内容变化了，剥离本地 Chrome ID 后的同步 JSON 变化，应标 dirty。

### 4.4 嵌入字段包

当前第一步至少保存：

- `sourceID`
- `folderType`
- `syncing`

但实现时不要把逻辑写死成只保存 `sourceID`。应该做成“嵌入字段包”，以后能自然扩展：

```json
{
  "sourceID": "src-xxx",
  "folderType": "bookmarks-bar",
  "syncing": false,
  "bookmarkCanvasMeta": {
    "color": "red",
    "pinned": true,
    "folderMarker": "work"
  }
}
```

具体字段名后续可以再定，但承载方式要提前按“包”设计，不要继续只做 `Chrome ID -> sourceID`。

## 5. 分流程说明

### 5.1 用户在 Chrome 书签管理器或其他插件里操作，且我们的页面关闭

流程：

1. 用户在外部改 Chrome 书签。
2. 我们没有页面打开，也没有后台常驻同步。
3. 用户下次打开侧边栏/标签页。
4. 打开时先读 Chrome 当前树。
5. 再读旧永久 JSON。
6. 按 Chrome ID 把 `sourceID` 和嵌入字段贴回去。
7. 写成新的永久 JSON。
8. 渲染 UI。

效果：

- 改名、改 URL、移动、重排都能保留旧 `sourceID`。
- 删除的节点自然消失。
- 新增的外部节点会得到新 `sourceID`。
- 大批量导入只在打开时做一次校准。

### 5.2 用户在 Chrome 书签管理器或其他插件里操作，且我们的页面打开

流程：

1. 小量操作：继续用现有 Chrome 事件监听。
2. UI 可以先做轻量增量更新，避免整树闪烁。
3. 延迟做一次永久 JSON 校准。
4. 短时间大批量新增/删除：继续走现有批处理阈值。
5. Chrome 导入：`onImportBegan` 静音，`onImportEnded` 后做一次全量校准。

效果：

- 小操作看起来仍然及时。
- 大批量导入不会每个事件都重算。
- 最终永久 JSON 以 Chrome 当前树为准，并保留嵌入字段。

### 5.3 用户在我们的插件里操作永久栏目

涉及：

- 右键新增书签/文件夹
- 右键改名
- 右键删除
- 右键移动
- 插件内拖拽移动
- 快速添加到永久栏

流程：

1. 调 Chrome Bookmarks API。
2. Chrome 成功后，触发或主动等待永久 JSON 校准。
3. 新增时记录新 Chrome ID 和本次生成的 `sourceID` 的归属。
4. 校准成功后才认为本次插件操作完整成功。
5. 校准失败时提示用户，并标记永久栏目需要修复。

效果：

- 不再留下“Chrome 已成功，但永久 JSON 不知道有没有成功”的状态。
- 改名、改 URL、移动都保留原 `sourceID`。
- 删除就是节点消失。
- 新增一定有明确的新 `sourceID`。

### 5.4 云端覆盖本地

流程：

1. 开始前保存当前永久 JSON 和当前 Chrome 树。
2. 保存目标云端永久 JSON。
3. 用目标云端永久 JSON 替换本地永久 JSON。
4. 把目标树应用到 Chrome。
5. Chrome 完成后回写本机 Chrome ID。
6. 后置校验。
7. 成功后清恢复锁。

中断恢复：

| 恢复动作 | 做什么 |
|---|---|
| 按云端继续 | 用目标云端永久 JSON 继续覆盖 Chrome，并回写 Chrome ID |
| 回到覆盖前本地状态 | 用开始前永久 JSON 覆盖 Chrome，并回写 Chrome ID |
| 导出备份 | 导出开始前永久 JSON、开始前 Chrome 树、目标云端永久 JSON、当前失败状态 |

效果：

- 不再把半完成的远端 JSON 当成本地正常状态。
- 用户关闭标签页或侧边栏后回来，恢复面板能继续或回滚。
- 恢复面板里的两条路都是明确的覆盖流程。

## 6. 具体改动计划

### P0：统一口径和文档

- [x] 在 review 报告中纠正“本地操作必须先写 JSON 再调 Chrome”的误导表述。
- [x] 新增本计划，明确校准层是下一步主线。

### P1：实现打开/回前台校准

目标：

- 打开侧边栏/标签页时，先用 Chrome 当前树校准永久 JSON，再渲染。
- 页面回到前台时，如果距离上次校准已有一段时间，做一次校准。

涉及位置：

- `history_html/history.js`
- `history_html/bookmark_canvas_module.js`

要点：

1. 新增明确的“读 Chrome 当前树”路径，不走 `bcs:perm:main` 优先的旧快照路径。
2. 渲染永久栏目之前先执行校准。
3. 校准时用 Chrome 当前树作为结构，用旧永久 JSON 作为嵌入字段来源。
4. 校准完成后再刷新主永久栏和副本。
5. 校准失败要提示，不要静默渲染旧状态。

验收：

- 关闭页面后，在 Chrome 书签管理器改名，重新打开，`sourceID` 保留。
- 关闭页面后，在 Chrome 书签管理器移动节点，重新打开，节点新位置正确，`sourceID` 保留。
- 关闭页面后，删除节点，重新打开，节点从永久 JSON 消失。
- 关闭页面后，新增节点，重新打开，新节点有新 `sourceID`。

### P2：嵌入字段包跟随

目标：

- 当前先保 `sourceID/folderType/syncing`。
- 代码结构按“嵌入字段包”设计，为后续颜色、置顶、文件夹标识预留。

涉及位置：

- `history_html/bookmark_canvas_module.js`

要点：

1. 把当前 `Chrome ID -> sourceID` 的收集逻辑升级成 `Chrome ID -> embedded fields`。
2. 普通校准只给新 Chrome ID 节点生成 `sourceID`。
3. 旧 Chrome ID 节点如果原本缺 `sourceID`，进入修复提示，不静默生成。
4. 顶层根目录的 `folderType/syncing` 也作为嵌入字段保留。

验收：

- 改名、改 URL 后，`sourceID` 不变。
- 移动后，节点的 `sourceID` 跟着节点走。
- 同级重排后，节点的 `sourceID` 不串位。
- 新增节点有新 `sourceID`。
- 已存在节点缺 `sourceID` 时，不被普通校准静默补齐。

### P3：打开期间事件和大批量优化收口

目标：

- 保留当前小事件增量更新体验。
- 大批量变化后只做一次全量校准。
- 补上同级重排监听。

涉及位置：

- `history_html/history.js`

要点：

1. 保留当前新增/删除批处理阈值。
2. `onImportEnded` 后执行一次全量校准。
3. 大批量新增/删除 flush 后执行一次全量校准。
4. 注册 `bookmarks.onChildrenReordered`。
5. 同级重排可以先不做复杂局部重排，直接触发一次校准。

验收：

- 导入大量书签时页面不因每个事件重复校准而卡死。
- 导入结束后永久 JSON 和 Chrome 当前树一致。
- Chrome 书签管理器里同级排序后，永久 JSON 顺序跟着变化。

### P4：本地插件操作成功后的明确状态

目标：

- Chrome API 成功后，永久 JSON 同步失败不能静默。

涉及位置：

- `history_html/bookmark_tree_context_menu.js`
- `history_html/bookmark_tree_drag_drop.js`
- `history_html/history.js`
- `history_html/bookmark_canvas_module.js`

要点：

1. 插件自发操作成功后，等待或触发一次永久 JSON 校准。
2. 校准成功：操作完整结束。
3. 校准失败：提示用户，设置永久栏目需要修复状态。
4. 新增路径要把新 Chrome ID 和新 `sourceID` 的关系说清并落到节点上。
5. 不再把失败只留在 `console.warn`。

验收：

- 人为让永久 JSON 写入失败时，UI 能提示。
- 失败后状态里能看出永久栏目需要修复。
- 再次打开或点击修复时能重新校准。

### P5：云端覆盖事务继续保留并验收

目标：

- 云端覆盖本地继续走中断恢复事务。
- 事务里同时保存永久 JSON 和 Chrome 树。

涉及位置：

- `history_html/sync/obsidian-git-sync.js`
- 恢复面板相关代码

要点：

1. 开始前快照必须包含当前永久 JSON。
2. Chrome 树作为额外保险也保存。
3. 目标云端永久 JSON 固化到事务里。
4. 继续和回滚都走覆盖流程。
5. 后置校验必须确认 Chrome 当前树和永久 JSON 一致。

验收：

- 云端覆盖过程中模拟 Chrome API 失败，进入恢复面板。
- 中途关闭侧边栏/标签页，再打开，恢复面板能继续。
- 选择按云端继续后，Chrome 和永久 JSON 都到目标状态。
- 选择回到覆盖前本地状态后，Chrome 和永久 JSON 都回到开始前状态。

### P6：比较/hash 与导出同步口径收口

目标：

- 比较、hash、dirty、push、导出都基于剥离本地 Chrome ID 后的同步 JSON。
- 顶层根目录 `folderType/syncing` 必须参与。

涉及位置：

- `history_html/sync/obsidian-git-sync.js`
- `history_html/bookmark_canvas_module.js`

要点：

1. 同步 JSON 保留 `sourceID/folderType/syncing`。
2. 同步 JSON 剥离本地 Chrome `id`。
3. `folderType/syncing` 进入 comparable/hash/signature。
4. Chrome ID 回写不标 dirty。
5. 外部 Chrome 内容变化校准后，如果同步 JSON 变化，应标 dirty。

验收：

- 只改变本地 Chrome ID，不产生同步差异。
- 改根目录 `folderType/syncing`，能进入 hash。
- 导出/云端 JSON 没有 Chrome ID。
- 导出/云端 JSON 保留 `sourceID/folderType/syncing`。

### P7：永久来源 payload 不再退回 Chrome/cache

目标：

- 永久来源的复制、拖拽、搜索结果创建临时栏目，都从永久 JSON 取 payload。

涉及位置：

- `history_html/bookmark_tree_context_menu.js`
- `history_html/bookmark_tree_drag_drop.js`
- `history_html/search/search.js`

要点：

1. 永久节点 payload 必须从 `bcs:perm:main.tree` 读取。
2. 读不到节点或缺 `sourceID` 时失败并提示。
3. 不用 Chrome subtree 或旧缓存拼永久 payload。

验收：

- 从永久栏复制到临时栏，`sourceID` 保留。
- 从永久栏拖到临时栏，`sourceID` 保留。
- 搜索结果生成临时栏目，来源是永久节点时 `sourceID` 保留。
- 人为制造永久 JSON 缺失时，操作失败并提示，不生成无身份 payload。

### P8：守门脚本更新

目标：

- 验收脚本跟上目标态。

涉及位置：

- `tools/run-sync-guard-acceptance.sh`
- `tools/run-sync-plan-regression.sh`

要点：

1. 不再断言运行期依赖旧 `bcs:perm:source-id-map`。
2. 检查导出/同步 JSON 不含 Chrome ID。
3. 检查本地永久 JSON 节点有 Chrome ID。
4. 检查同步 JSON 保留 `sourceID/folderType/syncing`。
5. 检查普通运行期不会给已存在缺身份节点静默补 `sourceID`。

## 7. 不做什么

1. 不恢复后台常驻全量监听。
2. 不靠“只标 dirty”解决问题。
3. 不把 Chrome subtree 当永久 payload 的兜底来源。
4. 不把 `Chrome ID -> sourceID` 继续扩展成新的长期身份表。
5. 不在云端覆盖恢复面板里做临时猜测式增量修补。

## 9. 建议执行顺序

第一步先做 P1 + P2：

- 打开/回前台校准。
- 嵌入字段包跟随。

原因：这是长期关闭后再次打开、以及后续标识系统能否成立的基础。

第二步做 P3 + P4：

- 打开期间监听收口。
- 本地插件操作成功后确认永久 JSON 状态。

原因：这是日常操作体验和异常可见性的基础。

第三步做 P6 + P7 + P8：

- hash/compare 收口。
- payload 收口。
- 守门脚本收口。

原因：这是同步、导出、回归验收的最终闭环。

云端覆盖事务 P5 已经作为最高风险路径优先收尾过，后续重点是补真实浏览器场景验收；如果当前工作区没有这部分代码，则应先按 P5 补回。
