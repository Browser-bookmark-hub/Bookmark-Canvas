# 画布浏览统计：对账落盘与删除信号收敛修改方案

> **基准 Commit**：`17b95a6`（承接 `6aa030b` → `b18b0cd` → `17b95a6`）。
> **定位**：不改数据模型（仍是 `schemaVersion: 4` 分桶账本），不改任何交互与触发入口，只修 1 个丢数据 bug，并去掉 3 类无效的写盘与对账。
> **依据**：2026-11-25 在本机 Chrome 上用 CDP 实测（3403 个白名单书签、90 天内 380 条历史、快照约 206KB）。

---

## 一、结论先行

| 问题 | 严重程度 | 本方案是否处理 |
| :--- | :--- | :--- |
| `releaseMemory()` 可能把空账本写进 IndexedDB，90 天前的老账永久丢失 | 高（概率低，后果不可逆） | 是，改动一 |
| 数据零变化时仍整包读写 206KB 并广播 | 中（浪费，不出错） | 是，改动二 |
| 与书签无关的历史删除也强制跑全流程对账 | 中（浪费，不出错） | 是，改动三 |
| `deleted_urls` 元组消费后不清理，累积到 500 条触发近 90 天全量重建 | 中（周期性浪费） | 是，改动四 |
| 会重定向的书签在账本里永远是 0 次 | 高（用户可见，结果错误） | 否，见第七节，待决策 |

四项改动合计约 30 行，涉及 2 个文件。改完后用户看到的交互完全不变。

**明确保留的现有行为**：页面打开后在空闲时预热搜索索引与浏览统计账本。这是刻意设计，本方案不动它，只让预热在「无变化」时不再写盘。

## 三、改动明细

### 改动一：`releaseMemory()` 不再写出空账本

**问题**：`flushSavePending()` 发起的写入是异步的，真正序列化发生在 `persistWriteChain` 的下一个微任务里。`releaseMemory()` 在调用它之后立刻同步把 `archiveMap`、`recentDayBuckets`、`variantsMap`、`knownTargets` 置空，于是写进 IndexedDB 的是空账本，且带着新的 `lastSyncTime`。

**触发条件**：`search.js` 的 5 分钟 `releaseSearchMemory` 定时器，恰好落在一次 500ms 防抖保存的窗口内（例如刚右键文件夹「信息」触发了对账，或刚新建书签完成补种）。

**实测**：复现后天桶 24 行 → 0，`knownTargets` 3403 → 0，`variants` 22 → 0。

**后果**：下次加载会把所有书签当成新增，近 90 天自动重建；但 `archiveMap` 里 90 天以前的累计次数拿不回来。

**改法**（两处，共约 6 行）：

1. `flushSavePending()` 传一份浅拷贝，保住各 Map 的引用：

```js
function flushSavePending() {
    if (!saveDebounceTimer) return;
    clearTimeout(saveDebounceTimer);
    saveDebounceTimer = null;
    const detachedState = { ...internalCache };
    persistSnapshotNow(detachedState, {
        expectedSavedAt: detachedState.lastKnownSavedAt,
        requireDataMutation: true,
        allowPeerRealign: false
    }).catch(() => {});
}
```

2. `persistSnapshotNow()` 在 `buildSnapshotPayload` 之前加一道守卫，账本结构不完整时一律不写：

```js
if (!(targetState.archiveMap instanceof Map) ||
    !(targetState.recentDayBuckets instanceof Map) ||
    !(targetState.knownTargets instanceof Set)) {
    return false;
}
```

第 1 处让待写的数据真正落盘，第 2 处保证以后任何路径都写不出空账本。

### 改动二：数据无变化时不写盘、不广播

**问题**：对账结束后只要水位线前进就整包写一次，而水位线每次对账都会前进。写之前还要先整包读一次比对 `savedAt`。写完广播 `stats-snapshot-saved`，其他实例被标记 `staleByPeer`，下次聚焦绕过 30 秒节流再跑一遍、再写一遍。

**实测**：

| 场景 | 现状 |
| :--- | :--- |
| 聚焦搜索框，距上次同步超过 30 秒，数据零变化 | 整包读 + 整包写 206KB + 广播 |
| 双开，A 同步 2.6 秒后 B 聚焦 | B 仍跑全流程并再写、再广播 |
| 打开页面空闲预热 | 约 1.0 秒后同样整包写一次 |

206KB 里真正的桶数据只有 24 行，其余主要是 3403 个 `knownTargets`。

**改法**（1 个常量 + 改 1 个条件）：纯水位线推进最多每小时落盘一次。

```js
const WATERMARK_PERSIST_INTERVAL_MS = 60 * 60 * 1000;
```

`reconcileLoadedState()` 第 1912 行的分支改为：

```js
} else if (result.nextSync - (internalCache.lastPersistedSyncTime || 0) >= WATERMARK_PERSIST_INTERVAL_MS) {
    saveSnapshotToStorage(internalCache, { immediate: false });
}
```

**为什么安全**：
- 数据或白名单有变化时走的是上面的立即落盘分支，不受影响。
- 内存里的 `lastSyncTime` 照常前进，30 秒节流不变。
- 落盘的水位线最多滞后 1 小时，下次冷加载的增量窗口从「24 小时」变成最多「25 小时」，增量是按天幂等覆写的，结果一致。
- 对端加载快照后会继承 `lastPersistedSyncTime`，不会接着再写，互相击穿自然消失。

### 改动三：只有命中账本的删除才触发对账

**问题**：`hasUnprocessedDeletionSignal()` 只比较时间戳，不看被删的 URL 是否与书签有关。Chrome 的 90 天自动过期也会触发 `onVisitRemoved`，所以后台几乎每天都有信号。

**实测**：删除 1 条与书签无关的历史后，下次聚焦（距上次同步仅 1.3 秒）仍跑了 `getTree` + `history.search` + 整包写 + 广播。

**改法**（改 1 个函数 + 1 个调用点）：

```js
function hasUnprocessedDeletionSignal(stored, lastSyncTime, state = internalCache) {
    if (!stored || typeof stored !== 'object') return false;
    const syncTs = Number(lastSyncTime) || 0;
    if ((Number(stored[STORAGE_KEY_PURGED_AT]) || 0) > syncTs) return true;
    if ((Number(stored[STORAGE_KEY_OVERFLOW_AT]) || 0) > syncTs) return true;
    const deletedUrls = stored[STORAGE_KEY_DELETED_URLS];
    if (Array.isArray(deletedUrls)) {
        for (let i = 0; i < deletedUrls.length; i++) {
            const item = deletedUrls[i];
            if (!Array.isArray(item) || (Number(item[1]) || 0) <= syncTs) continue;
            const canonicalUrl = normalizeHistoryUrl(item[0]);
            if (canonicalUrl && hasLedgerEntry(state, canonicalUrl)) return true;
        }
    }
    return false;
}
```

三个调用点里，第 2030 行和第 2650 行用默认的 `internalCache`；第 2064 行（冷加载判断 `cleanSignals`）此时内存还没就绪，要显式传入 `snapshot`。

**为什么等价**：账本里没有记录的 URL，对账管线在「情况 C」里本来就会跳过（`!hasRecent && maxLastVt === 0`）。这里只是把同一个判断提前，省掉整条管线。

### 改动四：后台裁剪已消费的删除元组

**问题**：`canvas_history_deleted_urls` 由后台写入、前台只读。后台只在「清空全部历史」或「溢出」时才清理它，已被前台处理过的元组永远留着。累积到 500 条就会写 `overflow_at`，前台随即清空近 89 天天桶并做一次 90 天全量重扫。

**实测**：元组被对账消费后仍留在 storage。累积到 500 条触发溢出这一步是按代码推断的，没有实测。

**改法**：前台落盘成功后写一个「已同步到哪」的小键，后台下次 flush 时据此裁剪。

前台（`history_stats_service.js`，约 5 行加一个 set 小函数）：

```js
const STORAGE_KEY_SYNCED_AT = 'canvas_history_stats_synced_at';

// persistSnapshotNow() 内，saveBookmarkVisitStats 成功之后
storageLocalSet({ [STORAGE_KEY_SYNCED_AT]: payload.meta.lastSyncTime });
```

后台（`background.js` 的 `flushCanvasHistoryRemovedEvents()`，3 行）：

```js
const CANVAS_HISTORY_STATS_SYNCED_AT_KEY = 'canvas_history_stats_synced_at';

const stored = await storageLocalGet([
  CANVAS_HISTORY_DELETED_URLS_KEY,
  CANVAS_HISTORY_OVERFLOW_AT_KEY,
  CANVAS_HISTORY_PURGED_AT_KEY,
  CANVAS_HISTORY_STATS_SYNCED_AT_KEY
]).catch(() => ({}));

const resetCutoff = Math.max(
  Number(stored?.[CANVAS_HISTORY_PURGED_AT_KEY]) || 0,
  Number(stored?.[CANVAS_HISTORY_OVERFLOW_AT_KEY]) || 0,
  Number(stored?.[CANVAS_HISTORY_STATS_SYNCED_AT_KEY]) || 0
);
```

现有的 `ts > resetCutoff` 过滤会自动丢掉已消费的元组，不需要新写裁剪逻辑。

**为什么安全**：
- 每个键只有一个写入方：前台只写 `synced_at`，后台只写 `deleted_urls`，不存在页面和后台互相覆盖。
- 元组时间戳不大于「已落盘的 `lastSyncTime`」，意味着任何实例之后加载的快照都已经处理过它。
- 这个小键的写入频率等于快照落盘频率，所以必须和改动二一起上；否则每次聚焦都会触发一次 `storage.onChanged`，顺带唤醒后台。

## 四、用户侧行为对照

| 用户操作 | 改前 | 改后 |
| :--- | :--- | :--- |
| 打开标签页或侧边栏 | 空闲时预热账本，并整包写盘 | 空闲时预热账本，无变化不写盘 |
| 聚焦搜索框、输入、`@热度`、`@最近` | 结果即时 | 不变 |
| 反复开关侧边栏、反复聚焦 | 每次超过 30 秒都写 206KB | 无变化时每小时最多写一次 |
| 标签页和侧边栏双开 | 一端同步，另一端被迫重跑并重写 | 一端无变化同步，另一端不受影响 |

| 右键书签或文件夹「信息」 | 即时 | 不变 |
| 搜索关闭 5 分钟后释放内存 | 小概率清空账本 | 不会 |

没有任何一项改变用户的操作方式或看到的结果。

## 五、风险与已知边界

| 项 | 说明 |
| :--- | :--- |
| 水位线滞后 | 落盘水位线最多滞后 1 小时，冷加载增量窗口相应变大，开销可忽略 |
| 相关删除但数据未变 | 极少数情况下，命中账本的删除对账后数据没变、因此没落盘。之后 1 小时内的冷加载会走「先对账再返回」而不是「秒读快照」，首搜慢几十毫秒 |
| 已有的窄竞态（本次不处理） | 后台元组的时间戳取自 flush 开始时刻。若前台恰好在后台「取时间戳」和「写入 storage」之间的几毫秒内读取信号，这条元组会被漏掉。现状就存在，本方案不加重也不修复 |
| 未实测部分 | 「清空全部历史」和「超过 500 条溢出」两条路径只读了代码；大历史库下的耗时没有测 |

本方案自身没有发现严重风险：四项改动都是收紧条件或补守卫，没有新增状态机，也不改数据格式，不需要迁移。

## 七、待决策：重定向书签计数为 0

**现象**：书签地址如果会跳转到另一个地址（登录跳转、`/` 跳 `/home`、短链），搜索列表、`@热度`、`@最近` 里它永远是 0 次，而右键「信息」能显示真实次数。本机 24 个有访问的书签里有 2 个是这种情况。

**原因**：账本靠 `history.search` 筛出「哪些书签被访问过」，而 Chromium 的 `GetVisibleVisitsInRange` 只返回重定向链末端的访问。`getVisits` 则返回全部访问。

**为什么没放进本方案**：它不是一个小改动，而且要部分恢复 `f74b68e` 砍掉的「对未命中书签逐个调 `getVisits`」。

**最小做法**（估计 40–60 行）：
1. 冷构建和新书签补种时，对 `history.search` 没命中的白名单书签，按原始地址分批直查 `getVisits`，查到的写入天桶。
2. 把这批「只能直查」的规范化地址记进快照的一个小列表，每次增量对账时一并直查。
3. 新出现的重定向书签，靠每天第一次空闲预热时的一轮补查发现。

**成本参考**：本机实测 935 次 `getVisits` 耗时 36ms。按这个比例，3400 个书签约 130ms；放进空闲预热分批执行应该不卡，但这一点没有实测，大历史库下也没测过。

**不做的代价**：最常用的那类书签在 `@热度` 里排在最后，且与右键「信息」的数字对不上。

## 八、明确不做

| 项 | 原因 |
| :--- | :--- |
| 页面打开时不预热 | 空闲预热是刻意设计 |
| 用 `storage.onChanged` 接收删除信号 | 只省一次 storage 读取，却要多维护一个脏标记 |
| 用 `navigator.locks` 重写多实例并发 | 属于重写；改动二之后互相击穿基本消失 |
| 冷态右键文件夹改走账本 | 有空闲预热后冷态右键很少见，本机 1066 个叶子也只要 36ms |
| 清理死代码（`RECENT_REBUILD_DAYS`、`peerLatestSavedAt`、`getDomainStats` 等） | 与本次目标无关，可单独做 |
