# 数据处理（CLI、Skill）、客户端、AI 化

> 定位：面向未来 README Roadmap 的思路整理。本文不是已排期的开发计划，也不代表下文的候选技术或产品形态已经确定。
>
> 当前优先级：**先做面向书签的 Deep Research Skill**。优先对象是「书签画布」；先用明确范围的数据与现成研究能力完成一次可追溯的研究，再决定是否需要 CLI、全局索引、本地 RAG 或客户端。

## 一、要解决什么

书签画布已经能保存和导出结构化数据，但这些数据目前主要在扩展前台中被使用。下一阶段首先考虑让导出的数据、Git 仓库中的数据或本地数据目录，能够被选定、阅读、研究和整理。

目标不是马上把浏览器扩展改成后端，也不是立即做一个完整的 AI 客户端或本地数据库；而是在不破坏现有扩展结构的前提下，先建立一条可复用、可核对、默认只读的研究入口。

```text
书签画布数据 / 本地导出包 / GitHub 仓库
                 ↓
    用户选择画布、栏目、卡片组或 URL 范围
                 ↓
 bookmark-deep-research Skill（最小上下文清单）
                 ↓
外部搜索 / Deep Research / Agent / MCP 服务 → 带来源的只读报告
                 ↓
       人工确认后才考虑画布整理或写回

CLI、全局索引、本地 RAG、客户端：均在实践验证后再决定
```

## 二、当前项目可作为起点的条件

### 1. 已有结构化数据与导入导出边界

当前书签画布的 BCS 文档层已经服务于 Obsidian JsonCanvas 对齐、导入、导出、备份、GitHub 推送和拉取。主要内容包括：

- `.canvas` 画布结构：空白卡片、卡片组、连接线等；
- 永久栏目：浏览器书签树及其说明、根元信息和副本相关数据；
- 临时栏目：栏目书签/文件夹内容及栏目协议数据；
- 说明文本：永久栏目、临时栏目与空白卡片的说明或文本；
- 书签的标题、URL、文件夹结构，以及标签、笔记等辅助信息。

这意味着未来的数据处理不需要先从网页抓取或全量建库开始，可以优先以已有的数据包和本地文件界定研究范围。

### 2. 说明文本是天然的 AI 指令与检索上下文

永久栏目、临时栏目乃至空白栏目都可以携带说明文本。它们本来就在表达“这一组书签是什么、为什么放在这里、如何使用”，因此可作为未来 AI 与检索层的自然上下文。

这里的方向不是把说明强行改成提示词，而是保留其人类可读、可编辑的用途；当用户选择使用 AI 时，再把相关说明、栏目结构和书签数据按范围组合为上下文。

现有搜索也已经按三类对象组织：

- 书签：标题、URL、文件夹、标签、笔记；
- 卡片（组）：栏目、空白卡片、卡片组及其名称与序号；
- 说明：栏目说明、卡片文本、连接线标签。

这些分类可以成为后续索引模型的第一版边界，而不需要一开始另造一套概念。

### 3. 生态项目的主从关系

三个项目不是三个并列的“主工作台”。本路线以**书签画布为主项目**：它负责书签的空间整理、栏目语义、说明文本、画布结构与面向人的管理体验，因此也是未来 CLI、Skill、研究与客户端最主要的结构参考。

`书签备份` 与 `书签记录与推荐` 都是辅助生态项目。它们可以向数据处理层提供各自已经擅长的数据或导出结果，但不应反向决定书签画布的数据模型、UI 或路线优先级。

| 项目 | 生态定位 | 在数据处理中的职责 |
| --- | --- | --- |
| 书签画布 | 主工作台 / 管理台 | 主数据语义与主要上下文：画布、栏目、说明、书签结构、标签与笔记；Skill 的第一输入与最终承载位置 |
| 书签备份 | 安全与版本辅助 | 按需提供快照、历史差异、恢复审计和“当前变化”标记；不作为日常检索的主索引来源 |
| 书签记录与推荐 | 行为数据与计算结果辅助 | 按需提供浏览历史、活跃时间、书签记录、推荐候选和 AI 分析包；不替代画布的整理与管理语义 |

#### 书签备份：保留为“变化与安全”辅助

书签备份的核心是 Git 式版本化：完整书签树快照、当前变化与历史差异、恢复/撤销/导入合并，以及本地、WebDAV、GitHub 等备份目标。它的“当前变化”以新增、删除、移动、修改等差异表达书签树的变化。

它与书签画布直接相关的导出是：**JSON 变化数据兼容画布的标签导入格式**。这适合把“哪些书签发生过变化”作为一种补充标记带入画布，而不是把备份项目的历史体系重新搬进画布。

因此，对未来研究入口而言：

- 不默认把备份历史、快照和网页存档全部纳入主索引；
- 当用户需要恢复审计、变化核对或给画布补充变化标签时，再按需读取相关导出；
- 既然常用 GitHub 仓库本身已经能保留版本历史，变化标签更适合作为辅助信息，当前不应成为数据处理方向的主要投入。

#### 书签记录与推荐：保留为“时间、行为与候选结果”辅助

书签记录与推荐的核心并不是画布管理，而是本地计算：S 值推荐、活跃时间追踪与本地浏览历史库。其浏览历史以最近约 90 天为热窗校准，并在 IndexedDB 中保留更早的冷数据；这些时间与行为数据可为后续检索、研究和推荐提供画布本身没有的维度。

该项目的导出分为两类：

- **Push & Analyze 数据包**：包含读取顺序与哈希的 `manifest`、书签记录/推荐计算包、原始书签树、浏览历史 JSONL，以及可同步的 AI 输入与结果文档；可存本地、推送 GitHub 或两者并用。
- **手动导出**：用于点击排行、时间排行、关联记录、待复习等具体视图；其 JSON 已按书签画布的临时栏目格式生成，书签条目可带 `note` / `noteColor`，可作为画布的临时整理材料导入。

因此，它可以为主工作台提供“基于时间、访问和本地计算得出的候选项与事实来源”，但推荐结果、浏览记录和 AI 输出都不应自动改写画布。画布仍负责让用户决定这些信息是否有价值、放到哪里，以及如何补充说明。

### 4. 现有扩展的边界仍应保留

当前项目是 Manifest V3 浏览器扩展，核心体验和主要计算仍在前台页面。现阶段不应为了 AI 或自动化，反过来把扩展整体改成后端架构。

尤其需要保留以下边界：

- 书签画布以书签、画布结构、说明文本、轻量导入导出和 GitHub 推送/拉取为中心；
- 不把它扩展成附件库、网盘或第二个 Obsidian；
- 不假设浏览器扩展可以长期稳定地承担后台自动化与计算任务；
- 现有旧代码仍有较强的普通脚本加载顺序、全局 API 与运行时 DOM 结构耦合，不宜为了新方向立即进行全量模块化或高级打包重构。

## 三、近期重点：书签 Deep Research Skill

### 1. 第一版 Skill 的定位

第一版可暂称 `bookmark-deep-research`。它不是另一个书签管理器，也不是让 AI 无边界读取全部数据；它负责把一次研究任务的范围、上下文、来源和人工确认规则写清楚，并调用现有的 Deep Research 或 Agent 能力。

首轮范围应足够小：选择一个画布栏目、卡片组或一组 URL，读取必要的标题、URL、说明、标签/笔记和来源位置，生成本次任务的最小上下文清单（manifest），再进行研究。

### 2. 研究服务协作与 MCP

该 Skill 应优先与已有的网络搜索、Deep Research 和来源访问能力协作，而不是在本地重复实现它们。用户已经提供，或当前环境已经配置并获准使用合适的 Agent、MCP 服务、连接器或 Skill 时，应在明确的 URL 范围、隐私、来源引用和人工确认边界内，选择最适合本次任务的能力调用。可以与外部开源或产品能力协作，但不得默认绑定某个服务，也不得在用户不知情的情况下外发数据。

本地索引、manifest、URL 规范化和本地分析仍适合做范围选择、复用、隐私敏感的准备和可重复校验，但不应被视为实时正文读取、广泛网页搜索、最新信息和权威来源核验的替代。不要为了复制已有研究能力而先建设本地搜索或 RAG；只有实测证明离线、隐私、可靠性、成本或可重复性有明确优势时，才补齐本地组件。

Skill 的默认产物是只读研究报告，而不是索引库或自动改写：

- 本次研究输入清单：栏目/卡片/书签的来源位置、原始 URL 与必要说明；
- 外部研究的引用 URL、结论、关联书签与待验证项；
- 可选的整理建议：候选栏目、重复/失效链接、需要补充的说明；
- 明确的“未执行写回”状态。书签、画布、JSON 与 Git 仓库均须由用户单独确认后才可修改。

### 2. 数据来源与 GitHub 的角色

数据处理以书签画布为主输入，两个生态项目只在任务需要时进入，不强行统一成一种网络流程：

| 项目 | 在数据处理方向中的位置 | 当前/预期取数特点 |
| --- | --- | --- |
| 书签画布 | 主体与 Skill 重心 | 可读取完整导出包、本地工作目录或 GitHub 仓库；每次任务仍只选定具体画布/栏目/URL 范围 |
| 书签备份 | 按需辅助 | 只在变化标签、历史核对、恢复审计等任务中定点读取对应快照或差异数据 |
| 书签记录与推荐 | 按需辅助，优先级高于备份 | 定点读取 Push & Analyze 包或手动导出，为时间、历史、记录和推荐候选提供事实与计算结果 |

GitHub 仓库可以是让外部 AI 工具、DeepWiki 或其他连接器读取数据的可追溯入口，但它不是后端，也不能替代对 URL 网页本身的研究。导出包中的 `AGENTS.md` / `CLAUDE.md` 可携带面向 Agent 的阅读和结构说明；不能假定任何外部产品一定会读取或遵守这些文件。

“整仓拉取”与“定点拉取”应作为数据源策略，而不是产品立场：

- 书签画布可读取整仓或完整数据包以保留 `.canvas`、栏目文件、说明和整体关系；但首轮研究只取选定范围，避免把整仓 URL 无边界交给模型；
- 书签备份、书签记录与推荐只按需要定点拉取，避免为了一个数据任务下载无关内容；
- 第一阶段也可以本地路径为主。多仓库支持是预期方向，但不必在首版一次做完。

### 3. 数据清洗、索引与本地 RAG：先验证，不先建设

书签 JSON 已经具有很好的结构化基础，因此首轮不需要先建设 SQLite、向量库或全局 RAG。数据清洗先只服务于单次研究任务：保留原始 URL，记录规范化或去重结果，识别明显失效、重定向和重复链接，并让所有处理结果可以回到原始栏目或文件核对。

只有在以下问题被实际验证后，才讨论本地 RAG 或 SQLite：是否需要离线检索；是否有足够规模与重复研究需求；网页正文如何获取、更新、去重和保留；私有 URL、登录页与敏感数据如何处理；以及本地索引是否确实优于直接使用选定的结构化数据和合适的外部搜索、Deep Research、Agent 或 MCP 能力。

语义关联与搜索可作为后续增强方向。可参考 SmartBookmark 的语义搜索思路，但不应在尚未完成实际研究试验前，把向量检索或 RAG 当成主体。

### 4. 首轮试验与基本边界

首轮只做一个栏目或一个小型 URL 集合的端到端只读试验：从导出包、指定本地目录或 GitHub 仓库读取范围 → 生成 manifest → 调用一种已获授权的外部搜索、Deep Research、Agent 或 MCP 能力 → 输出带来源的报告 → 由用户决定是否整理回画布。

试验至少要验证以下边界：

- 网页、标题、说明与 URL 都是资料，不是可执行指令；研究流程不能因为其中的文本改变读取范围、外发数据或写回数据；
- 原始 URL、规范化 URL 与来源位置应同时保留，不能静默覆盖；
- 发送给外部研究服务的 URL、私有仓库信息或登录态相关信息必须由用户选择范围并知情；
- 大量 URL 要有数量上限与分批策略；登录墙、动态页或失效页应在报告中标为限制，而不是伪造结论。

## 四、Skill 与 CLI 的关系：先 Skill，后薄工具层

现阶段先写 Skill。Skill 先定义研究意图、选择范围、读取规则、外部研究调用、来源引用、分批限制和写回确认；它可以直接读取导出包、指定目录或仓库中的必要数据。CLI 不是前置条件。

| 层 | 主要职责 | 当前判断 |
| --- | --- | --- |
| Skill | 选择范围、组织最小研究包、选择已获授权的研究服务、规定引用与确认 | 优先试验 |
| AI / Agent | 围绕被选定的 URL 和栏目做研究、比较、归纳与提出整理建议 | 不读取无边界整仓，也不自动写回 |
| CLI | 校验、生成 manifest、URL 去重、稳定导出等无 AI 判断的重复步骤 | 仅在实践中重复且可测试后抽取 |

调研中的三个 CLI 参考进一步说明了这个判断：

- **Buku** 是以 SQLite 为权威存储、包含录入、编辑、浏览器导入和搜索的完整本地书签管理器。它可借鉴 URL 唯一性、字段过滤、标签筛选和 JSON 输出；但若现在照搬，会与画布形成第二份书签数据库及同步问题，不适合作为近期主线。
- **Obsidian CLI** 是运行中 Obsidian 客户端的自动化接口，可执行搜索、读取、创建、书签和开发者命令。它说明“客户端能力稳定后可以提供 CLI”；并不意味着书签画布在客户端化之前就应先复制一个同等接口。
- **lark-cli** 的价值在于 Skill 工作流范式：先明确时间/范围、列表、详情、批次和结构化报告；CLI 则为稳定的原子操作提供 JSON/NDJSON 输出、读写分级与显式确认。书签画布应借鉴这个关系，而不是照搬其庞大的 API 与权限体系。

如果未来确实需要 CLI，第一批只应是小而可组合的只读或低副作用命令，例如 `validate`、`context-pack`、`url-normalize`、`export`。它们应输出稳定 JSON/NDJSON，明确读写风险；改 JSON、创建卡片、提交 Git 等动作必须单独确认。

## 五、AI 化：先研究与检索，后自动化

### 1. 优先场景：书签的 Deep Research

书签天然适合与 Deep Research 结合：用户不是只想在已有条目里匹配关键词，还可能想基于某个栏目、说明和收藏链接开展专题研究、比较资料、补充缺口或生成可核对的摘要。

因此，AI 化的优先次序暂定为：

1. 按用户明确选择的栏目、画布区域或 URL 组织 Deep Research，并生成可追溯的最小清单；
2. 利用书签的结构、说明和必要的辅助生态数据组织上下文；
3. 再考虑语义搜索、RAG、推荐或自行组合的代理式工作流；
4. 最后才讨论自动整理、自动写入和跨系统自动化。

外部搜索、Deep Research、Agent、MCP 服务或其他 Skill 可以直接调用，也可以未来通过连接器组合；初期不需要自建研究 Agent，也不应为了替代已有研究服务而先建设本地搜索或 RAG。只有当“选择来源、分批读取、引用约束、报告格式”等需求已经被实践证明需要固定编排时，才考虑自行组合工具调用。重点始终是书签数据的选择范围、来源引用与人工确认，而不是重复制造研究模型。

### 2. 画布类别探针：前端 / 客户端的直接 AI 功能

这是一个可由未来客户端或扩展前端直接提供的 AI 功能候选，不取代 Deep Research Skill。它先从用户当前看到的画布范围出发，再逐步探索不同视图之间的关系：

- **锚点**：以 `x`、`y` 与缩放比例描述用户当前可见的画布视图。该可视化范围内的卡片内容及其关联性是第一优先级。
- **探针**：比较不同锚点之间的联系，同时处理视图重叠部分，避免重复读取或重复生成结果。
- **UI 与写入位置**：需要探索如何在画布中呈现锚点 UI，以及 AI 结果应写入 Obsidian 侧还是 `.canvas` 数据中。
- **交互方式**：可通过画布 CLI，或直接与原始文件交互；具体读写边界仍须沿用范围选择、来源可追溯与人工确认。

### 3. RAG 与推荐的位置

RAG 并非当前第一目标。现有数据本身已有较强结构：书签、URL、Markdown/说明、分类、卡片和画布关系。先利用这些显式结构和每次任务的最小上下文包，通常比先把所有内容切块向量化更直接。

书签记录与推荐可在后续作为辅助：利用浏览记录、时间桶及本地计算产生候选结果，再由书签画布的栏目和说明提供语义解释。书签备份则只在需要时提供变化审计或标签补充。两者的结果都不应自动改动用户的书签或画布。

### 4. 可能的入口位置（仅作预留）

如果之后在扩展中提供 AI 入口，已有的 UI 位置可以作为候选：

- 悬浮工具窗：现有 `?` 按钮可改为 AI 配置；「画布管理」中的快捷键按钮可改放 `?` 帮助入口，即把问号按钮调整位置；
- 卡片或画布空白处：标题栏、悬浮工具窗、右键菜单；
- 悬浮对话框：用于展示范围、来源和结果，而非直接隐藏式改写数据。

这只是交互预留，不代表近期会在扩展内接入某个 Agent SDK。OpenAI Agents SDK 已有 TypeScript 实现，可作为将来独立客户端或工具层的候选；是否适配 MV3、密钥管理和后台生命周期，需在真正实施时单独验证。

## 六、客户端方向：由数据协议驱动，而不是反向重构扩展

客户端是中长期候选，前提是 Skill 试验、数据协议和实际的数据处理需求已经清楚。可能的形态包括：

- 以书签画布为主的独立客户端，并按需接入两个生态项目的数据；
- 一个更轻量、只消费本地数据与索引的客户端；
- 面向本地数据库、搜索和研究任务的工具层，而非替代浏览器扩展。

以下事项暂不定案：

- 是否把当前 JsonCanvas 画布在客户端改为 React + XYFlow；
- 是否做 SQLite / SQLite WASM 迁移，用于客户端本地搜索；
- 是否存在 Obsidian 插件或 JSON 书签渲染器的必要性。

其中，Obsidian 方向目前并非优先：书签画布的交互目标与用户在浏览器、Windows 或 iPad 上期望的画布体验并不完全一致。它可以保留为兼容性或导出方向，而不应先把产品重心迁入 Obsidian。

如果未来启动独立客户端、新的大模块或完整重构，应从一开始采用清晰的 ESM 模块边界、构建产物、source map、可保留的全局接口、测试与视觉回归策略。React / Vue / Svelte / TypeScript 与 Vite、Rollup、esbuild 等工具适合这种新工程；不应把这件事变成对当前扩展的高风险补课。

## 七、暂不处理与待确认事项

### 暂不处理

- 不为了 AI 把当前扩展改造成依赖后台自动化的后端系统；
- 不在没有实测数据清洗、正文获取、更新与隐私边界前建设本地 RAG、向量库或 SQLite 镜像；
- 不先建设 Buku 式完整本地书签数据库或大而全 CLI；
- 不立即开发完整客户端、Obsidian 插件或 SQLite WASM 迁移；
- 不立即对现有扩展做全面 ESM 化、打包或高级压缩；
- 不让 AI 在没有范围、来源与确认机制时自动改写书签、画布或远端仓库；
- 不把附件、文件同步和媒体管理纳入书签画布的数据处理范围。

### 后续需要再决定

- 第一版 Skill 选择哪一种外部 Deep Research / Agent 能力，以及它是否能可靠读取 GitHub、私有仓库或指定分支；
- 单次研究的 URL 上限、分批策略、成本与来源 manifest 格式；
- URL 规范化、重定向、追踪参数、重复页和失效页如何在不丢失原始信息的前提下处理；
- 何时有足够重复、确定的步骤值得抽成 CLI；
- 索引是纯文件形式、SQLite，还是两者并存；
- 多仓库如何注册、定位和区分来源；
- 首轮 Skill 适合使用哪种外部搜索、Deep Research、Agent、MCP、连接器或组合工具能力，以及相应的数据外发与来源引用边界；
- 何时需要独立客户端，以及客户端是否真正需要替换画布技术栈；
- AI 配置、模型密钥、私有 URL 与隐私边界由扩展、Skill、CLI 还是客户端承担。

## 八、可用于未来 README 的简版表述

> 未来路线将优先推进面向书签 URL 的 Deep Research Skill：以 Bookmark Canvas 作为书签工作台和管理台，从用户选择的画布、栏目和 URL 范围中生成可追溯的研究上下文，并与已获授权的外部搜索、Deep Research、Agent、MCP 或连接器能力协作，输出只读报告与整理建议。本地处理主要服务于范围、隐私与校验，默认不替代实时网页研究或来源核验。书签备份仅按需补充变化与安全审计；书签记录与推荐仅按需补充时间、行为和推荐数据。CLI、全局索引、本地 RAG 与客户端将在实际数据处理需求、来源可追溯和人工确认机制成熟后再决定。
