## 1. 先锁死三条边界
- 永久栏目主内容：继续以 Chrome bookmarks API 为真相源，不改成插件自存整份 md。
- 空白栏目：改成 Markdown-first，`markdownSource` 是正文真相源，`html` 只留运行时渲染态。
- `.canvas`：对齐导出的节点层；`file` 节点不内嵌正文，原生 `text` 节点保留 Obsidian 语义。
- 空白栏目 / `.canvas`：这一轮要收敛正式存储模型，不只是补临时缓存层。
- 永久栏目：这一轮继续保留 Chrome bookmarks API 真相源，只补“规范化快照 / 协议视图服务”，不等于新增一份持久化中转真相源。
- 临时栏目：这一轮先补“协议中转层 / 协议缓存层”，不等于立刻重写全部运行时结构。

### 1.1 顺序边界补充
- 在真正进入第 7 步 `JSON模式（供AI）` 之前，不提前改现有本地存储的顶层结构。
- 在真正进入第 7 步 `JSON模式（供AI）` 之前，不提前改现有 `visual / visual-no-icon` 的文件顶层、正文外壳与现有导出格式。
- `obsidianExportFormat` 扩成 `visual / visual-no-icon / json`，以及 `json` 的默认值、候选框、说明文案、解析入口，统一放到第 7 步处理，不前置到前几刀。
- `bookmarkTree / meta(sectionMeta)` 这类 JSON 正文顶层字段，只在进入 `json` 模式实现当次锁死，不作为前面几刀的前置阻塞。
- 全量备份旧导入路径、旧恢复分支，本轮不额外为新结构追加兼容逻辑；未来如要清理，可单独成刀。
- 当前项目尚未发布，不为已下线编辑模式、未来将删除的旧结构额外保留兼容成本。
- 如果某一刀的前提是“先删除旧实现，再接入新实现”，则后续实现直接以删除后的新结构为准，不再反向补旧路径兼容。
- 但“可以不保留旧兼容”不等于“可以直接硬删旧实现”：删除前必须先查清旧实现关联了哪些函数、解析入口、存储键、DOM 标识、事件绑定与调用方。
- 凡是仍被其他模块依赖的旧入口，要么同一刀一起改掉调用方，要么在新实现上保留等价入口，避免误删导致别的功能连带损坏。

## 2. 第一刀：先补协议对象层（已有实施计划，可直接作为当前实施参考）
- 临时栏目先补一层规范化协议对象。
- 永久栏目先补一层规范化快照 / 协议视图服务。
- 空白栏目、`.canvas` 也允许有协议对象，但它们更重要的是先收敛正式存储模型。
- 这层专门给导入、导出、同步、比较使用，不直接等于 DOM，也不直接等于旧运行时对象。
- 目标是把“同步时临时抽取再解析”改成“平时就有一份可复用的协议快照 / 缓存”。
- 这一刀更偏“边界冻结 + 最小读侧协议对象 + 适配器入口”，不要求先把永久栏目、临时栏目的全部运行时写侧都切到新层。

### 2.1 为什么需要协议中转层
- 现在的文件级命中本身已经可以按路径精确挑文件；真正重的是远端拉取后再做正文解析、树重建、整包应用。
- 没有协议中转层时，导入、导出、同步都要临时从运行时对象重新抽结构，再各自解析 / 拼装一轮。
- 永久栏目和临时栏目当前运行时结构都不适合直接承担稳定的导入导出协议职责，但两者来源不同：永久栏目靠 API + 快照，临时栏目靠 `items` + 适配层。
- 协议中转层的核心价值不是“再造一份真相源”，而是给导入、导出、同步、比较一份稳定、可复用、可缓存的统一对象。

### 2.2 协议中转层 vs 直接拉取解析
- 协议中转层的优点：导入、导出、同步都能直接对统一对象操作；重复解析和重复拼装明显减少；更容易支持临时栏目 `json` 链路与后续 AI 改动；不要求 `visual / visual-no-icon` 也长期切到这层。
- 协议中转层的缺点：要多维护一层缓存 / 快照；要解决失效、刷新、回写时机；如果边界没定清楚，容易出现“运行时结构一套、协议层一套”不同步。
- 直接拉取解析的优点：实现简单；没有额外缓存失效问题；当前不需要先定义完整协议对象。
- 直接拉取解析的缺点：每次导入、导出、同步都要重新抽结构、重新解析、重新组装；临时栏目和永久副本尤其容易出现多处分支各写各的；越往后接入 `JSON模式（供AI）`，维护成本越高。

### 2.3 当前选择
- 永久栏目：优先补“规范化快照 / 协议视图服务”，因为它的真相源本来就是 Chrome bookmarks API，不应再造一份本地持久化树正文。
- 临时栏目：优先补协议中转层，因为它当前运行时 `items` 和协议表达不是同一件事。
- 空白栏目 / `.canvas`：优先收敛正式存储模型，因为它们本来就更适合直接对齐 Obsidian 文件结构。
- `visual / visual-no-icon`：继续沿用现有导出 / 解析链路，不进入长期协议中转层；真正新增这层的重点，是临时栏目 `json` 链路。
- 换句话说：中转层主要是为临时栏目 `json` 服务；永久栏目更偏“API 真相源 + 快照投影”；空白栏目、`.canvas` 更偏正式模型收口，而不是长期停留在“只靠中转层”。
- 这一刀按 [第一刀协议对象层实施计划](./第一刀协议对象层实施计划.md) 落地。

## 3. 第二刀：空白栏目 + `.canvas`（已有详细执行计划，可直接作为当前实施参考）
- 第二刀不是重做整套 Canvas 运行时模型，而是完成“正文归 `.md`、布局归 `.canvas`、HTML 只做运行时渲染”的边界对齐。
- 先改插件空白卡片，让正文真相源从 `html/text` 切到 `markdownSource`，导出不再依赖 `node.html -> markdown` 临时转换。
- 原生 `text` 卡片继续保留 Obsidian `text` 节点语义，不和插件空白卡片混成同一种正文协议。
- `.canvas` 这一刀重点不是大收口，而是和当前导出结构对齐一次“小边界”：`file / text / group / edges` 的外部语义固定下来。
- 插件内部当前 `tempSections / mdNodes / edges` 运行时桶结构先保留，不要求第二刀立刻改成单一 `nodes[]` 真相源。
- 这一刀按 [空白栏目与.canvas边界对齐执行计划书](./空白栏目与.canvas边界对齐执行计划书.md) 落地。

## 4. 第三刀：永久栏目主栏 / 副本（已有边界子计划与实施计划，可直接作为当前实施参考）
- 目标不是复制 DOM，而是“同一内容源，多视图壳”。
- 主永久栏目和所有副本，都不要各自存一份书签树正文。
- 永久内容源统一为规范化后的 permanent tree snapshot；这里的“快照”指书签树快照，不是 DOM 快照。
- 当前实现本来就已经是“一个内容源，对应多个 DOM”；后续只是从“主树 clone 到副本”收敛为“同源独立渲染”，不是把多个副本改成共享同一个 DOM 实例。
- 每个永久视图只保留：`descriptionMd / scrollState / foldState / cardState`。
- 这一步只统一“书签树内容源”，不是重做副本外壳；现有 `copyId`、标题标签、搜索定位 / 跳转、目录栏定位、导出节点标识、同步识别等外部标识体系都要继续兼容。
- 这一刀先保留现有 `.permanent-bookmark-section` / `.bookmark-tree` / `data-permanent-section-copy-id` 等 DOM 合同与现有 storage key 读写入口，再在内部把“主树 clone 到副本”替换成“同源独立渲染”。
- 文件夹折叠、垂直滚动条、说明、懒惰加载、路径徽章 / 标识系统允许内部实现跟着适配，但外部行为不能退化。
- 统一内容源后，预期会比原来的 DOM 同步方式更稳定、更容易做导出 / 同步 / 比较，但不允许以牺牲现有兼容性为代价。
- 具体结构以 [书签树协议层统一子计划](./书签树协议层统一子计划.md) 为准。
- 实施落点以 [第三刀永久栏目主栏副本实施计划](./第三刀永久栏目主栏副本实施计划.md) 为准。

## 5. 第四刀：临时栏目先补协议层，再谈底层迁移（已有边界子计划，执行前仍需补实现级计划）
- 临时栏目当前可继续沿用现有内部结构，不先硬改全部运行时逻辑。
- 但临时栏目应进入同一套协议中转层，不能继续只在同步时临时抽取。
- `JSON模式（供AI）` 第一版允许临时栏目接入，但先通过 `items <-> bookmarkTree` 适配层实现。
- 等协议层稳定后，再决定是否把 `items` 真正对齐到统一书签树协议。

## 6. 第五刀：导入 / 导出 / 同步（已有多份参考计划，执行前需补一份合并后的实施计划）
- 转换器集中放在导入、导出、同步、协议层解析器。
- 不再让运行时 UI 对象承担导入导出协议职责。
- 导出尽量直接从正式内容模型生成，不再从旧对象临时拼装一大轮。
- `visual / visual-no-icon` 继续沿用原有链路；`json` 才接入新增协议结构与对应解析器。
- 在轮到 `json` 之前，这一刀先服务于空白栏目 / `.canvas` / 永久快照 / 临时协议层收口，不要求提前把现有 `visual` 顶层一起改型。
- 文件级推送 / 拉取本来就支持按路径精确命中，不是每次都盲目全量上传所有文件。
- 当前真正偏重的是：远端正文下载后，协议解析、树重建、`tempState` 应用这一层。
- 四种操作后的颜色标识、路径徽章先继续沿用现有比较链路；批量操作后的批处理优化属于后续性能项，不阻塞这次结构改造。

## 7. 最后才上 `JSON模式（供AI）`（已有主计划与子计划，执行前仍需补实现级计划）
- `JSON模式（供AI）` 与 `visual`、`visual-no-icon` 并列。
- 它是第三种正文投影，不是底层重构起点。
- 适用范围包括：永久栏目、永久栏目副本、临时栏目。
- 其中临时栏目第一版只要求协议层、导入导出、同步链路支持 `json`，不要求立刻替换运行时 `items`。
- 现有“只认 `visual / visual-no-icon`”的设置值、默认值、候选框与回退逻辑，也统一在这一步改成三值，不前置。
- `json` 自己的正文顶层字段、`bookmarkTree / meta` 边界，也统一在这一步定稿并接入实现，不倒逼前面步骤先改现有本地顶层或 `visual` 顶层。
- 首次同步一旦选定模式，后续同步默认沿用该模式；如果中途切换模式，应按“格式迁移 / 重导出 / 本地覆盖云端”处理，不按普通增量同步处理。
- 这一步按 [JSON结构模式最终方案](./JSON结构模式最终方案.md) 落地。

## 8. 存储后端只做收口，不先大搬家
- `chrome.storage.local`：正式主路径。
- `localStorage`：bootstrap、小 UI 状态、轻量 signal。
- `IndexedDB`：恢复包、staging、大缓存、兜底。
- 先定“存什么”，再定“存哪里”，不要反过来做。

## 9. 当前推荐开工顺序
1. 先锁死协议对象边界：永久栏目补规范化快照 / 协议视图服务，临时栏目补协议中转层，空白栏目与 `.canvas` 收敛正式存储模型。
2. 空白栏目 Markdown-first 子计划落地，正文真相源切到 `markdownSource`。
3. `.canvas` 和当前导出结构完成边界对齐，固定布局侧语义。
4. 永久栏目主栏 / 副本统一内容源与视图壳。
5. 临时栏目接入协议层，先把 `items <-> bookmarkTree` 适配层与导入 / 导出 / 同步所需协议入口铺好，再决定是否继续改底层。
6. 导入 / 导出 / 同步切换到新模型，但此时仍不要求现有 `visual` 顶层与设置枚举提前改型。
7. `JSON模式（供AI）` 最后接入；到这一步再统一补 `obsidianExportFormat` 三值、`json` 顶层协议、对应解析器与默认值。

## 10. 后续性能优化项
- 四种操作后的颜色标识、路径徽章，后续改成“批量操作后统一比较 / 统一刷新”，不要求每一步都重跑完整差异计算。
- 侧边栏 / 标签页后续可降级为：前台不强制实时做差异比较，只消费后台已算好的结果。
