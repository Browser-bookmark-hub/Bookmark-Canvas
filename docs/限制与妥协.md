# 限制与妥协

## 限制

### 限制一：卡片直接加载 WebView

❌ **不支持。**

MV3 的 WebView 不支持。除非做 Obsidian 插件，或者在别的 <font color="#ffff00">开源书签管理 app</font> 上去做，或者直接基于 Chrome 引擎开发；但 Chrome 原生现在还不支持垂直标签页。

不做第二个 Obsidian，浏览器环境本身也不支持。

#### 原因

**目标：** 验证在 Manifest V3 插件中，通过「侧边栏」、「Canvas 浏览器卡片」或「分页」形式打开外部 URL 的可行性。

**验证结论：** 功能_技术上_可实现，但_实用性_极低。无论是「侧边栏」、「Canvas 浏览器卡片」还是自定义「分页」，其核心实现均为 `<iframe>`，因此均受同样的安全策略限制，无法可靠加载外部网站。

**核心限制：**

1. **`<iframe>` 限制：** 无论是侧边栏（Side Panel）还是设想的 Canvas 卡片，都只能通过 `<iframe>` 来尝试嵌入外部 URL。
2. **安全策略（CSP / X-Frame-Options）：** 绝大多数主流网站（如 Google、GitHub 等）出于安全考虑，使用 `X-Frame-Options` 或 `CSP` 安全策略，**主动禁止**自己被 `<iframe>` 嵌入。
3. **「分页」问题：** 浏览器没有“侧边栏分页”API。自定义分页功能只是在扩展页面内切换不同的 `<iframe>`，无法解决上述 `<iframe>` 限制。
4. **最终结果：** 用户尝试使用这些功能时，绝大多数情况看到的只是“拒绝连接”（refused to connect）错误。

### 限制二：无法自动命名 Window

无法自动命名「Window」，但是「Group」可以。

Chrome `windows` API 没有设置/读取“窗口名”的字段；MDN 的 `windows.Window.title` 也是只读，本质是窗口显示标题，不提供设置。

参考：developer.chrome.com

✅ **曲线方案：** 使用「书签画布」页面，对 tab 进行命名，并且自动定位当前栏目（生成窗口的栏目）。

### 限制三：无法读取已经关闭的组名

无法针对「已经关闭的组的名次进行读取」。

`chrome.tabGroups.*` 只能访问**当前打开窗口里**仍然活跃的分组；窗口一关，组就不在这个 API 里了。

Session / Sync 数据（包括“已关闭窗口”列表、云端同步的 tab 组）只给 Chrome 内部或登录账户使用，扩展没有接口可以读。

Chrome 确实把关闭的窗口/分组保存到 Session Restore 体系中，但那块数据只对浏览器内建功能开放。扩展能访问的 `chrome.sessions` API 也只提供“最近关闭的窗口/标签列表”，而无法告诉你“这个条目里包含了哪些分组、原名是什么”。这在官方文档和 MDN 上都写得很清楚。

#### 其他

✅ **曲线方案：** 增加一个 tab 页面，直接进行管理：「同窗专属组」、「同一窗口」、「专属窗口」。

系统级别 bug。✅ 只能不要 popup 页面了，唤醒有问题，确认状态丢失。

如果侧边栏在打开的情况下，我们过了一会儿不操作浏览器或者去了其他地方，然后再回来按下快捷键，会发现关不掉，也就是说，第一次按下根本没有任何反应，第二次按下它才会关掉。

### 限制五：Edge 侧边栏刷新与 Chrome 行为不一致

有两个问题：

1. 关于 Edge 浏览器：它虽然没有置顶按钮，但 Chrome 确实有置顶功能，侧边栏的置顶有什么用？
2. 标签页切换问题：为什么我们每点击、每切换一个标签页，侧边栏里面的内容都会刷新一遍？这显得非常奇怪。和「1.」有关联吗？能修复吗？Edge 会刷新一遍，Chrome 一点都不会刷新。

#### Chrome 的做法：单例模式

Chrome 把侧边栏看作一个**全局独立的窗口**。一旦打开，它就成了一个持久存在的页面，切换标签页只是切换了它旁边的“邻居”，侧边栏的 JS 上下文完全没动。

#### Edge 的做法：多实例 / 隔离模式

Edge 为了深度集成它的“侧边栏助手”，默认会为**每个标签页（Tab）尝试创建一个侧边栏实例**。当你切换标签时，Edge 会销毁上一个 Tab 的侧边栏上下文，并重新加载当前 Tab 的侧边栏。

✅ **当前方案：** 用的是壳，用的是 panel shelf。

### 限制六：Windows 离散鼠标输入手感

Windows 的离散鼠标输入感不如 macOS，一格格的不舒服。

✅ 勉强做了曲线优化，但体感还是不如 macOS。

### 限制七：多卡片、多书签渲染导致的闪烁

当前最大的体验限制之一，是多卡片、多书签同时渲染时仍可能出现卡片闪烁。

虽然已经在「性能」相关能力里做了多条曲线优化：

- 低细节模式。
- 视角外低细节。
- 懒惰加载。
- 视野内外虚拟化 / 分批渲染。

这些优化已经大幅改善大画布、大书签树、多卡片场景的可用性；但如果当前视口内元素过多，仍可能因为 DOM 渲染、图标加载、卡片更新和浏览器绘制压力导致闪烁。

这是浏览器扩展 + DOM Canvas 方案的现实限制，不是单个开关能完全消除的问题。当前策略是继续用性能模式、低细节、懒加载和虚拟化降低触发概率，而不是承诺无限量卡片和书签都能稳定无闪烁。

### 妥协二：侧边栏没有捏合缩放

#### 为什么 HTML 标签页可以，侧边栏不行？

- 普通页面里，触摸板捏合通常会映射为 `wheel` 且 `ctrlKey=true`（MDN 明确写了）。
- 但 Side Panel 是浏览器 UI 托管页面（Chrome API 文档），手势在宿主层被处理 / 拦截时，页面就收不到这类“捏合缩放信号”。
- 所以同一套代码在标签页可用，在侧边栏失效。

`Ctrl + 双指滑动`

✅ 后续版本已解决。

### 妥协三：GitHub 不支持单目录打包下载

GitHub 长期以来都有社区需求希望官方支持单目录下载：

https://github.com/orgs/community/discussions/178419

```text
### 1. GitHub 不支持单目录打包下载

GitHub 官方的 `/zipball` 接口设计非常简单，它只接受 `owner`（所有者）、`repo`（仓库）和 `branch`（分支/引用），**无法指定路径**。也就是说，GitHub 的接口不支持“只帮我打包 `remoteRoot` 文件夹”这样的操作。
```

✅ **曲线方案：**

```text
在「默认数据包导入方式」上方给一个勾选选项吧：「拉取数据包方式」

定点拉取法、整仓压缩包法

整仓压缩包法：速度快，但要过滤：永久/临时栏目卡片多，仓库干净，用压缩包
定点拉取法：速度可能慢，但精准：永久/临时栏目卡片少，仓库不干净（尤其是其他大型文件多），用定点拉取
```

### 妥协五：说明框是否换成 CM6

空白栏目卡片（走 `.canvas` 的 `text` 节点）、永久栏目和临时栏目的说明框（`descriptionMd`）这些东西换成 CM6？

可以，但没有必要。

1. CM6 是 Markdown 源码编辑器，不是现有这种 HTML 富文本 DOM 编辑器。CM6 的主数据是文本 document。现在很多工具是直接改 `innerHTML`、选区 DOM、`document.execCommand`、checkbox DOM、`span` 样式。CM6 不能直接吃这些逻辑，需要改成“改 Markdown 文本”或 CM6 extension / decoration。

==Obsidian 官方开发文档和博客都说明编辑器底层是 CodeMirror（现已全面 CM6）== <font color="#548dd4">后期可能换渲染器</font>

但是当前没有必要加入，因为我们的说明框只是展示，有基本渲染能力就够了。

#### 是否加入 Mermaid 渲染支持？

没必要。

我们本来就是在画布里边。要加入 Mermaid 的话，这种渲染器要做的东西还很多，相当于画布中的画布渲染，还会有画布中的缩放、卡片中的缩放，体验可能不太好，纯属没必要。

### 妥协六：不做附件功能

最大妥协之一，是不做附件功能。

这会影响长期能力，尤其是 GitHub 推送 / 拉取场景：如果支持任意附件、图片、PDF、音视频或其他 file 节点，长期数据包会迅速变大，远端目录也会变得难以管理。推送拉取不再只是轻量的画布结构和书签数据，而会变成一个近似文件同步系统。

理论上可以曲线支持其他 file 节点的渲染或引用，但问题会马上变复杂：

- 数据包体积可能巨大。
- GitHub 推送 / 拉取的速度和稳定性会明显下降。
- 远端目录会承担文件仓库职责。
- 文件预览、缓存、更新、删除、冲突和跨设备一致性都需要额外系统。
- 用户可能会期待它像 Obsidian 或网盘一样管理附件。

结论：~~附件功能~~不做。

Bookmark Canvas 不是重做一个 Obsidian 客户端，也不是文件管理器。需要长期管理附件、媒体文件、PDF 或大型资料库时，建议用户使用更适合的工具，把 Bookmark Canvas 保持在书签、画布结构、说明文本、导入导出和 GitHub 轻量推送拉取这个边界内。
