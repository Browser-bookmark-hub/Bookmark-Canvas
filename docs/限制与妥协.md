# 限制与妥协

## 限制

### 限制一：卡片直接加载 WebView

❌ **不支持。**

MV3 的 WebView 不支持。除非做 Obsidian 插件，或者在别的 <font color="#ffff00">开源书签管理 app</font> 上去做，或者直接基于 Chrome 引擎开发；但 Chrome 原生现在还不支持垂直标签页。

不做第二个 Obsidian，浏览器环境本身也不支持。

#### 原因

**目标：** 验证在 Manifest V3 插件中，通过「侧边栏」、「Canvas 浏览器卡片」或「分页」形式打开外部 URL 的可行性。

**验证结论：** 功能_技术上_可实现，但_实用性_极低。无论是「侧边栏」、「Canvas 浏览器卡片」还是自定义「分页」，其核心实现均为 `<iframe>`，因此均受同样的安全策略限制，无法可靠加载外部网站。

**核心限制：**

1. **`<iframe>` 限制：** 无论是侧边栏（Side Panel）还是设想的 Canvas 卡片，都只能通过 `<iframe>` 来尝试嵌入外部 URL。
2. **安全策略（CSP / X-Frame-Options）：** 绝大多数主流网站（如 Google、GitHub 等）出于安全考虑，使用 `X-Frame-Options` 或 `CSP` 安全策略，**主动禁止**自己被 `<iframe>` 嵌入。
3. **「分页」问题：** 浏览器没有“侧边栏分页”API。自定义分页功能只是在扩展页面内切换不同的 `<iframe>`，无法解决上述 `<iframe>` 限制。
4. **最终结果：** 用户尝试使用这些功能时，绝大多数情况看到的只是“拒绝连接”（refused to connect）错误。

### 限制二：无法自动命名 Window

无法自动命名「Window」，但是「Group」可以。

Chrome `windows` API 没有设置/读取“窗口名”的字段；MDN 的 `windows.Window.title` 也是只读，本质是窗口显示标题，不提供设置。

参考：developer.chrome.com

✅ **曲线方案：** 使用「书签画布」页面，对 tab 进行命名，并且自动定位当前栏目（生成窗口的栏目）。

### 限制三：无法读取已经关闭的组名

无法针对「已经关闭的组的名次进行读取」。

`chrome.tabGroups.*` 只能访问**当前打开窗口里**仍然活跃的分组；窗口一关，组就不在这个 API 里了。

Session / Sync 数据（包括“已关闭窗口”列表、云端同步的 tab 组）只给 Chrome 内部或登录账户使用，扩展没有接口可以读。

Chrome 确实把关闭的窗口/分组保存到 Session Restore 体系中，但那块数据只对浏览器内建功能开放。扩展能访问的 `chrome.sessions` API 也只提供“最近关闭的窗口/标签列表”，而无法告诉你“这个条目里包含了哪些分组、原名是什么”。这在官方文档和 MDN 上都写得很清楚。

#### 其他

✅ **曲线方案：** 增加一个 tab 页面，直接进行管理：「同窗专属组」、「同一窗口」、「专属窗口」。

### 限制五：Edge 侧边栏刷新与 Chrome 行为不一致

有两个问题：

1. 关于 Edge 浏览器：它虽然没有置顶按钮，但 Chrome 确实有置顶功能，侧边栏的置顶有什么用？
2. 标签页切换问题：为什么我们每点击、每切换一个标签页，侧边栏里面的内容都会刷新一遍？这显得非常奇怪。和「1.」有关联吗？能修复吗？Edge 会刷新一遍，Chrome 一点都不会刷新。

#### Chrome 的做法：单例模式

Chrome 把侧边栏看作一个**全局独立的窗口**。一旦打开，它就成了一个持久存在的页面，切换标签页只是切换了它旁边的“邻居”，侧边栏的 JS 上下文完全没动。

#### Edge 的做法：多实例 / 隔离模式

Edge 为了深度集成它的“侧边栏助手”，默认会为**每个标签页（Tab）尝试创建一个侧边栏实例**。当你切换标签时，Edge 会销毁上一个 Tab 的侧边栏上下文，并重新加载当前 Tab 的侧边栏。

✅ **当前方案：** 用的是壳，用的是 panel shelf。

### 限制六：Windows 离散鼠标输入手感

Windows 的离散鼠标输入感不如 macOS，一格格的不舒服。

✅ 勉强做了曲线优化，但体感还是不如 macOS。

### 限制七：多卡片、多书签渲染导致的闪烁

当前最大的体验限制之一，是多卡片、多书签同时渲染时仍可能出现卡片闪烁。

虽然已经在「性能」相关能力里做了多条曲线优化：

- 低细节模式。
- 视角外低细节。
- 懒惰加载。
- 视野内外虚拟化 / 分批渲染。

这是浏览器扩展 + DOM Canvas 方案的现实限制，不是单个开关能完全消除的问题。当前策略是继续用性能模式、低细节、懒加载和虚拟化降低触发概率，而不是承诺无限量卡片和书签都能稳定无闪烁。

## 妥协



### 妥协一：不做附件功能

最大妥协之一，是不做附件功能。

这会影响长期能力，尤其是 GitHub 推送 / 拉取场景：如果支持任意附件、图片、PDF、音视频或其他 file 节点，长期数据包会迅速变大，远端目录也会变得难以管理。推送拉取不再只是轻量的画布结构和书签数据，而会变成一个近似文件同步系统。

理论上可以曲线支持其他 file 节点的渲染或引用，但问题会马上变复杂：

- 数据包体积可能巨大。
- GitHub 推送 / 拉取的速度和稳定性会明显下降。
- 远端目录会承担文件仓库职责。
- 文件预览、缓存、更新、删除、冲突和跨设备一致性都需要额外系统。
- 用户可能会期待它像 Obsidian 或网盘一样管理附件。

结论：~~附件功能~~不做。

Bookmark Canvas 不是重做一个 Obsidian 客户端，也不是文件管理器。需要长期管理附件、媒体文件、PDF 或大型资料库时，建议用户使用更适合的工具，把 Bookmark Canvas 保持在书签、画布结构、说明文本、导入导出和 GitHub 轻量推送拉取这个边界内。

### 妥协六：说明框是否换成 CM6

空白栏目卡片（走 `.canvas` 的 `text` 节点）、永久栏目和临时栏目的说明框（`descriptionMd`）这些东西换成 CM6？

可以，但没有必要。

1. CM6 是 Markdown 源码编辑器，不是现有这种 HTML 富文本 DOM 编辑器。CM6 的主数据是文本 document。现在很多工具是直接改 `innerHTML`、选区 DOM、`document.execCommand`、checkbox DOM、`span` 样式。CM6 不能直接吃这些逻辑，需要改成“改 Markdown 文本”或 CM6 extension / decoration。

==Obsidian 官方开发文档和博客都说明编辑器底层是 CodeMirror（现已全面 CM6）== <font color="#548dd4">后期可能换渲染器</font>

但是当前没有必要加入，因为我们的说明框只是展示，有基本渲染能力就够了。

#### 是否加入 Mermaid 渲染支持？

没必要。

我们本来就是在画布里边。要加入 Mermaid 的话，这种渲染器要做的东西还很多，相当于画布中的画布渲染，还会有画布中的缩放、卡片中的缩放，体验可能不太好，纯属没必要。

### 妥协七：不后补通用打包和高级压缩

当前项目不再追求“把现有代码整体交给打包工具彻底重写输出形态”。这类工具本身没有问题，但对当前 Bookmark Canvas 这种代码形态，后补打包 / 高级压缩的风险大于收益。

调研结论：

- esbuild 的 `bundle` 会把 import 依赖递归内联到输出文件。
- esbuild 的 `minify` 不是单纯删空白，而是组合执行：删除空白、压缩语法、缩短局部变量名。
- esbuild 官方说明，JavaScript minification 并不能保证对 100% 的代码都安全；依赖函数源码字符串、函数/类名、内建对象行为假设的代码都可能受影响。
- esbuild 的 `mangle props` 官方明确警告可能以隐蔽方式破坏代码，除非非常清楚它会怎样影响本项目和全部依赖，否则不应使用。
- Chrome MV3 扩展页面对脚本声明、资源路径、`web_accessible_resources`、后台 service worker、扩展页之间的消息桥接都有固定约束；当前项目不是 content script 注入型项目，风险主要来自扩展页面内多个普通脚本的加载顺序和全局 API 耦合。

当前项目里大量存在：

- `history.html` 按固定顺序加载二十多个普通脚本：`storageBCS_core.js`、导入导出、`bookmark_canvas_module.js`、卡片组、搜索、Tag/Note、`history.js` 等。
- 很多模块通过 `window.CanvasModule`、`window.CanvasProtocolBridge`、`window.TagSystem`、`window.NoteSystem`、`window.BookmarkCanvasGithubTransfer`、`window.__...` 这类全局对象互相调用。
- 代码里大量使用 `document.getElementById()`、`querySelector()`、`classList`、`dataset`、固定 DOM id/class/data 属性和事件委托。
- 画布、设置弹窗、性能面板、导入导出、GitHub 弹窗、书签树、搜索结果等都有运行时 `innerHTML` / 模板字符串拼装。
- CSS 分散在 `history.css`、`bookmark_canvas.css`、`canvas_modals.css`、`tag_system.css`、`search.css` 等文件中，加载顺序和选择器优先级会影响最终 UI。
- 书签树、画布卡片、连接线、懒加载、低细节、虚拟化、favicon、搜索高亮和右键菜单都依赖 DOM 结构与 class/data 属性保持稳定。
- 部分文件很大且历史包袱重，例如 `bookmark_canvas_module.js`、`history.js`、`bookmark_tree_context_menu.js`，不是从一开始按 ES module / tree-shaking / minifier-safe 边界拆出来的。

这种项目最怕“构建过程悄悄改代码形态”。哪怕只是 `--minify-whitespace`，也可能改变输出布局和调试定位；功能可能还能跑，但脚本顺序、全局暴露对象、弹窗模板、CSS 覆盖关系、tooltip、布局、选择器命中、事件委托、字符串显示这些地方容易出现“不像原来”的问题。高级压缩如果再引入变量名压缩、属性名压缩、tree shaking、跨文件合并或模块包装，风险会继续放大。

当前妥协：

- 现有主代码不为了少量压缩收益做大范围重构。
- 不使用属性名混淆 / mangle。
- 不把运行时 DOM/CSS 拼装密集的旧代码整体交给高级压缩。
- 如必须压缩，只考虑非常保守的低级压缩，并且需要完整人工验收关键 UI。
- 打包工具只能用于后续边界清晰、从一开始就模块化的新模块。

更合理的方向是：如果未来做下一个客户端、下一个大模块或重新拆分架构，应从最开始就按模块边界、导入导出关系、构建产物、source map、保留全局 API、视觉回归测试来设计。那时再引入 esbuild / Vite / Rollup 等工具才合理。

这不是否定打包工具，而是承认当前项目早期没有按“可安全高级压缩”的方式组织代码。现在为了那一点压缩质量去补课，代价会是大范围重构和大量 UI 回归风险。

参考：

- https://esbuild.github.io/api/#bundle
- https://esbuild.github.io/api/#minify
- https://esbuild.github.io/api/#keep-names
- https://esbuild.github.io/api/#mangle-props
- https://developer.chrome.com/docs/extensions/reference/manifest
- https://developer.chrome.com/docs/extensions/reference/manifest/web-accessible-resources
- https://developer.chrome.com/docs/extensions/develop/concepts/service-workers

### 妥协八：临时栏目空占位不作底层破坏性清洗，以约束模板与新插件派生索引承接

❌ **主分支明确妥协：不实施 BCS 底层历史数据清洗或破坏性运行时迁移。**

临时栏目源 JSON 长期存在历史序列化遗留的空占位字段：`folder` 节点通常带有空 `url: ""`，而 `bookmark` 节点通常带有空 `children: []`。这在交给 LLM / Agent 处理时容易引发语义混淆（误以为文件夹有 URL、书签有子节点，甚至怀疑数据损坏），并白白浪费 15%~25% 的上下文 Token。

虽然在底层升级存储协议并强行全量清洗技术上可行，但经过深度评估与实验验证，主分支明确做出架构妥协：**保持现有 BCS 存储协议与历史源数据完全不变，不把底层清洗的不可逆破坏风险带入生产环境，转由上层「约束文件 + 新插件派生索引投影」非侵入式解决**。

#### 为什么选择妥协？（底层一刀切清洗的致命隐患）

1. **运行时崩溃与 `TypeError` 致命隐患：**
   代码库中大量既有逻辑（如拖拽插入、跨栏目移动、书签树展开等）在历史实现中隐含了节点字段存在性假设。若底层强行剥离书签节点的 `children: []`，拖拽与节点操作时一旦访问 `bookmark.children.length` 或 `bookmark.children.push(...)` 就会直接抛出致命 `TypeError` 导致整个画布交互崩溃；跨栏目移动若“先删原节点后判目标有效性”，还会导致用户数据静默丢失。
2. **全链路强耦合与维护代价过高：**
   临时栏目涉及的入口极广，横跨 BCS 存储协议（`bcs:section:*`）、runtime 恢复逻辑、自动备份槽（`bcs:backup:slot`）、剪贴板历史（`bcs:clipboard-history`）、历史 section 快照（`bcs:temp-snapshot`）、GitHub Push / Pull、JSON/HTML/ZIP 导入导出、多处克隆/粘贴及 6 个以上的序列化函数。任何一处改造遗漏，都会导致脏数据死灰复燃或版本不兼容。
3. **启动时序与竞态风险：**
   在扩展启动初始化阶段，BCS 异步读取、备份槽保护与内存回刷之间存在竞态条件。若清洗器在内存状态尚未完全就绪时介入，极易误判为空栏目从而发生误删或数据覆盖。

#### 明确不实施的内容（妥协边界）

- **不修改 BCS 存储协议、runtime 恢复逻辑或普通保存逻辑。**
- **不对历史 section、自动备份槽或剪贴板历史做一次性数据清洗。**
- **不改写备份、导入、导出、GitHub Push / Pull、JSON/HTML/ZIP 或跨类型转换的源数据。**
- **不逐一改造旧版应用中所有的 serializer、clone、paste、drag/drop 和构造器。**
- **不把模板或插件索引投影当作新的源文件格式，也不据此强制迁移旧用户数据。**

#### ✅ 落地的妥协与破局方案：约束模板 + 新插件派生索引

系统采取非侵入式的“双层边界”方案，在零风险前提下彻底化解问题：

1. **底层源数据保持现状，以显式 `type` 判型：**
   源数据继续保留 `folder` 的 `url: ""` 与 `bookmark` 的 `children: []` 序列化形状；所有业务判型与 Agent 读写严格以显式 `type`（`folder` / `bookmark`）为准，不凭字段有无猜测类型。`folder` 的空 `children: []` 是有效的空文件夹状态，予以保留。
2. **约束文件（AGENTS 模板）规范模型认知：**
   通过中英文自包含的 `AGENTS_template` 约束文件明确告诉 Agent：这两个空占位属于历史序列化形状而非损坏，Agent 读取时忽略空 `url` 与空 `children`，禁止为了清理占位字段单独改写源文件；写回源文件前回读原节点，保留未修改字段与未知属性。
3. **新伴侣插件 [Bookmark Research](https://github.com/Browser-bookmark-hub/Bookmark-Research) 派生索引投影（现已落地解决）：**
   该派生索引能力已由官方独立伴侣插件 [Bookmark Research](https://github.com/Browser-bookmark-hub/Bookmark-Research)（支持 Codex、Claude Code、DeepSeek Harness (dsh) 等环境，提供 Skill + 本地 MCP + CLI）完整落地并解决。插件在导出的画布包外建立只读派生索引，源 JSON 依然是唯一事实来源。在定点搜索（`search_bookmarks`）、上下文读取（`get_context`）或大纲提取（`inventory`）向模型输出投影时，插件会自动滤除/省略 folder 上的多余空 `url` 以及 bookmark 上的多余空 `children`，输出扁平紧凑的树状投影。这一机制彻底消除了模型的语义混淆与 15%~25% 的 Token 冗余，且无需在底层破坏性清洗用户的任何源数据包。

### 妥协九：浏览历史访问统计与删除对账的架构妥协

❌ **主分支明确妥协：不进行常驻后台全量监听，不维持庞大的后台删除网址列表，不做类似生态项目「书签记录与推荐」的永久历史数据库。**

在引入书签访问频次（`@热度`）与最近访问时间（`@最近`）时，系统面临浏览器底层 API 机制的客观硬约束。经过实测与架构评估，主分支确立了以下明确的妥协与边界：

#### 1. 为什么不做像生态项目「书签记录与推荐」那样的永久浏览历史数据库？

在书签生态中，[书签记录与推荐（Bookmark Record and Recommend）](https://github.com/Browser-bookmark-hub/Bookmark-Record-Recommend) 的核心使命是全天候追踪用户访问轨迹并生成智能推荐，因此它必须通过后台常驻监听维持一份独立、长期的全量历史库。但对于 **Bookmark Canvas（书签画布）**，主分支明确**拒绝**这种做法：

- **极简性能与 0 耗电哲学：**
  若要做永久记录，后台 Service Worker 必须 24 小时挂载 `chrome.history.onVisited`，用户每打开一个网页、点一个链接、甚至后台标签页刷新，后台都必须被频繁唤醒、过滤并落盘写入。这会带来持续的 CPU 唤醒、内存占用和笔记本电池消耗，严重违背书签画布“平时 0 监听、0 唤醒、用户不搜索不花 1 毫秒 CPU”的性能底线。
- **存储无限膨胀与脏数据垃圾池：**
  普通用户一年的全网浏览量极其庞大（新闻、购物、临时页面等数十万条无用记录）。若在插件内建立私有持久历史库，会导致扩展本地存储无限膨胀，带来沉重的存储 I/O 负担与数据同步灾难。
- **僵尸幽灵数据与一致性矛盾：**
  一旦脱离浏览器原生底层建立影子库，当用户在浏览器主动“清除历史记录”时，由于底层 API 存在通知盲区（见下文），插件私有库极易出现“浏览器已彻底删除、插件却依旧留存”的僵尸幽灵数据，造成严重的数据不一致。
- **隐私底线与用户信任：**
  书签画布是纯净的本地可视化工作台。我们只在用户使用搜索时，依附于浏览器物理留存的 90 天窗口按书签白名单反向过滤，绝不在后台暗中建立用户全量上网轨迹的永久监控库。

#### 2. 浏览器底层 API（`chrome.history`）的平台级限制与妥协

- **90 天物理留存天花板：**
  Chrome 等 Chromium 内核浏览器的本地 SQLite 数据库会自动滚动淘汰 90 天以前的历史。无论调用 `history.search` 传入多早的 `startTime`，浏览器底层最多只能返回近 90 天记录。90 天是浏览器平台的能力上限，而非插件人为截断。
- **删除时间范围完全失明：**
  浏览器的 `onVisitRemoved` 事件对象仅包含 `{ allHistory: boolean, urls: string[] }`，**绝不告知用户清理的是哪个时间范围**（无从获知用户是清除了“过去 1 小时”、“过去 24 小时”、“过去 7 天”还是“过去 4 周”）。
- **对「部分删除」完全不发通知：**
  当某个书签在过去有旧访问、最近又有新访问时，用户若在浏览器选择“清除近 7 天历史”，虽然最近的访问记录被删除了，但因该 URL 在浏览器底层数据库中依然留有更早的访问记录，**浏览器根本不会在 `onVisitRemoved` 中通知该网址**！它仅在某个网址的所有历史被彻底抹除时才加入 `urls`。
- **后台放弃维持庞大删除队列：**
  后台若将上百条被删网址持续写入 `chrome.storage.local`，既浪费存储 I/O，又无法防住“部分删除”（且 99.9% 是无关的非书签网页）。因此主分支做出妥协：后台仅设轻量防抖缓冲区，超过阈值直接升阶为「大清理时间戳」，不维护无意义的长网址垃圾池。

#### 3. 搜索候选全量预评分与按需更新机制

- **客观评分机制：必须先打分后展示**
  书签的访问频次与最近访问时间直接参与搜索面板的**候选评分（Scoring）与全局排序**（如 `@热度` / `@最近` 排序与分组）。系统无法在展示后再倒推计算前 50 个，而是必须基于本地持久化快照与增量流水对候选集完成整体打分，才能正确排出前 50 名。
- **冷启动与增量妥协：**
  - **冷启动**：一次性拉取近 90 天记录（Chrome 浏览器本地 SQLite 数据库物理留存的上限），建立书签反向白名单过滤并存入 IndexedDB 快照。
  - **日常使用**：平时完全不挂载 `onVisited` 监听（0 耗电、0 CPU 占用）；仅在用户聚焦搜索框、输入 `@热度` 或右键文件夹时，按需拉取上次同步以来的微切片增量流水。
  - **右键单书签**：右键单书签查看信息时，直接按原网址调用底层 API 精确查询（耗时 <0.1ms），兼顾实时性与低开销。
