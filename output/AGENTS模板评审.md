- **评审对象**：`AGENTS_template_zh.md`（模板）与包内 `书签画布/AGENTS.md`（导出产物）；下方一致性数据和旧行号来自初次评审快照，模板后续修改不会自动更新已有导出产物。
- **对照数据**：`bookmark/书签画布` — 36 个栏目 JSON（1 永久 + 35 临时）、46 个画布节点、13 条连线、2.0 MB
- **方法**：把模板里的硬规则逐条翻译成脚本断言跑真实包；再读导出/锚点的实现源码，核对"模板说的"与"程序实际写的"
- **未覆盖**：没有启动浏览器跑 UI 渲染，只做结构与实现层核对
- **后续处理（2026-11-01）**：P1 拆为 [存储协议精简与历史清洗方案](./临时栏目存储协议精简计划.md) 和 [Agent 树状上下文读取与模板增强计划](./Agent树状上下文读取与模板增强计划.md)。读取优化与安全红线无论删不删空值都要实施；存储层保留或删除是另一项选择，不再记录为已决定暂缓。P2–P6、P8、P9 及永久树时间字段规则的原评审状态保留；P7 按用户决定不新增校验脚本。

## 0. 结论

模板主体规则经真实包核验基本成立，但评审发现文件名、路径说明、锚点落卡、删除联动和 edge 方向等规则需要更贴近实际导出与操作。P1 涉及两条独立工作线：Agent 按类型理解和局部上下文读取必须优化；临时栏目共享存储协议是否删除空占位，按单独方案选择与验收。

当前模板处理状态：P2–P6、P8、P9 及永久树时间字段规则沿用原修改记录；P7 不新增脚本。P1 按拆分后的两份计划分别记录实施结果，已有说明不等于新增安全红线、两类示例与工具案例已经全部验收；不能把文档处理视为协议已修复。

## 2. 写得好的地方

1. **体量与工具分流**（L3–L8）写得很实：给出"先看字节数 → 用脚本定点提取"的顺序，正好对得上 543 KB 的主树。
2. **`pinned` 坐标是占位**（L38）——已核对源码：置顶切片节点统一写 `x:0, y:0, 300×200`（`canvas_sidebar_directory.js:5364`），模板说"避免照抄占位坐标"完全正确，这是最容易踩的坑。

## 3. 问题清单（按优先级）

### P1（读取优化独立必做，存储形状另行选择）临时栏目空字段

已确认 BCS section 分片与临时栏目 JSON 导出共用会写入空 `url`/`children` 的 serializer。[精简计划](./临时栏目存储协议精简计划.md)完整保留删除方案、历史数据处理、自动备份后清洗与跨流程回归；选择保留现状时，则在普通链式、特殊临时两类中英文示例中展示 folder 的空 `url` 和 bookmark 的空 `children`，解释占位含义并以 `type` 判型。无论选择哪一种，[Agent 读取计划](./Agent树状上下文读取与模板增强计划.md)都要求开头握手与后置安全红线共同约束：禁止整包、大栏目或多卡累计全文进入模型上下文，优先使用插件公开工具，无插件则用本地 JSON 解析，按节点读取祖先、必要后代、元数据和卡片关系，控制分页与索引新鲜度，写前回读原文件。工具可在本地完整解析；模型只接收必要结果。两份计划分别验收，不把保留空值或存储清洗当作读取优化的前提。

### P2（高/真实回归）特殊栏目文件名规则与导出实现不符

- **位置**：§2.5 L185 写的是 `临时栏目/特殊临时栏目/<label>.json`（如 `AI.json`）
- **证据**：实物 11/11 都不是 `<label>.json`，而是 `<label> <title>.json`：`添加 token测量.json`、`存档 工作与趋势.json`、`添加-7 AI search _ information projects.json`。导出代码确认文件名 = `seqLabel + " " + title` 再规范化（`import-export-transfer-feature.js:3934`），`/` 会变成 ` _ `。
- **这是回归**：`0afb8ff` 之前的 A1 目录树写的是 `AI <标题>.json`、`添加/搜索/导入 <标题>.json`（正确）；压缩后 §2.5 变成了 `<label>.json`（错误）。旧版对、新版错。
- **后果**：AI 新建特殊栏目会产出 `AI.json` 这种与包内风格不一致的文件名，画布 `file` 路径也跟着不同。
- **改法**：路径改成 `临时栏目/特殊临时栏目/<label> <title>.json`，并注明"文件名取序号标签 + 空格 + 标题，`/` 等字符导出时规范化；新建时沿用相邻文件的命名习惯"。

### P3（中/澄清）锚点是对话镜头对象；补充窄视野的落卡处理

> 注：这里指的不是用户给的锚点数据——那份数据是自洽的（见 §4）；是模板对"锚点是什么"的定义有歧义。

- **位置**：§2.1.6（L37）、§3.3（L245）
- **证据**：锚点是宿主**粘贴在对话里的独立对象**（`workspaceType: "anchor" | "temp-anchor"`，字段 `camera`/`visibleRange`/`timestamp`），**不会写进 `.canvas`**；本仓库的 `.canvas`（含本包）里 `bookmark-canvas-anchor` 出现 0 次。模板读起来像"画布里有一种节点叫这个"。
- **改法**：明确它是宿主粘贴到对话里的镜头输入，不是 `.canvas` 节点；空间不足时说明，再按用户意图询问是否改放附近空位或请用户提供更宽镜头。不要把本包观察到的最窄宽度 477 写成全局协议阈值；它只是当前卡片尺寸的实测，不是固定最小尺寸。

### P4（中/导出路径核对）示例路径须对应实际导出设置

- **位置**：L42 示例 `"file": "<画布数据包根目录>/永久栏目/A书签树（永久栏目）.json"`
- **实际导出设置**：Obsidian ZIP 导出对话框由用户设置 `.canvas` 内部路径；生成画布 file 引用时，根目录模式用导出目录名，vault 子目录模式把完整相对前缀（如 `Exports/书签画布`）写入 file 字段，独立 vault 则不加目录前缀。用户数据包中的路径是 vault-relative，不是相对 `.canvas`。
- **模板生成器现状**：`__buildExportGuide()` 已替换 `{{EXPORT_ROOT}}`，但该值是 `exportRoot`（目录名），不是完整 `vaultPrefix`；同时模板没有一个已确认能覆盖上述三种路径形态的 token。故评审原先建议直接换成 `{{EXPORT_ROOT}}` 过于简单，嵌套 vault 子目录时可能仍误导。
- **怎么修（已落实）**：模板声明尖括号路径只是说明占位符，新增 file 节点须复制当前 `.canvas` 同类 file 引用的完整 vault-relative 前缀；不使用当前只包含目录名的 `{{EXPORT_ROOT}}` 伪装成所有导出模式都准确的路径。

### P5（低/项目惯例）栏目 file 卡片 ID 遵循既有惯例

- **证据**：36/36 file 卡片节点 id 与目标栏目 id 完全相等（`temp-section-A-6` 等）；永久主卡固定 `permanent-section`；副本卡按代码是 `permanent-section-copy-<copyId>`（`canvas_sidebar_directory.js:1036`）。
- **处理**：可以补为本项目导出惯例：临时栏目 file 卡片沿用栏目 `id`；永久主卡和副本卡沿用各自现有固定规则。编辑时先参照同类卡片，不把它写成通用 JSON Canvas 约束。用户导书包通常依既有惯例，因此这里重点是提醒 AI 复用惯例，不需要另造一套编号制度。

### P6（中/操作语义）删除、移动、重命名的影响范围应拆开写

模板已有栏目文件增删改名时维护 `.canvas file`、edges 与 `inheritFrom` 的总要求；仍需把用户实际操作中的几种“删”区分开。删除画布卡片框、删除栏目文件、删除栏目里的书签不是同一件事。评审中关于卡片 UI 的“仅删框体 / 连成员一起删”要按实际 UI 行为限定到相应节点类型，不能泛化成所有栏目卡片。

- **删除书签条目**：从永久 `tree` 删除时，核对并删除对应 `identityMap` 条目；临时 item 从所属 `items` 树删除。若删的是整个文件夹，还要明确是否递归删除后代。
- **删除画布卡片框**：只移除 `.canvas` node 及其关联 edge，不应默默删除栏目 JSON 或浏览器书签内容；若用户要求删除栏目数据文件，再同步处理引用。
- **跨栏目移动**：保留已有 item ID，并更新被移动项及其后代的 `sectionId`；模板 §2.4 已有后代更新规则，可在生命周期段落用“移动”显式索引到该规则。
- **重命名栏目**：同时核对 `label`、栏目 `id`、file 路径、file node ID、所有 item 的 `sectionId` 与 edge 端点；实际是否重算 `id` 必须服从应用当前重命名实现和既有文件，不得仅凭 label 推断后强行改 ID。
- **`descriptionMd`**：只在栏目用途/说明确实改变时更新；保留原 Markdown/HTML 内容，避免无关重写。需要把这条写成保留原则，而不是额外要求每次操作都改描述。

### P7（不采纳）新增校验脚本不是本次必要改动

模板已有按改动范围执行的写后自检规则。按用户决定不新增 `tools/validate_package.py`；若后续重复出现人工校验成本，再单独评估工具化。

### P8（低/已落实）示例与 label 细节

- 标题格式已统一为全角中文括号。
- 浏览器根节点示例改为当前样本的 `syncing: true`，并说明值是动态只读状态，编辑时以实物为准。
- 普通临时栏目示例补 `source`，并要求编辑时保留已有来源值。
- 特殊栏目 label 增加字符规范化说明，生成栏目 ID 前沿用应用规则。

### P9（中/已落实）恢复 edge 箭头字段说明

- **位置**：新版全文没有 `toEnd` / `fromEnd`
- **证据**：旧版 A8 写"单箭头默认省略两端字段，无箭头写 `toEnd: "none"`，双端箭头写 `fromEnd: "arrow"`"；你给的实包 13 条 edge 中 3 条在用这些字段（`toEnd: "none"` ×2、`fromEnd: "arrow"` ×1）。AI 改连线时缺少这条规则，可能把既有箭头语义改掉。
- **处理**：已在中英文 §2.1 edge 规则中补回默认单箭头、省略字段、无箭头和双端箭头的字段语义；未额外增加大段编辑示例。

## 4. 「视觉」锚点实测

锚点：`camera(-2418,-333, zoom 0.43)`，`visibleRange = (-2631,-1127, 427×1587)`。

- **自洽**：矩形中心 `(-2417.5, -333.5)` 正好等于 camera，坐标没问题。
- **形状异常**：按导出公式 `world = 面板px ÷ zoom` 反推，保存时画布面板约 **184×682 px**。这不是正常画布尺寸，八成是侧栏/窗口被压窄时存的，或槽位里的 `viewW/viewH` 是旧的。
- **在屏卡片**（按模板 L37 的矩形相交公式，4 张）：

| 卡片 | 坐标 | 交集 |
|---|---|---|
| `temp-section-B-1-1`（AI Audio/视频/多模态） | (-2621,-771) 708×627 | 417×627 |
| `temp-section-A-6`（视觉） | (-2621,-1351) 693×550 | 417×326 |
| `temp-section-添加`（AI EE / CS 应用） | (-2963,253) 551×766 | 219×207 |
| `temp-section-A-9`（具身智能） | (-2213,253) 502×587 | 9×207 |

- **能不能在这里落一张新卡？不能。**
  1. 视野宽 427 世界单位 < 全包最窄卡片 477 —— 任何整卡都放不进去；
  2. 这条竖条已被 A-6 / B-1-1（各占 417 宽）基本铺满；
  3. 它所在的组 `card-group-23（视觉与多模态）` 也满了：4 张卡之后，组内最大空矩形只有 304×1276（右侧窄条），装不下标准卡；
  4. 全画布最近的可放 660×560 空位在 `(-1695,-202)`，距镜头中心 735，且在组外。

**结论**：这个锚点适合做"在屏筛选"，但不适合把标准尺寸新卡落在当前窄视野中。模板现已说明空间不足时可提附近空位或请求更宽镜头；若用户明确指定其他方案，再按新落点检查几何与组关系。

## 5. 建议补充的流程（模板目前只有契约，没有 playbook）

1. **新增书签**：用工具读目标栏目并按所属格式生成节点。永久树按 Chrome 树形结构写 bookmark URL/folder children，扩展元数据更新 `identityMap`；临时栏目按 `type` 判型，沿用包含空字段的当前协议，不清洗旧数据 → 校验 → 内容编辑不动 `.canvas`。
2. **新建栏目**：定 label → 按 P2 起文件名 → 建 JSON（含 `source`）→ 建 file 卡（id = 栏目 id）→ 不连线进 group。
3. **删除/移动/重命名**：见 P6，删完查 `identityMap` 与 `sectionId`。
4. **改布局**：先算目标矩形与占位，再写坐标，写后复算一次重叠。
