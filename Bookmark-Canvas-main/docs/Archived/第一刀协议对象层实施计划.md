## 1. 这份计划书要解决什么问题

第一刀不是重写整个运行时，也不是提前把 `visual / visual-no-icon / json` 三套导出格式一起推倒重来。

第一刀只做一件基础工作：

- 给当前仓库补齐“可复用、可比较、可缓存”的协议对象层

这层协议对象专门服务：

- 导入
- 导出
- 同步
- 比较
- 后续第三刀永久栏目主栏 / 副本共享内容源

第一刀完成后，后续三条线的边界应当更清楚：

- 永久栏目正文继续以 Chrome bookmarks API / 规范化 permanent snapshot 为真相源
- 空白栏目正文继续朝 `markdownSource` 单一真相源收敛
- `.canvas` 继续只负责布局和节点语义

## 2. 当前仓库现状

当前仓库其实已经有部分协议层雏形，但入口还比较分散。

### 2.1 空白栏目已经有 `markdownSource` 协议雏形

`history_html/bookmark_canvas_module.js` 里已经有：

- `__deriveMdNodeMarkdownSource`
- `__ensureMdNodeMarkdownProtocol`
- `__syncMdNodeFromEditor`

而且在这些路径里已经在调用：

- 加载主状态时给 `CanvasState.mdNodes` 补协议
- 导入 `.canvas + .md` 时把 `parsedMarkdown.rawBody` 写进 `markdownSource`
- 恢复时按 `markdownSource -> html/text` 刷新缓存

这说明第二刀要走的 `markdownSource` 单一真相源方向，当前仓库已经有现实落点；第一刀要做的是把这套读侧协议收拢，避免导入、导出、同步各自再做一遍临时转换。

### 2.2 永久栏目已经有 snapshot 协议雏形

同一个文件里已经有：

- `__normalizePermanentTreeSnapshotForProtocol`
- `__buildBookmarkTreeSnapshotFromPermanentMarkdown`

在这些链路里也已经在用：

- 全量备份导出
- 文件夹 / zip 导入
- 同步恢复

问题不在“有没有规范化”，而在“调用点太散”。现在还是多个分支各自去解析、归一化、补字段，后面越接近第三刀和 `JSON模式（供AI）`，越容易出现多处分叉。

### 2.3 同步层仍然大量直接面向 raw storage

`history_html/sync/obsidian-git-sync.js` 现在直接处理：

- `bookmark-canvas-temp-sections`
- `permanent-section-position`
- `permanent-section-copies`
- `canvas-permanent-tip-text`

同步比较和恢复时，既要吃 raw storage，又要吃 `permanentTreeSnapshot`，还要对空白栏目、永久栏目、副本说明分别做特殊处理。

这会导致：

- 比较口径容易不一致
- 导入导出和同步重复解析
- 回滚时难以只切一层

## 3. 第一刀锁死的边界

### 3.1 真相源边界

- 永久栏目主内容真相源：Chrome bookmarks API / 规范化 permanent snapshot
- 空白栏目正文真相源：`markdownSource`
- 空白栏目 `html / text`：运行时渲染缓存与预览缓存
- 临时栏目当前运行时真相源：`items`
- `.canvas` 真相源：位置、尺寸、节点类型、连线

### 3.2 第一刀不做什么

- 不把永久栏目主内容改成 Markdown-first
- 不把临时栏目运行时 `items` 一次性重写成协议树
- 不提前改 `obsidianExportFormat` 三值
- 不提前清理旧导入、旧恢复、旧导出入口
- 不提前把永久栏目副本改成独立正文源

### 3.3 第一刀与前三刀的关系

第一刀是前三刀的底座，不替代后两刀：

- 第一刀先锁协议对象和适配入口
- 第二刀再把空白栏目写侧正式切到 `markdownSource`
- 第三刀再把永久栏目主栏 / 副本切到“独立视图壳 + 共享内容源”

## 4. 第一刀的最小协议对象集合

当前仓库不适合一开始就新建一整套庞大的类型系统。第一刀只需要锁定最小对象集合。

### 4.1 `permanentTreeSnapshotProtocol`

职责：

- 表达永久栏目规范化书签树
- 供导入、导出、同步、比较共用
- 作为第三刀主栏 / 副本共享内容源的输入

来源：

- Chrome bookmarks API 拉树后规范化
- 从永久栏目 `.md` 恢复时由 `__buildBookmarkTreeSnapshotFromPermanentMarkdown` 重建

### 4.2 `mdNodeProtocol`

职责：

- 表达空白栏目 / Markdown 节点的正文协议

最少字段：

- `id`
- `subtype`
- `x / y / width / height`
- `color / colorHex`
- `markdownSource`
- `html`
- `text`

关键原则：

- 比较、导出、同步优先看 `markdownSource`
- `html` 只做运行时缓存，不再当正文真相源

### 4.3 `tempSectionProtocol`

职责：

- 给临时栏目提供统一读侧结构
- 供导出、同步、比较使用
- 运行时仍允许继续保留 `items`

关键原则：

- 第一刀先做 `items -> protocol` 适配
- 不要求第一刀就把所有写侧改成 `protocol -> items`

### 4.4 `permanentViewShellProtocol`

这一层在第一刀只需要先定义边界，不要求完整实现。

它的作用是为第三刀预留：

- 主永久栏目视图壳
- 永久栏目副本视图壳

它不承载书签树正文，只承载：

- `copyId / viewId`
- `descriptionMd`
- `scrollState`
- `foldState`
- `cardState`

当前 `canvas-permanent-tip-text*` 仍是老存储键；第一刀先把协议口径锁住，第三刀再正式收口。

## 5. 面向当前仓库的实施顺序

### 5.1 第一步：把现有协议 helper 收成统一入口

先不急着拆文件，优先在 `history_html/bookmark_canvas_module.js` 内把以下入口统一成“单点调用”：

- md node 协议归一化
- permanent snapshot 归一化
- tempState 协议归一化
- 从导入包 / 同步快照恢复协议对象

也就是先做到：

- 别的调用方只找统一入口
- 不再在每个分支手写一遍字段补齐逻辑

### 5.2 第二步：让空白栏目读侧彻底以 `markdownSource` 为准

把当前仓库里所有会读取空白栏目正文的入口统一到同一规则：

- 读取时先走 `markdownSource`
- 没有 `markdownSource` 时才从旧 `html/text` 兜底补建
- 一旦补建成功，立刻回到标准协议对象

这一步不要求立刻删除旧字段，但要求比较、导出、同步都改用统一口径。

### 5.3 第三步：让 permanent snapshot 也改成统一入口

把现在散在这些路径里的 permanent snapshot 收口到同一协议：

- 备份导出
- 文件夹 / zip 导入
- 同步读取
- 同步恢复
- 本地 / 云端差异比较

目标是：

- 同一份永久树，不再被多套解析器各自处理

### 5.4 第四步：让同步层只消费协议对象

`history_html/sync/obsidian-git-sync.js` 后续应优先拿到：

- 规范化后的 `tempStateProtocol`
- 规范化后的 `permanentTreeSnapshotProtocol`
- 规范化后的永久视图壳协议对象

而不是在同步模块里继续直接散着处理 raw storage key。

### 5.5 第五步：为第三刀预留永久视图壳读口

这一阶段先不改主栏 / 副本渲染，但要先把“永久内容源”和“永久视图壳”拆成两个读口：

- 书签树内容源读口
- 视图壳状态读口

这样第三刀做独立视图壳时，就不用边改渲染边改协议。

## 6. 第一刀完成后的直接收益

- 空白栏目不会再在导出 / 同步时到处临时做 `html -> markdown`
- 永久栏目快照不会再在导入 / 导出 / 同步里各自维护一套解析差异
- 第二刀切 `markdownSource` 写侧时，不用再顺带重写同步比较
- 第三刀做永久栏目主栏 / 副本共享内容源时，可以直接消费同一份 permanent snapshot

## 7. 验证要点

### 7.1 空白栏目

- 本地加载旧数据时，缺失 `markdownSource` 的节点能自动补齐
- 导入 `.md` 后，`markdownSource` 可直接恢复
- 同步比较优先比较 canonical `markdownSource`，而不是 `html`
- 仅刷新 `html/text` 缓存时，不应产生正文差异误报

### 7.2 永久栏目

- 同一份永久树从 API、全量备份、Obsidian 导入、同步快照恢复后，规范化结果一致
- `permanentTreeSnapshot` 比较口径一致，不因调用入口不同产生误差
- 第三刀前即使不改主栏 / 副本渲染，也能先稳定拿到统一内容源

### 7.3 同步链路

- `obsidian-git-sync.js` 能直接消费协议对象，不再依赖多处分支补字段
- `bookmark-canvas-temp-sections` 的比较结果不再受 `html` 缓存抖动影响
- 永久栏目说明 / 副本说明暂未迁移时，也不影响正文协议判断

## 8. 回滚与并行协作要点

### 8.1 回滚原则

- 回滚优先切入口，不回退用户数据
- 保留旧字段读侧兜底，不在第一刀当天删除旧字段
- 协议层出问题时，只回退到旧调用入口，不回滚别人同时改过的文件

### 8.2 并行协作原则

- 当前仓库可能有人同时改 `bookmark_canvas_module.js`、`history.js`、`obsidian-git-sync.js`
- 第一刀实现必须优先走“加适配器 / 包装旧入口”，不要直接大面积重排
- 不能用覆盖式回退去处理冲突，尤其不能为了切协议层把别人刚改的调用方重置掉

### 8.3 建议的安全落地方式

- 先补统一 helper 与 wrapper
- 再逐个调用点切换
- 最后再删旧分支

一句话总结：

- 第一刀的目标不是“多造一份真相源”
- 而是把当前仓库已经零散存在的 `markdownSource` / permanent snapshot / tempState 读侧协议，收成后两刀都能复用的稳定边界
