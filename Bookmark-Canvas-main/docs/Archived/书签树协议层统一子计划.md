> 返回文档索引：[docs/README.md](./README.md)
> 关联主计划：[JSON结构模式最终方案](./JSON结构模式最终方案.md)
> Obsidian 双链：[[JSON结构模式最终方案]]

## 1. 当前定位

这个子计划不是普通补充说明，而是 `JSON结构模式最终方案` 的前置子计划。

它专门解决下面这个核心问题：

- 是否要把永久栏目、永久栏目副本、临时栏目所使用的“书签树 JSON”统一成同一套协议层
- 是否要让本地存储里的书签树结构，与导出 JSON、同步 JSON 共用同一种树模型
- 如何把“书签树内容”和“插件运行时壳子”拆开

这份子计划当前先锁死两件事：

- 主永久栏目与临时栏目正文都不再保留额外标题文字，正文直接使用单一代码块承载
- 永久栏目副本继续沿用 Obsidian 的嵌套引用 / 嵌套块包装，不改成纯 JSON 引用包装对象

若两个文档有冲突，以本子计划为准

---

## 2. 为什么要单独拆出来

这次改动已经不只是“新增一个 JSON 模式”。

它正在触及四层东西：

1. 插件内部本地存储
2. 导出到 `.md` 的正文结构
3. 同步到云端的正文结构
4. 导入 / 拉取 / 同步恢复时的解析器

如果这四层不统一：

- 导出是一套
- 导入是一套
- 同步又是一套
- 本地存储还是另一套

后面维护会越来越乱。

所以这次真正要统一的是：

- 书签树协议层

而不是：

- 整套插件运行时对象

---

## 3. 统一范围

本子计划只统一“书签树内容层”。

### 3.1 需要统一的部分

- 永久栏目主文件里的书签树正文
- 永久栏目副本所引用的书签树正文
- 临时栏目里的书签树正文
- 永久栏目规范化快照 / 协议视图使用的树结构
- 临时栏目协议层快照，以及它与本地 `items` 的转换器
- 导入 / 导出 / 同步共用的 JSON 解析器输入输出

### 3.2 明确不统一的部分

- 卡片位置：`x / y / width / height`
- 颜色、边框、缩放、折叠、懒加载
- 四种操作后的颜色标识、路径徽章
- `.canvas` 布局文件
- 选中态、拖拽态、运行时 UI 状态
- 空白栏目 / Markdown 卡片自己的正文协议

结论就是：

- 插件壳子还是插件壳子
- 书签树就是书签树

---

## 4. 分层原则

- 永久栏目和临时栏目不采用同一种本地来源策略。
- 永久栏目：Chrome bookmarks API 是真相源，协议层只负责规范化快照 / 协议视图，不把永久栏目改成本地自存整份树正文。
- 临时栏目：当前仍以 `items` 为运行时主结构，协议层先通过适配器与 `bookmarkTree` 对齐。
- 这里讨论的 `bookmarkTree / sectionMeta(meta)` 顶层边界，只作用于 `json` 正文协议层，不要求当前本地存储顶层或现有 `visual / visual-no-icon` 顶层先改。

建议正式分成三层：

### 4.1 `bookmarkTree`

这是统一后的书签树正文，只负责树本身。

它应该能被：

- 永久栏目规范化快照 / 协议视图直接使用
- 临时栏目协议层直接使用，必要时再映射回当前 `items`
- 导出 JSON 直接写出
- 同步 JSON 直接写出
- 导入 / 拉取 / 同步解析器直接读取

### 4.2 `sectionMeta` / 顶层 `meta`

这是栏目级包装信息，只负责：

- 这是永久栏目还是临时栏目
- 栏目标题
- `slot / label / source / createdAt / originPermanent` 这类栏目元数据

简单理解：

- `bookmarkTree` 只放“树本身”
- 顶层里凡是不属于树节点正文、但又需要跟着这个栏目一起导出 / 同步的信息，都放进 `sectionMeta`

### 4.3 `pluginRuntimeState`

这是插件自己的运行时外壳，只负责：

- 卡片位置和大小
- 颜色和显示态
- 组框和边
- 其他 Canvas 运行时状态

因此最终关系应当是：

- `bookmarkTree` 可以被单独抽出来
- `sectionMeta` 负责说明“这棵树属于哪个栏目”
- `pluginRuntimeState` 不进入统一书签树协议

## 5. 当前锁定方向

下面这些已经按当前讨论先锁定，可直接作为后续实现约束。

### 5.1 主永久栏目

结论固定为：

- 主永久栏目 `.md` 文件不再保留额外标题文字
- 整个文件直接就是一个 `json` fenced code block
- 这个 JSON 块就是唯一正文真相源
- 但这个 JSON 正文来自永久栏目规范化快照 / 协议视图投影，不反推插件本地真相源改成 JSON 文件存储

也就是：

````md
```json
{
  "format": "bookmark-canvas-section",
  "schemaVersion": 1,
  "meta": {
    "sectionType": "permanent",
    "slot": "A"
  },
  "bookmarkTree": {
    "id": "root",
    "kind": "folder",
    "children": []
  }
}
```
````

### 5.2 永久栏目副本

结论固定为：

- 副本文件也不再保留额外标题文字
- 副本不复制第二份 `bookmarkTree`
- 副本继续作为“主永久栏目正文的包装 / 引用层”
- 副本本质是视图壳，可独立保存 `descriptionMd / scrollState / foldState / cardState`
- 这里强调的是“共享内容源”，不是“共享同一个 DOM 实例”

这里的目标不是让副本也拥有独立真相源，而是：

- 副本仍属于 JSON 模式体系
- 但它本质是对主永久栏目的引用

- 副本最终固定为继续沿用 Obsidian 的嵌套引用 / 嵌套块语法
- 不引入纯 JSON 的引用包装对象
- 文件正文不再额外加标题文字，保持“直接一个块”的形式
- 统一的是“书签树内容源”，不是副本外壳标识体系；现有 `copyId`、标题标签、搜索定位 / 跳转、目录栏定位、导出节点标识、同步识别都必须兼容保留。
- 每个副本自己的 `descriptionMd / scrollState / foldState / cardState` 继续独立保存；懒惰加载、路径徽章 / 标识系统允许内部适配，但外部行为不能退化。

在包装语法锁定后，副本继续只遵守这条原则：

- 不允许出现第二份独立书签树正文

#### 5.2.1 永久栏目主栏 / 副本改造边界

这一步要明确：

- 改的是“书签树内容源统一”，不是把永久栏目整套外壳推倒重来
- 原来通过主树 DOM 同步到副本 DOM 的做法，后续可以收敛成“同一内容源，多视图独立渲染”
- 统一内容源后，理论上更适合后续导出、同步、比较与维护，但不允许因为内部改造导致现有外部能力断掉

必须兼容保留的部分：

- `copyId`
- 标题标签与副本显示编号
- 搜索定位 / 跳转
- 目录栏定位
- 导出节点标识
- 同步识别

允许内部实现跟着适配、但外部行为不能退化的部分：

- 垂直滚动条状态
- 文件夹折叠状态
- 说明
- 懒惰加载
- 路径徽章 / 标识系统

### 5.3 临时栏目

结论固定为：

- 临时栏目也走同一套 `bookmarkTree` 结构
- 临时栏目导出到 `.md` 的 JSON 正文
- 临时栏目同步出去的 JSON 正文
- 临时栏目导入 / 同步恢复时，先还原成协议层，再映射回当前运行时 `items`
- 临时栏目本地运行时仍以现有 `items` 为主结构，不强行改成和协议层 / 导出 JSON 同名
- 协议层、导出 JSON、同步 JSON 三者字段保持同一套命名；本地 `items` 继续通过适配器转换

也就是说，临时栏目不再只是“视觉模式导出时临时转成另一套结构”，而是：

- 第一版先把协议层跑通
- 本地运行时 `items` 不要求第一刀立刻整体迁移
- 第一版明确不要求本地 `items` 和导出 JSON 一一同名
- 等协议层稳定后，再决定是否把本地 `items` 真正迁到统一树协议

## 6. 当前最重要的统一目标

这次真正想统一的是：

- 统一永久栏目书签树
- 统一永久栏目副本所引用的正文
- 统一临时栏目书签树
- 统一本地与导出 / 同步之间的树形 JSON

这样做的直接收益是：

- 导入更简单
- 导出更简单
- 同步解析器更简单
- 以后做 AI 改动也更简单

一句话总结就是：

- 视觉模式是显示层
- JSON 模式是协议层
- 永久栏目通过规范化快照 / 协议视图靠齐协议层
- 临时栏目先通过适配层靠齐协议层
- 永久栏目副本走“共享内容源，多视图壳”，不是共享同一个 DOM
- `visual / visual-no-icon` 不要求进入长期协议中转层；真正新增长期协议层的重点，是临时栏目 `json` 链路

---

## 7. 当前必须保留的兼容要求

即使要做这次统一，也必须满足下面这些要求：

### 7.1 永久栏目现有能力不能退化

- 首次同步仍然可用
- 云端覆盖本地仍然可用
- 本地覆盖云端仍然可用
- 永久栏目增量同步 / 覆盖同步仍然继续沿用当前书签树比较流程
- 主栏 / 副本统一内容源后，`copyId`、标题标签、搜索跳转、目录定位、导出节点 id、同步识别这些外部接口不能断
- 折叠、滚动、说明、懒惰加载、路径徽章 / 标识系统允许内部实现调整，但外部行为与现有使用方式不能退化

### 7.2 临时栏目现有能力不能退化

- 视觉模式当前能导出什么，JSON 模式至少也要能表达同样的书签树内容
- 临时栏目特殊来源字段不能丢
- 临时栏目 `label / sequenceNumber / createdAt / originPermanent` 不能丢

### 7.3 插件运行时不能被误塞进协议层

- 卡片位置和样式仍然留在插件自己的存储
- 不把运行时布局塞回 `bookmarkTree`
- 不把四种操作后的颜色标识、路径徽章、懒加载前台状态塞回协议层

---

## 8. 还要继续讨论并锁死的点

目前只剩一个需要在真正开改代码前再锁死的点：

1. `bookmarkTree` 与 `sectionMeta` 的最终字段边界

简单说就是：

- 树节点、`children`、路径型 `id / parentId`、`url` 这些进 `bookmarkTree`
- 栏目级类型、来源、标签、创建时间、说明这类字段进 `sectionMeta`

这个点的顺序边界也要写死：

- 它只在真正开始接入 `JSON模式（供AI）` 的导出 / 导入 / 同步当次锁死
- 不阻塞前面空白栏目、`.canvas`、永久内容源统一、临时栏目协议层这几刀先落地

## 9. 子计划内部推荐落地顺序

整体项目总顺序仍以 [存储收敛与 JSON 模式总顺序计划书](./存储收敛与JSON模式总顺序计划书.md) 为准。

本节只约束“书签树协议层”这一子计划内部的实现顺序。

1. 先锁死统一后的 `bookmarkTree` 字段结构
2. 再锁死 `sectionMeta` 字段结构
3. 再把已锁定的永久副本包装语法接入协议层与导出链路
4. 先补临时栏目 `items <-> bookmarkTree` 适配层
5. 再改导出器
6. 再改导入解析器
7. 协议层跑稳后，再决定是否改本地存储映射
8. 最后改同步解析器与恢复链路
