# Bookmark Canvas 应用级同步元信息实施计划书

> 目标：在现有 Bookmark Canvas 分片同步体系上，新增云端同步账本 `bcs-sync-manifest.json`，用应用级 `updatedAt + hash` 替代 GitHub commit time 作为结构化数据冲突裁决依据。

## 1. 目标与结论

当前同步体系已经具备本地 dirty state、path map、prev sync index、文件级三方比较和冲突面板。需要改造的是远端缺少可信的应用级修改时间，导致历史上的 `newer` 策略容易误用 GitHub commit time。

GitHub commit time 只能说明 Git 历史中的提交时间，不能可靠代表某个业务对象或同步分片的真实修改时间。

本计划的核心结论是采用 **manifest-first / 云端账本优先**：

```text
本地：继续使用 Chrome local storage 里的 dirtyState / prevSyncIndex / pathMap。
云端：在同步导出根目录新增 bcs-sync-manifest.json。
业务文件：不内嵌 bcs:sync。
.canvas：保持 Obsidian 原生结构。
冲突裁决：按 manifest.files[path].updatedAt 比较。
可信校验：按 manifest.files[path].hash 校验实际文件内容。
```

Git/GitHub 只保留为传输层、备份层、版本历史层、单边同步辅助；不再把 GitHub commit time 当作结构化数据自动取胜依据。

## 2. 时间戳格式

采用 Unix epoch milliseconds，也就是 JavaScript `Date.now()` 的数字格式：

```text
1778205123456
```

约定：

- 同步协议内部使用 Unix epoch milliseconds。
- UI 展示时可转为本地时间。
- 不使用本地时区字符串。
- 不使用 Git commit time 作为自动取胜时间。

## 3. 云端账本文件：`bcs-sync-manifest.json`

放在同步导出根目录，与 `说明导入规则.md`、`.canvas`、`永久栏目/`、`临时栏目/` 同级：

```text
同步导出根目录/
├── bcs-sync-manifest.json
├── 说明导入规则.md
├── 书签画布.canvas
├── 永久栏目/
└── 临时栏目/
```

核心原则：

```text
bcs-sync-manifest.json 是同步控制账本，不是普通业务文件。
业务 JSON、Markdown、.canvas 内部不写 bcs:sync。
```

## 4. Manifest 结构

Manifest 使用普通 JSON 文件，只保存 `files[path]` 当前状态表。它逻辑上是同步账本，但不是追加式日志；每个 path 只保留当前最新状态。

```json
{
  "files": {
    "书签画布.canvas": {
      "type": "canvas",
      "updatedAt": 1778205123000,
      "hash": "..."
    },
    "永久栏目/A书签树（永久栏目）.json": {
      "type": "permanent",
      "updatedAt": 1778205121000,
      "hash": "..."
    },
    "临时栏目/常规链式/A-1 示例.json": {
      "type": "temporary",
      "updatedAt": 1778205122000,
      "hash": "..."
    }
  }
}
```

字段说明：

- `files[path]`：每个同步文件的应用级元信息。

Manifest 不设置顶层 `updatedAt` 作为裁决字段。manifest 自身不是业务对象，不按“账本文件谁新”决定整包胜负；每次同步都会读取远端 manifest，并按 `files[path]` 条目逐个 path 比较。

每个 `files[path]` 条目：

- `type`：文件类型。
- `updatedAt`：该业务文件的应用级修改时间。
- `hash`：该业务文件内容 hash。

Manifest 不记录完整历史流水，也不记录目录树。它只回答一个问题：

```text
这个 path 当前最新的应用级修改时间和内容 hash 分别是什么？
```

## 5. hash 规则

直接 hash 业务文件最终内容：

```text
manifest.files[path].hash = hash(业务文件最终内容)
```

因为 sync meta 不再写入业务文件，所以不需要处理 `bcs:sync.hash` 自引用问题。

若 manifest 记录的 hash 与实际文件内容不一致：

```text
该 path 的 manifest 元信息不可信。
该 path 不允许按 updatedAt 自动取胜。
进入手动冲突或修复流程。
```

## 6. 受管文件范围

纳入 manifest 管理的文件：

- 永久主栏目 JSON。
- 永久副本 anchor JSON。
- 临时栏目 JSON。
- `.canvas` 文件。
- 视觉 Markdown 文件。

Manifest 方案不修改这些文件内部结构，`.canvas` 保持 Obsidian 原生结构。

## 7. 改造现有本地账本

本地不新增第二套 manifest 存储，继续复用并扩展现有同步状态：

```text
prevSyncIndex：继续作为本地“上次同步基线”。
dirtyState：继续作为本地“本轮脏变更来源”。
pathMap：继续作为业务对象到同步 path 的映射。
```

`bcs-sync-manifest.json` 是云端共享账本，不应再在 Chrome local storage 里完整复制一份新的本地 manifest。需要保存到本地的 manifest 信息，应落到现有 `prevSyncIndex.files[path]` 里。

它们通常在启用同步、发生本地变更、首次同步成功、推送/拉取成功或重建同步索引时写入。关闭同步或尚未初始化同步时，这些记录可以不存在或为空；它们丢失后不会导致业务文件丢失，只是会失去一部分“上次同步基线”和“本地变更来源”，必要时需要重新建立基线。

`prevSyncIndex.files[path]` 保留现有字段，并增加 `appUpdatedAt`：

```json
{
  "hash": "...",
  "sha": "...",
  "size": 123,
  "mtime": 1778205000000,
  "syncedAt": 1778205000000,
  "appUpdatedAt": 1778205123456
}
```

字段职责：

- `hash`：本地业务文件内容 hash。
- `sha`：GitHub 远端文件版本标识，用于判断远端文件是否变化。
- `size`：文件大小。
- `mtime`：旧同步索引时间，不作为业务修改时间。
- `syncedAt`：同步成功时间。
- `appUpdatedAt`：该 path 上次同步成功时的应用级修改时间。

兼容原则：

- 保留旧字段。
- `appUpdatedAt` 缺失时按 `0` 处理。
- 旧用户升级后不应触发异常。

需要调整的函数：

- `normalizePrevSyncIndex()`
- `savePrevSyncIndex()`
- `pushObsidianFilesIncremental()`
- 重建 prev index 的相关逻辑。

## 8. Push 流程

```text
1. bridge.buildSyncFiles() 生成业务同步文件。
2. 排除 bcs-sync-manifest.json，计算每个业务文件 hash。
3. 加载 dirtyState、prevSyncIndex。
4. 为每个 path 生成 manifest.files[path]。
5. 若业务内容变化或 path dirty，则更新 updatedAt。
6. 若业务内容未变化，则尽量沿用 prevSyncIndex 中的 appUpdatedAt。
7. 只有本次需要写云端时，才将 bcs-sync-manifest.json 加入待上传文件列表。
8. 上传本次变化的业务文件和对应更新后的 manifest。
9. 同步成功后更新 prevSyncIndex 的 appUpdatedAt，并继续维护现有 hash/sha/size/syncedAt。
```

`updatedAt` 来源优先级：

```text
dirtyState.pathUpdatedAt[path]
> dirtyState.updatedAt
> Date.now()
```

重要约束：

```text
业务文件未变化时，不应仅因为 push 刷新该 path 的 updatedAt。
```

否则会制造假冲突。

## 9. Pull 流程

保留现有三方比较模型：

```text
prev baseline
local current
remote current
```

同步仍然是文件级合并计划，不是内容级合并：

```text
本地没变，云端没变 => 跳过
本地变了，云端没变 => 上传
本地没变，云端变了 => 下载
本地变了，云端也变了 => 走冲突策略
```

同步不是整包本地覆盖云端，也不是整包云端覆盖本地；它是按受管业务文件逐个生成上传、下载、跳过、冲突计划。

所有同步入口，包括同步按钮、push 按钮和 pull 按钮，都先读取远端：

```text
bcs-sync-manifest.json
```

远端 manifest 读取函数：

```js
readRemoteBcsSyncManifest(rootPath)
```

若远端 manifest 不存在，不能立即假设云端为空，也不能直接进入整包覆盖。必须先读取远端受管文件结构：

```text
1. 读取远端文件清单 path/sha/size。
2. 若远端受管业务文件也为空 => 视为云端空仓，可直接按本地当前文件初始化云端，并生成新的 manifest。
3. 若远端存在受管业务文件但 manifest 缺失 => 视为旧仓、manifest 被删除或 manifest 损坏，不能使用 updatedAt 自动裁决。
4. 对非空旧仓按现有 sha/hash 基线尽量重建；无法确认 winner 的路径进入手动冲突或初始化确认流程。
```

如果同步后端提供文件 mtime，可以作为展示、诊断或初始化确认的辅助信息，但不能替代 manifest：

```text
manifest 存在 => 以 manifest.files[path].updatedAt 为准。
manifest 缺失且远端为空 => 用本地当前文件初始化 manifest。
manifest 缺失且远端非空 => 云端 mtime 只作为人工确认辅助，不能自动裁决 winner。
人工确认基线后 => 写入 manifest.files[path].updatedAt/hash，后续回到 manifest-first。
```

只有当发现：

```text
localChanged && remoteChanged
```

才使用本地 app meta 与远端 manifest meta 做自动裁决。必要时读取冲突路径远端文件内容，校验 `manifest.files[path].hash` 是否等于实际内容 hash。

按时间判断时使用应用级时间：

```text
本地 appUpdatedAt vs 远端 manifest.files[path].updatedAt
```

### 9.1 文件级同步情况

同步时不要先把云端整包拉下来覆盖本地，也不要先把本地整包推上去覆盖云端。正确模型是先构建文件级计划，再执行计划。

每个 path 都按同一套规则判断：

```text
本地没变，云端没变 => skip
本地变了，云端没变 => upload
本地没变，云端变了 => download
本地变了，云端也变了，且内容 hash 相同 => skip content，更新本地基线
本地变了，云端也变了，且内容 hash 不同 => 进入冲突策略
```

同一轮同步可以同时存在多种结果：

```text
A.json 只有本地变 => 上传 A.json
B.json 只有云端变 => 下载 B.json
C.json 本地云端都变 => 按冲突策略决定上传或下载 C.json
D.json 都没变 => 不处理 D.json
```

纯下载不回写云端 manifest 只适用于本轮没有任何需要写云端的业务变化：

```text
本轮只有 download / skip => 不回写云端 manifest，只更新本地 prevSyncIndex。
本轮包含 upload => 需要回写云端 manifest，但只更新被上传的 path 条目。
本轮包含 upload + download => 上传项更新 manifest；下载项沿用云端 manifest，并写入本地基线。
```

## 10. 双端冲突取胜规则

只有同时满足以下条件，才允许自动按时间取胜：

- 本地有该 path 的可信 app meta。
- 远端 manifest 有该 path 的可信 app meta。
- 本地业务文件 hash 与本地 app meta 匹配。
- 远端业务文件 hash 与远端 manifest meta 匹配。
- 两边 `updatedAt` 都是有效 Unix epoch milliseconds。
- 两边 `updatedAt` 不相等。
- 时间没有明显异常。
- 当前路径确实是 `localChanged && remoteChanged`。

取胜规则：

```text
localMeta.updatedAt > remoteMeta.updatedAt
=> upload

remoteMeta.updatedAt > localMeta.updatedAt
=> download
```

以下情况必须进入手动冲突：

- manifest 缺失且远端受管业务文件非空，无法建立可信 meta。
- path 条目缺失。
- hash 不匹配。
- 时间相等但内容不同。
- 时间无效。
- 远端读取失败。
- baseline 不完整。

## 11. Manifest 不是普通文件

这是 manifest 方案的核心防守规则。

错误做法：

```text
把 bcs-sync-manifest.json 当普通文件参与 localChanged/remoteChanged 冲突。
```

正确做法：

```text
1. 所有同步入口先读取远端 manifest。
2. manifest 缺失时先读取远端受管文件清单，区分空仓和非空旧仓。
3. 以远端 manifest 作为当前云端账本底本；若为空仓则以本地当前文件初始化新 manifest。
4. 按业务文件生成上传、下载、跳过、冲突计划。
5. 只有本次需要写云端时，才更新 manifest 中对应 path 的条目。
6. 纯下载云端文件时，不回写云端 manifest，只更新本地 prevSyncIndex。
```

这样可以避免：

```text
两端改了不同业务文件，却因为 manifest 同时变化而误判全局冲突。
```

manifest 的合并不是复杂内容合并，只是按 path 更新账本条目：

```text
本地上传 A.json => 更新云端 manifest 里的 A.json 条目。
云端下载 B.json => 保留云端 manifest 里的 B.json 条目，本地记录为新基线。
同一个 C.json 两边都改 => 按用户策略处理；如果选择按时间，则比较 manifest/appUpdatedAt。
```

## 12. Guard / 防守员设计

同步元信息 guard：

```js
normalizeBcsSyncManifest(raw)
buildLocalBcsSyncEntries(files, dirtyState, prevSyncIndex)
computeManagedFileHash(file)
validateManifestFileEntry(path, file, entry)
readRemoteBcsSyncManifest(rootPath)
mergeBcsSyncManifestEntries(remoteManifest, localEntries, plan)
getAppMetaForPath(path, prevSyncIndex, remoteManifest)
decideWinnerByManifestUpdatedAt(localMeta, remoteMeta)
```

`validateManifestFileEntry()` 应返回结构化结果：

```js
{
  trusted: false,
  reason: 'hash-mismatch',
  updatedAt: 0,
  hash: ''
}
```

这样冲突面板可以展示明确原因。

常见 reason：

- `manifest-missing`
- `entry-missing`
- `hash-mismatch`
- `invalid-updated-at`
- `same-updated-at`
- `remote-file-unavailable`
- `baseline-missing`

## 13. UI 与策略文案

`newer` 策略的含义应改为：

```text
按云端同步账本中的应用级修改时间取胜。
```

不再出现：

```text
local dirty time vs cloud commit time
```

冲突面板应展示：

- 本地 appUpdatedAt。
- 远端 manifest updatedAt。
- 本地 hash 是否可信。
- 远端 hash 是否可信。
- 无法自动取胜的原因。

示例文案：

```text
无法按应用级修改时间自动裁决：远端 manifest 中该文件 hash 与实际内容不匹配。
```

## 14. 导入规则与 AI 编辑约束

同步导出目录中的 `说明导入规则.md` 应包含同步元信息规则：

```text
bcs-sync-manifest.json 是同步账本。
修改任意受管同步文件后，必须更新 manifest.files[path]。
updatedAt 使用 Unix epoch milliseconds。
hash 必须匹配实际业务文件内容。
不能使用 Git commit time 作为应用修改时间。
不能把 bcs:sync 写入业务 JSON、Markdown 或 .canvas。
无法重算 hash 时不要伪造，应保留冲突给插件处理。
```

AI 编辑规则：

```text
Preserve valid JSON.
Preserve .canvas top-level nodes and edges.
Do not embed bcs:sync into business files.
Update bcs-sync-manifest.json when changing managed sync files.
Use Unix epoch milliseconds for manifest.files[path].updatedAt.
Recompute hash for changed files.
Never use GitHub commit time for conflict winner decisions.
```

## 15. 测试清单

静态检查：

```text
node --check history_html/sync/obsidian-git-sync.js
node --check history_html/bookmark_canvas_module.js
git diff --check
```

功能测试：

- push 后同步目录包含 `bcs-sync-manifest.json`。
- 业务文件内容不因 sync meta 被改写。
- `.canvas` 内部结构不新增 `bcs:sync`。
- 本地单边改临时栏目，只上传对应分片。
- 远端单边改临时栏目，只下载对应分片。
- 本地无变化时不刷新 `updatedAt`。
- 双端改不同文件，不因 manifest 同时变化而误判全局冲突。
- 双端改同一文件，本地 `updatedAt` 较新则上传。
- 双端改同一文件，远端 `updatedAt` 较新则下载。
- 双端改同一文件，时间相同但内容不同则冲突。
- manifest 缺失且远端为空时初始化云端 manifest。
- manifest 缺失且远端非空时不自动按时间取胜。
- hash 不匹配则冲突。
- 旧云端文件无 manifest 时不误自动覆盖。

## 16. 风险与约束

风险：

- 第三方编辑器或 AI 只改业务内容，不改 manifest。
- manifest 可能成为共享热点，必须结构化处理。
- 设备时钟错误导致 `updatedAt` 不可信。
- path 重命名/移动时必须同步更新 manifest key。

约束：

- `updatedAt` 不能单独决定 winner，必须结合 hash guard。
- manifest 与实际文件不一致时，以“不可信”处理。
- 自动裁决必须保守，无法确认时进入手动冲突。
- GitHub commit time 不参与自动 winner。

## 17. 最终原则

```text
本地账本：dirtyState / prevSyncIndex / pathMap。
云端账本：bcs-sync-manifest.json。
共同索引：files[path]。

业务文件保持干净。
.canvas 保持 Obsidian 原生结构。
manifest 是当前状态账本，不是业务文件，也不是追加历史日志。
hash 负责可信性。
updatedAt 负责先后顺序。
prevSyncIndex 负责本地基线。
dirty state 负责本地修改来源。
文件级三方比较负责上传、下载、跳过、冲突计划。
冲突面板负责兜底。
GitHub commit time 不负责自动裁决。
```
